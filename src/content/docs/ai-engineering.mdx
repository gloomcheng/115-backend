你把一段程式碼交給 AI。幾秒後，它改了四個檔案，還說「已完成」。

現在真正要問的不是它寫得快不快，而是：它看見了什麼？哪個步驟產生這段 code？誰驗證它沒有破壞 API？

AI 工程不是把 prompt 寫得漂亮。它是把一個會產生機率性輸出的模型，放進有資料、工具、權限、測試與 log 的系統。

<Callout type="note" title="這個單元的先備知識">
  先學過 HTTP、JSON、路由、資料庫、認證與 log，再來追模型內部。這一單元不要求你訓練大型模型；你要能指出每個機制解決哪個問題，以及它在哪裡可能失敗。
</Callout>

<Callout type="warning" title="把這四條規則帶回 backend">
  這門課允許你使用 AI，但不把責任交給模型。先看需求與上下文，再問模型；不要貼上 `.env`、API key、Token 或個人資料；模型提出的 patch 或 tool call 要在模型外通過 schema、身分與權限檢查；最後用測試、`curl` 與 log 證明結果，並說明 AI 幫了哪裡。這套規則參考[臺大生成式 AI 工具之教學因應措施](https://www.dlc.ntu.edu.tw/ai-tools/) 與 [數位發展部 AI 產業人才認定指引](https://moda.gov.tw/ADI/services/publications/19692)。
</Callout>

## 01. 為什麼文字要切成 token？

模型不能直接讀懂「fix the login bug」這個人類字串。它先把文字切成 token，再把 token 映射成整數 ID。模型接收到的是數字序列，不是字典裡的單字。

## 02. 為什麼 token 要變成向量？

整數 ID 只能表示「這是哪個 token」。它沒有表示 token 之間的關係。模型需要一個可以被加法、乘法與線性變換處理的表示，所以每個 token 會先進入 embedding table，取出一個向量。

這裡先分清兩種 embedding：token embedding 是模型內部處理文字的表示；text embedding 是拿來做文件或查詢相似度搜尋的表示。兩者都叫 embedding，但用途、模型與評估方式不必相同。

<Terminal title="bash — toy vector distance">{`
python3 - <<'PY'
vectors = {
    "login": [1.0, 0.0],
    "signin": [0.9, 0.1],
    "database": [0.0, 1.0],
}
score = sum(a * b for a, b in zip(vectors["login"], vectors["signin"]))
print("login · signin =", score)
PY
`}</Terminal>

這個數字不是「相似度真理」。它只示範向量可以被比較；真正的空間是模型用訓練資料學出來的。

## 04. 為什麼 attention 能建立上下文關聯？

attention 的核心不是「模型突然理解整句話」。它是讓每個 token 根據其他 token 的分數，取回一份加權資訊。

為什麼它看起來很快？因為 `QKᵀ` 可以用矩陣乘法一次算出很多 token 對之間的分數，GPU 可以平行處理。不是因為關聯變少；標準 self-attention 對長度 `n` 的成本仍大致是 `n²`。

## 05. 為什麼需要 multi-head attention？

一個 attention head 不必負責所有關係。不同 head 可以在不同表示空間裡學不同線索，例如語法、指代、括號配對或程式碼中的呼叫關係。

## 06. 為什麼 attention 後面還要有 MLP？

attention 比較像把其他位置的資訊搬回目前 token。它搬回來之後，還需要一個非線性轉換，把多種特徵重新組合。這就是 Transformer block 裡的 feed-forward network / MLP 所負責的工作。

## 07. 為什麼模型需要 MoE？

如果每個 token 都經過同一個 feed-forward network，所有輸入共享同一條計算路徑。MoE 放入多個 expert，讓 router 依 token 的表示選擇少數路徑。

PY
`}</Terminal>

## 08. 為什麼模型可以寫程式？

模型不是先理解「需求」，再像工程師一樣設計程式。它根據訓練過的 token 關係，逐步預測下一個 token。程式碼的語法、慣例與 API 使用方式都會成為可預測的結構，但可預測不等於正確。

## 09. 為什麼模型需要 context window？

模型只能直接使用這次輸入的 token。context window 是模型一次可以處理的輸入與輸出範圍，不是無限記憶體。

## 12. 為什麼需要 tool calling？

## 15. 為什麼 Agent 需要結構化狀態？

第 09 節講了 context window 是有限的。接著還有更麻煩的一件事：**對話會被 compact**。被 compact 掉的不是重複，是細節——包含 Agent 已經排好的工作順序。

如果工作順序只活在對話的散文裡，它會跟著 compact 一起衰敗。Agent 會忘記自己答應過要做什麼，而且不會承認自己忘記，它會很流暢地從頭開始。

解法不是寫更好的摘要，而是把工作順序從散文裡拿出來。**能結構化就結構化**：計畫狀態交給 host 保存與重播，模型不負責重述。實際上有四條通道，每一條都不依賴模型記得。

這四條通道其實都是 backend 的基本功：**append-only 的事件記錄，加上從記錄重播狀態，再加上每次寫入前的驗證**。單元 10 開始，每一個單元都會把當週的主題接進同一個 `agent-harness` 專案，到期末專題時它是一個跑得起來的系統。

<Terminal title="bash — 狀態寫在事件記錄裡，不是模型重述的">{`
$ cat events.jsonl
{"event_id": "45712ffb6e20453baeb09507eaed6609", "observed_at": "2026-10-24T02:55:48Z", "op": "tool_result", "payload": {"tool_call_id": "call_1", "tool_name": "todowrite", "details": {"todos": [{"content": "write the replay tests", "status": "pending"}]}}}
`}</Terminal>

單元 10 的 harness 只有寫入端與讀取端；單元 12 加上了重播端 `/state`，把事件記錄還原成一份狀態：

```json
{
  "todos": [{"content": "write the replay tests", "status": "pending"}],
  "counts": {"pending": 1, "in_progress": 0, "completed": 0, "cancelled": 0, "unknown": 0},
  "confirmed": true,
  "source_event_id": "e3406a8ab325433798037f0258b83f05",
  "updated_at": "2026-10-24T10:03:06Z",
  "last_failed_event_id": null
}
```

`confirmed` 這個欄位是重播的核心：**只有被成功結果確認過的寫入才算狀態**，失敗的寫入不覆蓋先前的狀態，而是被記在 `last_failed_event_id`。單元 13 會把這條規則寫成斷言。

被拒絕的寫入不會出現在狀態裡，因為它根本沒進事件記錄。**記錄裡只裝被接受的東西，重播就不需要猜。**

## 16. 期末專題：續接之後，計畫不遺失

第 15 節說「把工作順序從散文裡拿出來」，但還沒回答一個實際問題：**續接的時候，那份結構化狀態要怎麼交給下一個 session？**

直覺答案是寫一段摘要。那個答案是錯的，原因要講準確：**摘要是散文，而散文是副本。同一件事的兩份副本會開始分歧，一旦有人改其中一份，沒有人能說得清哪一份才對。**

所以期末專題把 checkpoint 分成兩半：

- **散文**說工作要去哪裡，並指向附錄。它**不列**任務。
- **附錄**放任務清單，版本化的結構化格式，程式讀得懂。

<Terminal title="bash — the checkpoint, both halves" flavor="output">{`
$ curl -s 'http://127.0.0.1:8010/checkpoint?goal=ship%20the%20replay%20tests' \\
    -H "Authorization: Bearer $TOKEN" | python -m json.tool
{
  "prose": "Goal: ship the replay tests\\n\\nThe task list is in the appendix below. That appendix is the only copy of it.",
  "appendix": "<harness-context version=\\"1\\">\\n  <task-state confirmed=\\"true\\" source-event-id=\\"e3406a8ab325433798037f0258b83f05\\" updated-at=\\"2026-10-24T10:03:06Z\\">\\n    <todo status=\\"pending\\">write the replay tests</todo>\\n    <todo status=\\"completed\\">design the replay rules</todo>\\n  </task-state>\\n</harness-context>"
}
`}</Terminal>

散文裡**沒有**任務清單。清單只在附錄裡，而且附錄有版本號——不知道版本的讀者，不知道自己在看什麼。

附錄是寫給程式看的，那程式就得讀得回去。這個往返是防止格式慢慢變成只有人看得懂的最後一道保險：

```python
from harness.appendix import parse_appendix

parsed = parse_appendix(appendix)
```

## 單元實作作業

建立一個最小的 AI coding proof，不要先做聊天機器人：

1. 準備三個小型 repository 問題，每題都有明確的 expected result。
2. 讓模型提出 patch，但把檔案寫入限制在 sandbox。
3. 執行測試、收集 diff、stdout、stderr、延遲與 token 使用量。
4. 加入一份含有錯誤指令的文件，觀察 RAG 或 Agent 是否把它當成權限命令。
5. 最後提交一張流程圖：`input → model → retrieval / tool → policy → test → result`。
6. 補上一段責任說明：你給了模型哪些去識別化的上下文、哪些建議被你拒絕，以及哪一個測試讓你接受最後的 patch。

這份流程圖比「模型回答得很像人」更能證明你知道系統在哪裡做決定。

7. 走完第 16 節的期末專題：`curl -s 'http://127.0.0.1:8010/checkpoint?goal=你的目標'` 的輸出截圖，必須同時看得到散文與附錄；`pytest -q -k checkpoint` 截圖。**回答兩個問題：(a) 附錄為什麼要有版本號？(b) 如果散文也把任務清單列出來，會發生什麼事？**
