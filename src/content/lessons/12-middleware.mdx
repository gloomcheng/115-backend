## 01. 連路由都沒比到的請求，也會經過它

先打一個這支 API 完全沒有定義的路徑：

<Terminal title="bash — a path with no route at all" flavor="output">{`
> curl -i http://127.0.0.1:8005/nope
< HTTP/1.1 404 Not Found
< x-trace: outer:in > inner:in > inner:out > outer:out
< x-request-id: r0001

{"detail":"Not Found"}
`}</Terminal>

`404`，但 `x-trace` 與 `x-request-id` 兩個 Header 都在。**這條路徑沒有任何路由可比，中介軟體還是跑完了，並且在 Response 上寫了兩個 Header。**

FastAPI 官方文件對中介軟體的定義是：它處理「every request **before it is processed by any specific path operation**」。位置就在路由比對之前。

<Callout type="important" title="這決定了 log 該寫在哪裡">
  打到不存在的路徑、使用者打錯字、機器人來爬 `/wp-login.php`——這些請求永遠不會進入任何 handler。如果 log 寫在 handler 裡，這些全部不會被記錄。寫在中介軟體裡，全部都會。
</Callout>

## 02. 巢狀：進去照順序，回來照相反

這條位置還決定了第二件事：**多個中介軟體怎麼串。**`x-trace` 這個 Header 是為了讓巢狀看得見而存在的，看它的順序：

<Terminal title="bash — the nesting order in one header" flavor="output">{`
> curl -i http://127.0.0.1:8005/open | rg -i '^x-trace'
< x-trace: outer:in > inner:in > inner:out > outer:out
`}</Terminal>

進去是 `outer` 然後 `inner`，回來是 `inner:out` 然後 `outer:out`。**`call_next` 是一道門**：門前面的是進去，門後面的是裡面，回來時順序反過來。

這裡的「外面」指的是離入口最近的那一層，也就是每個 Request 最先碰到的那個。這一串 `x-trace` 裡 `outer` 最先出現，就是這個意思。

順序不是自己排的，是註冊順序決定的，而且方向和直覺相反：

<Terminal title="FastAPI — Multiple middleware execution order">{`
The last middleware added is the outermost, and the first is the innermost.
On the request path, the outermost middleware runs first.
On the response path, it runs last.
`}</Terminal>

**最後註冊的那個在最外面，也就是每個 Request 最先跑的那一層。** 所以 `main.py` 裡 `trace_inner` 寫在 `trace_outer` 前面，`trace_outer` 才會先進去。

把這兩個 block 對調，會發生什麼？`trace_inner` 變成最外層，於是它在 `trace_outer` 之前執行，而 `request.state.trace` 還沒被建立：

<Terminal title="Terminal 1 — after swapping the two blocks" flavor="output">{`
AttributeError: 'State' object has no attribute 'trace'

> curl -i http://127.0.0.1:8005/open
< HTTP/1.1 500 Internal Server Error
`}</Terminal>

`/open` 這條路由本身完全正常。**壞掉的是中介軟體，而外面只看到一個 `500`。**

<Callout type="note" title="單元 03 與 07 的規則第三次出現">
  單元 03 說過：責任是在五個階段的哪一步被決定的。這裡的答案是「在路由比對之前」。所以中介軟體裡的例外和 handler 裡的例外，從 Client 看到的一樣都是 `500`，沒有任何線索指向真正出錯的地方。例外要留 traceback 在 Server 終端機，這也是單元 15 會接回來的主題。
</Callout>

## 03. 看得到「是誰來的」，看不到「要做什麼」

中介軟體執行的時候，`method`、`path`、所有 `Header` 都已經讀得到了（Request 物件在第一個位元組到達時就組好）。但還沒有人去比對路由表，所以它不知道：

- 這次請求會對上哪一條路由
- 那條路由要不要認證
- 如果要認證，該用哪一種認證方式

第三點最要緊。單元 11 講過，`401` **必須**帶 `WWW-Authenticate`，而裡面的 `realm` 是每一個保護範圍各不同的。一個「保護所有路由」的中介軟體如果想回正確的挑戰，它必須先知道每條路由的設定——而那正是它還不知道的事。

所以這支 API 的寫法是：認證與權限掛在路由上，不是掛在中介軟體上。

<Terminal title="exercises/12-middleware/main.py — the check lives on the route" flavor="output">{`
def current_subject(authorization: str | None = Header(default=None)) -> str:
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(status_code=401, detail="Missing credentials", headers=CHALLENGE)
    return read_token(authorization.removeprefix("Bearer ").strip())["sub"]


def require_admin(subject: str = Depends(current_subject)) -> str:
    if USERS[subject]["role"] != "admin":
        raise HTTPException(status_code=403, detail="Admins only")
    return subject
`}</Terminal>

`/open` 什麼都沒有掛，`/profile` 掛 `current_subject`，`/admin` 掛 `require_admin`。差別是宣告出來的，不是中介軟體猜出來的。

## 04. 權限不等於驗證：role 一律從 Server 自己的表拿

現在做這支 API 最故意的設計。先登入管理員，然後把 token 的 payload 解出來看：

<Terminal title="Terminal 2 — bash — log in both accounts">{`
export STUDENT=$(curl -s -X POST http://127.0.0.1:8005/login \\
  -H 'Content-Type: application/json' \\
  -d '{"name":"iris","password":"lesson"}' \\
  | python3 -c "import json,sys;print(json.load(sys.stdin)['access_token'])")

export ADMIN=$(curl -s -X POST http://127.0.0.1:8005/login \\
  -H 'Content-Type: application/json' \\
  -d '{"name":"root","password":"lesson"}' \\
  | python3 -c "import json,sys;print(json.load(sys.stdin)['access_token'])")

python3 -c "
import base64, json, sys
p = sys.argv[1].split('.')[1]
print(json.loads(base64.urlsafe_b64decode(p + '=' * (-len(p) % 4))))
" "$ADMIN"
`}</Terminal>

管理員的 token 裡，role 這一欄寫的是 `intern`：

<Terminal title="the admin token's own role claim" flavor="output">{`
{'sub': 'root', 'role': 'intern', 'exp': 1790956815}
`}</Terminal>

**這個欄位是故意寫錯的。**現在拿它去打只有管理員能用的路徑：

<Terminal title="bash — the wrong claim does not matter" flavor="output">{`
> curl -i http://127.0.0.1:8005/admin -H "Authorization: Bearer $ADMIN"
< HTTP/1.1 200 OK

{"sub":"root","admin_panel":true,"role_source":"server table"}
`}</Terminal>

`200`。因為 `require_admin` 沒有讀 token 裡的 `role`，它拿 `sub` 去 `USERS` 這張表查。token 裡那個寫錯的欄位完全沒有被使用。

換成學生的 token，同一條路徑：

<Terminal title="bash — the same route, a student token" flavor="output">{`
> curl -i http://127.0.0.1:8005/admin -H "Authorization: Bearer $STUDENT"
< HTTP/1.1 403 Forbidden

{"detail":"Admins only"}
`}</Terminal>

<Callout type="warning" title="這裡修掉了單元 11 的一個弱點">
  單元 11 的 `/admin` 是直接讀 token 裡的 `role`。那份教學程式能運作，因為 payload 有簽名、沒被改過。但它把「這個人是誰」和「這個人能做什麼」綁在同一個簽發動作上：**任何有簽發權限的人，權限就跟著 token 一起發出去。**

  改成查表之後，token 只回答「是誰」。角色是 Server 用自己的資料決定的，要改就改那張表，並且留下紀錄。`role_source` 這個欄位就是為了讓你在回應上看見它。
</Callout>

## 05. 未宣告欄位要拒絕，不要忽略

同一個問題在單元 10 出現過，而且那一次更安靜：那邊 `POST /strict` 送 `{"name":"iris","admin":true}` 進去，`admin` 被安靜地丟掉了，沒有任何錯誤。那一節的最後一句是：怎麼宣告禁止未宣告欄位，在單元 12 處理。

宣告的方式是一行：

<Terminal title="exercises/12-middleware/main.py — refusing what was not declared" flavor="output">{`
class ProfileIn(BaseModel):
    # extra="forbid" turns a silent drop into a 422 that names the field.
    model_config = ConfigDict(extra="forbid")

    nickname: str
`}</Terminal>

送一個沒有宣告的欄位進去：

<Terminal title="bash — the undeclared field is now named" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8005/profile \\
>   -H 'Content-Type: application/json' \\
>   -H "Authorization: Bearer $STUDENT" \\
>   -d '{"nickname":"iris","is_admin":true}'
< HTTP/1.1 422 Unprocessable Entity

{"detail":[{"type":"extra_forbidden","loc":["body","is_admin"],"msg":"Extra inputs are not permitted","input":true}]}
`}</Terminal>

`type` 是 `extra_forbidden`，`loc` 精確指到 `["body","is_admin"]`。單元 07 教過的 `loc` 就是給 Client 定位用的——這一次它指的不是型別不對，而是「這個欄位不該存在」。

<Callout type="important" title="忽略與拒絕的差別，是 Client 會不會知道">
  忽略：Client 送出 `is_admin`，收到 `201`，以為設定成功。實際上什麼都沒發生。
  拒絕：Client 送出 `is_admin`，收到 `422`，而且 `loc` 告訴它是 body 裡的 `is_admin`。

  在顯示名稱這種欄位上，兩個差別只是使用者困惑。在權限欄位上，這就是資安差別——**一個被忽略的權限欄位，等於一個你以為有設但其實沒設的權限。**
</Callout>

## 06. 密鑰在哪：環境變數，不是程式碼

回到啟動時那個 `SIGNING_KEY=...`。把環境變數拿掉，看這個程式怎麼反應：

<Terminal title="bash — the app refuses to start without a key" flavor="output">{`
$ python -c "import main"
RuntimeError: SIGNING_KEY is not set. A signing key belongs in the
environment; hardcoding one here would put it in version control.
`}</Terminal>

它不是印一句警告然後用預設值繼續跑，而是**拒絕啟動**。這是刻意的：如果程式裡有 `SIGNING_KEY = "..."` 這一行，那一行就會進 Git，進每一個人的 clone，而且刪掉之後歷史裡還在。

接著要看目前生效的是哪一把金鑰，用這支 API 提供的端點：

<Terminal title="bash — a fingerprint, never the key itself" flavor="output">{`
> curl -s http://127.0.0.1:8005/key-info
{"key_fingerprint":"4ce62386","source":"environment variable"}
`}</Terminal>

回應裡是指紋，不是金鑰。金鑰永遠不該被印出來。

<Callout type="note" title="為什麼是指紋">
  金鑰需要能被比較（「現在這把跟上次那把是不是同一把？」），但不需要能被讀回來。雜湊函式把這兩件事分開：你可以放心地比較 `4ce62386` 和 `05e21816` 而不必讓任何人看到金鑰本身。`sha256` 在這裡不是拿來保護金鑰，是拿來讓金鑰可以被指名而不被洩漏。
</Callout>

## 07. 換一把金鑰：無狀態的帳單終於結清

單元 11 留下一筆債：Server 無法把你的登入清掉。這裡是答案，而且是可以真的觀察到的。

再開一個 Terminal 3，用**不同的金鑰**啟動同一支程式：

<Terminal title="Terminal 3 — bash — the same code, a different key">{`
cd exercises/12-middleware
SIGNING_KEY=lesson-12-key-b fastapi dev main.py --port 8006
`}</Terminal>

兩把金鑰的指紋不同：

<Terminal title="bash — two instances, two keys" flavor="output">{`
> curl -s http://127.0.0.1:8005/key-info
{"key_fingerprint":"4ce62386","source":"environment variable"}

> curl -s http://127.0.0.1:8006/key-info
{"key_fingerprint":"05e21816","source":"environment variable"}
`}</Terminal>

現在把 Terminal 2 拿到的那枚 token 送到 8006：

<Terminal title="bash — a token signed by the other key" flavor="output">{`
> curl -i http://127.0.0.1:8006/profile -H "Authorization: Bearer $STUDENT"
< HTTP/1.1 401 Unauthorized
< www-authenticate: Bearer realm="lesson-12"

{"detail":"Bad signature"}
`}</Terminal>

`401`。**同一枚 token，在 8005 還能用，在 8006 就不能用了。**

<Callout type="important" title="這就是撤銷，但要注意它的範圍">
  換金鑰會讓**所有已發出的 token 同時失效**——不是某一枚，是全部。剛才那枚是 student 的，admin 那枚一樣會死。

  所以這是一個粗體的工具：它處理「金鑰外洩」「有人拿到舊 token」「你發現權限設錯了要全部收回」這三種狀況，而且因為 Server 完全不需要保存狀態，做這件事的成本是零。代價是每個登入中的人都被迫重新登入一次。

  真正麻煩的是「只踢掉一個人」。那需要 Server 記住「這一枚已經作廢」，記住這件事本身就是狀態，而狀態正是單元 01 說 HTTP 沒有提供的東西。實務上的做法是折衷：把 `exp` 設短（單元 11 的做法），讓撤銷的視窗小到可以接受，再用換金鑰處理真正嚴重的事件。
</Callout>

## 08. 速率限制：拒絕之前，你得先活著

第 07 節才剛換完金鑰，第 04 到 06 節都在拒絕不該進來的人。但那些判斷要花時間：要讀 Header、要驗簽章、要查表。**一個不帶任何憑證的 Client 照樣能把這些步驟全部走完。**

**你的 Server 只有一顆 CPU。**一個不帶憑證的 Client 送出 10 000 個請求，不代表這支 API 很受歡迎，可能只代表有人正在打你。

<Callout type="important" title="速率限制是唯一一個「沒登入也適用」的控制">
  `401`、`403` 都要先知道你是誰才能判斷。速率限制不用——它只需要知道「這個來源剛剛叫了幾次」。

  這就是它必須寫在中介軟體裡、而且必須是最外層的原因：它是唯一一個**連路徑都還沒比對，就已經在做決定**的控制。
</Callout>

### 08.1 429 不是 403

先分清楚這三個碼。它們都會回給同一個 Client，但意義完全不同：

| 狀態碼 | 意思是 | Client 該做的事 |
| --- | --- | --- |
| `401` | 你還沒證明你是誰 | 去登入 |
| `403` | 知道你誰了，但你不能做這件事 | 別再試了 |
| `429` | 你沒問題，只是**太頻繁** | 等一下再試 |

<Terminal title="exercises/12-middleware/main.py — the limiter" flavor="output">{`
RATE_LIMIT = 30
RATE_WINDOW = 60.0
_hits: dict[str, tuple[int, float]] = {}


@app.middleware("http")
async def rate_limit(request: Request, call_next):
    client = request.client.host if request.client else "unknown"
    now = time.time()
    window_start = now - (now % RATE_WINDOW)
    count, seen_start = _hits.get(client, (0, window_start))
    if window_start != seen_start:
        count = 0
    if count >= RATE_LIMIT:
        retry_after = int(RATE_WINDOW - (now % RATE_WINDOW)) + 1
        return JSONResponse(
            status_code=429,
            content={"detail": "Rate limit exceeded"},
            headers={"Retry-After": str(retry_after)},
        )
    _hits[client] = (count + 1, window_start)
    response = await call_next(request)
    response.headers["x-ratelimit-limit"] = str(RATE_LIMIT)
    response.headers["x-ratelimit-remaining"] = str(RATE_LIMIT - count - 1)
    return response
`}</Terminal>

<Callout type="note" title="429 是後來才有的碼">
  `401`、`403`、`404` 都在 HTTP/1.1 裡（RFC 9110）。`429 Too Many Requests` 是後來用 RFC 6585 補上去的。

  它**不是** `503 Service Unavailable`。`503` 是「我現在壞掉了，等一下再試」，`429` 是「我好好的，是你太急」。Client 的重試策略完全不同，所以不能混用。
</Callout>

`Retry-After` 這個 Header 是重點：它告訴 Client **具體要等幾秒**，而不是讓它自己猜。沒有它，Client 通常會馬上重試，你剛擋下的流量又回來了。

### 08.2 跑起來看

<Callout type="note" title="為什麼是 30 不是 5">

  想提早看到拒絕，就把 `main.py` 裡那個數字改小。**限流值是政策，不是常數。**
</Callout>

打到第 31 次：

$ for i in $(seq 1 31); do curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8005/open; done | sort | uniq -c

`retry-after` 的數字會隨著你是在視窗的哪一段送出而變。**這不是 bug**——它就是「距離這個視窗結束還有幾秒」。

現在打一個**這支 API 根本沒有的路徑**：

<Terminal title="bash — the limiter runs before routing" flavor="output">{`
$ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8005/nope

<Callout type="important" title="`/nope` 沒有路由，但它拿到的是 429 不是 404">
  這是第 01 節的直接後果。中介軟體在路由比對**之前**執行，所以這次請求在還沒有人查「這個路徑存不存在」之前，就被限流擋下來了。

  順帶回答一個你現在應該會好奇的問題——同一段時間內打一個需要登入的路由：

  <Terminal title="bash — which check wins" flavor="output">{`
  $ curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8005/profile
  429

  **是 429，不是 401。**因為 `rate_limit` 是最後註冊的，也就是最外層，它比認證先跑。

  這是取捨，不是錯誤：如果你不想讓「沒登入的人」拿到 `429`（那會洩漏你每分鐘的上限），就要把限流註冊在認證**裡面**。**限流器的位置本身就是一個安全決策。**
</Callout>

### 08.3 這個寫法有個破口，而且就在視窗邊界

上面那個 `rate_limit` 擋的是每一個打到這支 API 的請求，而它是最多人寫的那一種：固定視窗計數器。它的問題不在效能，在**它答應的東西比它做到的多**。

`rate_limit.py` 把三種算法並排跑給你看。

<Terminal title="bash — fixed window at the boundary" flavor="output">{`
$ python rate_limit.py fixed
2. Fixed window: 5 per 60s
  all inside one window, 1s apart
    sent 7, allowed 5
    first refusal: {'retry_after': 56}
   now the same client, 5 requests at the end of one window...
  5 at t=56..59, then 5 at t=60..63
    sent 10, allowed 10
   10 requests in 9 seconds, limit is 5.
   The counter went back to zero at t=60, so the second batch never felt it.
`}</Terminal>

**三種算法裡的第一種，限制是每分鐘 5 個——這個 Client 在 9 秒內送了 10 個，全部通過。**

<Callout type="warning" title="破口的名字叫 double rate burst">
  計數器在視窗起點歸零。攻擊者在 `t=59.9` 送 5 個，等兩秒到 `t=60` 計數器歸零，再送 5 個。

  **他在任何連續 60 秒內都沒有超過 10 個，而你的規則寫的是 5。**攻擊成本直接翻倍，而且他不需要任何技巧，只要掐時間。

  修法就是把「到點歸零」換成「往回看過去 60 秒」。
</Callout>

<Terminal title="bash — sliding window log, same 10 requests" flavor="output">{`
$ python rate_limit.py sliding
3. Sliding window log, same 10 requests
  5 at t=56..59, then 5 at t=60..63
    sent 10, allowed 5
    first refusal: {'retry_after': 57}
   timestamps kept for one key: 5
   memory grows with what you allow, which is the price of exactness
`}</Terminal>

同樣 10 個請求，只准 5 個。差別在於：**它記住每一個請求發生的時間點，而不是記住「這一格有幾個」。**過期的丟掉，永遠只看「過去 60 秒有幾個」。

<Callout type="important" title="滑動視窗的代價是記憶體，而且要記每一筆">
  上面那個 `log` 裡存的是 5 個時間戳。上限調到 10 000，它就存 10 000 個。

  而且一個 Client 的紀錄會一直留在 dict 裡，除非你另外安排把它清掉——**否則記憶體會被這些從來不再回來的 Client 慢慢吃光。**
</Callout>

### 08.4 還有第三種：token bucket

滑動視窗是精確的，但真實 API 通常不想要「精確」。你往往想要的是：**短時間的爆量可以通過，長時間的高頻不行。**

<Terminal title="bash — burst allowed, sustained rate not" flavor="output">{`
$ python rate_limit.py bucket
4. Token bucket: burst of 3, refilling 1 per second
  4 at t=0, then 1 per second
    sent 8, allowed 7
    first refusal: {'retry_after': 2}
   3 got through at t=0, the 4th was refused, then 1 per second
   this is the shape you want for an API: short bursts pass, sustained load does not
`}</Terminal>

這種做法是公開 API 實務上最常見的：桶裡預先放 3 枚代幣，每秒補 1 枚。要通行就先花 1 枚，沒錢就等下一枚補滿。

<Callout type="note" title="三種算法怎麼選">
  - **固定視窗**：最省事、最容易寫。**會被 double rate burst 放大成兩倍**，不要用在牽涉金錢或權限的路由上。
  - **滑動視窗**：精確，數字能當合約講。要管記憶體。
  - **Token bucket**：允許爆量，之後回到穩定速率。**大部分公開 API 應該用這個。**

  三個都是正確的選擇，錯的是不知道自己選了哪一個。
</Callout>

### 08.5 依照誰來算，是政策不是技術

第 08.1 節那個限流器用 `request.client.host` 當 key，也就是來源 IP。這個選擇你必須想清楚，因為它決定了誰會被誤擋在這支 API 外面。

<Callout type="important" title="用 IP 當 key 的後果">
  - 同一間公司、同一個 NAT 後面的一整棟樓共用一個 IP。**一個人寫壞的迴圈，會讓整棟樓被擋。**
  - 反過來，攻擊者換一個 IP 就重置了計數器——**用 IP 擋不住真正的攻擊者。**

  常見的折衷是：**未登入的請求用 IP 當 key，登入後改用帳號當 key。**已驗證的 Client 比較好辨識，攻擊者要換帳號的成本比換 IP 高。
</Callout>

<Callout type="warning" title="限流器裡的 dict 是一份沒有上限的記憶體">
  `_hits` 這行會為**每一個來過的 IP** 留一筆，從來不刪。

  攻擊者不需要真的把你的 API 打慢——他只要讓幾百萬個不同 IP 各來一次，你的記憶體就被吃掉了，而當下幾乎沒有真實流量。

  **任何「依照來源分組」的結構，都要問自己：這個 key 的數量有上限嗎？**沒有的話，那是另一種形式的阻斷服務。
</Callout>

### 08.6 CSRF：這個漏洞，你的專題目前沒有

限流擋的是「同一個來源叫太多次」。CSRF 是反過來的方向：**攻擊者不在你的 Server 上，也沒有你的 token，他只是讓你的瀏覽器替他送出請求。**

先講結論，這件事會改變你看待單元 11 和 12 所有工作的方式——尤其那種把 Bearer 換成 Cookie session 的改法。

<Callout type="important" title="單元 11 和 12 的 `Authorization: Bearer` 方案，結構上就沒有 CSRF">
  `bearer` 那一組就是本課一直在用的做法：

  <Terminal title="bash — the scheme already in units 11 and 12" flavor="output">{`
  $ python csrf_server.py bearer 8008 &

  $ curl -s -X POST http://127.0.0.1:8008/transfer -d "amount=10000"
  {"detail":"Authorization header required"} [401]

  $ curl -s -X POST http://127.0.0.1:8008/transfer -H "Authorization: Bearer abc"
  {"ok":true} [200]

  $ curl -s -i -X POST http://127.0.0.1:8008/login -d "name=iris&password=lesson" | grep -c set-cookie
  0
  `}</Terminal>

  三件事同時成立：

  1. 認證憑證放在 **Header**，不是 Cookie。
  2. **瀏覽器不會自動幫你填 Header。**只有同一個 origin 的 JavaScript 可以設它，而攻擊者的頁面不是同一個 origin。
  3. `login` 回應裡**沒有 `Set-Cookie`**，因為 token 根本不存進瀏覽器。

  攻擊者能控制的只有「你的瀏覽器自動附上的東西」。這三點讓那個集合是空的。

  <Callout type="warning" title="但這是結構上的幸運，不是有人想過">
    這個設計擋住 CSRF，是因為 token 放在 Header 裡。**它沒有做任何 CSRF 防護**——沒有 token 比對、沒有 Origin 檢查。

    所以第 06 節的結論要說完整：JWT 是無狀態的，但「無狀態」不等於「自動安全」。這個安全性來自你選的傳輸方式，不是來自 JWT。
  </Callout>
</Callout>

### 08.7 把 Cookie 放回去，漏洞就回來了

真實系統幾乎都用 Cookie 存 session：它記得住、跨頁自動帶、而且 `HttpOnly` 可以擋掉 `document.cookie`。**換成 Cookie session 取代 Bearer 的那一刻，CSRF 就出現了。**

<Callout type="important" title="CSRF 的真正成因，是一句話">
  **Cookie 是瀏覽器在「不管你從哪裡來」的情況下自動附上的。**

  這是它的本分工作：使用者按了「登入」，網站記住他。問題是這個「他」只代表 session，**不包含他此刻正在看哪個網頁。**
</Callout>

`victim`、`guarded` 和 `attacker` 是同一個檔案裡的三組 Server，差別只有防護有沒有做。攻擊者頁面在第三個 origin。

`csrf_server.py` 的開頭就說明了要開幾個 Server：

<Terminal title="bash — three origins, because an attack needs more than one">{`
$ python csrf_server.py victim 8006 &
$ python csrf_server.py attacker 8007 &
$ python csrf_server.py guarded 8010 &
`}</Terminal>

登入之後，去 `http://127.0.0.1:8007/`。那個頁面上只有一個按鈕：

<Terminal title="bash — what the attacker page contains" flavor="output">{`
$ curl -s http://127.0.0.1:8007/ | grep -o 'action="[^"]*"'
action="http://127.0.0.1:8006/transfer"
`}</Terminal>

按下去之後看 `victim` 的終端機：

<Terminal title="victim terminal — the part that matters" flavor="output">{`
[server] TRANSFER 10000 from iris
`}</Terminal>

<Callout type="warning" title="伺服器上發生的事，和攻擊者完全無關">
  攻擊者的頁面**沒有**你的 token、**沒有**你的密碼、**沒有**任何你給過他的東西。

  你的瀏覽器讀到攻擊者的 `<form>`，把它送到 `8006`，同時因為這是 `127.0.0.1` 而**自動附上了 `session` Cookie**。`8006` 看到一張有效的 session cookie，執行了轉帳。

  整個過程裡，使用者看到的是「我點了一個按鈕」。**沒有任何畫面顯示錢掉了。**
</Callout>

現在打同一個請求，但繞過瀏覽器：

<Terminal title="bash — the same request, made explicit" flavor="output">{`
$ curl -s -X POST http://127.0.0.1:8006/transfer \\
    -H "Cookie: session=iris" -d "amount=10000"
ok, moved 10000 from iris
`}</Terminal>

這行指令沒有用到任何機密。`Cookie: session=iris` 是攻擊者的頁面**也會**帶上的東西，而它就是全部的憑證。

所以重點不是「攻擊者很會偽造 cookie」，而是**他根本不需要偽造**。

### 08.8 三道防線，而且它們擋的不是同一件事

這就是漏洞的形狀：憑證由瀏覽器自動附上，而 Server 沒有任何東西能分辨「本人來的」還是「別的頁面叫來的」。

要堵它，`guarded` 那組一次做了三件事，我們逐個拆開看。三道防線擋的東西不一樣，這點比記住設定值更重要。

<Terminal title="bash — the cookie it actually sets" flavor="output">{`
$ curl -s -i -X POST http://127.0.0.1:8010/login -d "name=iris&password=lesson" \\
    | grep -i set-cookie
set-cookie: session=iris; HttpOnly; Path=/; SameSite=lax
set-cookie: csrf=lesson-12-csrf-token; Path=/; SameSite=lax
`}</Terminal>

<Terminal title="bash — legitimate request, all three satisfied" flavor="output">{`
$ curl -s -X POST http://127.0.0.1:8010/transfer \\
    -H "Cookie: session=iris" \\
    -H "Origin: http://127.0.0.1:8010" \\
    -d "amount=100&csrf=lesson-12-csrf-token"
ok, moved 100 from iris
`}</Terminal>

<Terminal title="victim of the attack, pointing at the defended server" flavor="output">{`
$ curl -s -X POST http://127.0.0.1:8010/transfer \\
    -H "Cookie: session=iris" \\
    -H "Origin: http://127.0.0.1:8007" \\
    -d "amount=10000&csrf=" -w " [%{http_code}]"
bad origin [403]

$ curl -s -X POST http://127.0.0.1:8010/transfer \\
    -H "Cookie: session=iris" \\
    -H "Origin:" \\
    -d "amount=10000&csrf=" -w " [%{http_code}]"
bad csrf token [403]
`}</Terminal>

<Callout type="important" title="三道防線各擋什麼">
  - **`SameSite=Lax`**：瀏覽器層的規則。跨站的 POST 不附 cookie，所以 `8006` 那條路根本走不到 `session`。**這是最強的一道，因為它讓憑證不出發。**
  - **CSRF token**：攻擊者讀不到的那個值。`csrf` Cookie 設在 `8010`，攻擊者的頁面在 `8007`，同源政策擋住讀取，所以表單只能送出空字串。
  - **`Origin` 檢查**：瀏覽器送的 `Origin` 無法被頁面內容覆寫，跨站 POST 會誠實地寫上攻擊者的 origin（`8007`）。

  **三道都要有。**任何單獨一道被廢掉的時候——`SameSite` 的預設值改掉、token 在 XSS 裡外洩、某個舊客戶端不送 `Origin`——另外兩道還在。
</Callout>

<Callout type="warning" title="Origin 檢查有個洞，而且程式碼裡看得到">
  守衛的寫法是：

  ```python
  if origin and origin != ALLOWED_ORIGIN:
  ```

  注意開頭的 `origin and`。**沒有 `Origin` 的請求會被放行**，因為不是每個客戶端都會送它（`curl` 預設就不送）。

  照上面那段測試繼續往下打，可以量到這件事的真實代價：

  <Terminal title="bash — no Origin header, and the token is known" flavor="output">{`
  $ curl -s -X POST http://127.0.0.1:8010/transfer \\
      -H "Cookie: session=iris" \\
      -H "Origin:" \\
      -d "amount=10000&csrf=lesson-12-csrf-token" -w " [%{http_code}]"
  ok, moved 10000 from iris [200]
  `}</Terminal>

  **通了。**因為這個請求沒有帶 `Origin`，檢查直接跳過，而 token 又剛好是對的。

  這不是漏洞，是這兩道防線的邊界。攻擊者能不能走到這一步，取決於他能不能同時拿到 token 並且讓瀏覽器不送 `Origin`——真實瀏覽器在跨站情境會送，所以純網頁攻擊走不到。

  **但它說明了一件事：不要把「擋住大部分攻擊」當成「安全」。**你能說出它在哪裡失效，才算真的懂這三道防線。
</Callout>

### 08.9 判斷題：你的專題要不要處理 CSRF

<Callout type="important" title="一條規則，不是感覺">
  **你的認證憑證會不會被瀏覽器「自動附上」？**

  - 會（存在 Cookie 裡）→ **需要** CSRF 防護。
  - 不會（放 Header、由呼叫端自己帶）→ 這個攻擊不成立。

  然後記住第二件事：**改了傳輸方式，防護要跟著改。**從 Bearer 換到 Cookie session 的那一天，就是漏洞回來的那一天，而 git 不會提醒你。
</Callout>

<Callout type="note" title="SameSite 預設值這件事">
  現代瀏覽器已經把 `SameSite=Lax` 設為預設，所以很多系統「看起來沒事」——那是瀏覽器在替你擋。

  但 `Lax` **不擋跨站 POST**，只擋跨站 GET。也就是說「讀取資料」的路由安全，**「改資料」的路由並沒有**。

  要完全靠 cookie 本身擋住 POST，需要 `SameSite=Strict`，代價是所有從外部連結進來的第一次導覽都會沒有 cookie。**多數實務上是 `Lax` 加上 CSRF token，而不是只靠 `SameSite`。**
</Callout>

## 09. 終端實戰驗證

第 08 節的限流與 CSRF 都做完了，下面回到 `main.py`。Terminal 1 跑著 `SIGNING_KEY=lesson-12-key-a fastapi dev main.py --port 8005`，Terminal 2 已經把 `$STUDENT` 和 `$ADMIN` 放出來了。這支 API 的下面十步照順序做，每一步都先看指令再看截圖要求。**第 9 步會重啟 Terminal 1，重啟之後就不要再打其他請求**，否則第 10 步拿到的不是 `429`。

1. 先打一個這支 API 沒有定義的路徑：`curl -i http://127.0.0.1:8005/nope`。截圖必須同時包含 `404`、`x-request-id` 與 `x-trace`，因為中介軟體有沒有執行，證據就在那兩個 Header 上。
2. 接著看巢狀順序：`curl -i http://127.0.0.1:8005/open | rg -i '^x-trace'`。把 `outer:in > inner:in > inner:out > outer:out` 整串抄下來，這是第 02 節的證據。
3. 現在把 `main.py` 裡 `trace_inner` 與 `trace_outer` 兩個 block 上下互換，等重新載入後再打一次 `curl -i http://127.0.0.1:8005/open`。Terminal 1 會出現 `AttributeError: 'State' object has no attribute 'trace'`，curl 會拿到 `500`。**截圖必須兩邊都有**，因為它要證明的是「路由正常但中介軟體壞掉」。做完記得還原。
4. 解出 `$ADMIN` 的 payload，用第 04 節那個 `python3` 指令，截圖必須包含 `'role': 'intern'`。接著用這枚 token 打 `curl -i http://127.0.0.1:8005/admin -H "Authorization: Bearer $ADMIN"`，截圖必須包含 `200`。
5. 對照第 4 步，同一條路徑換成 `curl -i http://127.0.0.1:8005/admin -H "Authorization: Bearer $STUDENT"`，截圖必須包含 `403`。兩張截圖並排，唯一的差別就是 `$ADMIN` 與 `$STUDENT`。
6. 然後送出未宣告的欄位：`curl -i -X POST http://127.0.0.1:8005/profile -H 'Content-Type: application/json' -H "Authorization: Bearer $STUDENT" -d '{"nickname":"iris","is_admin":true}'`。截圖必須包含 `422`、`extra_forbidden` 與 `["body","is_admin"]`。
7. 接著把 `SIGNING_KEY` 拿掉，執行 `python -c "import main"`。截圖必須包含 `RuntimeError` 與那句完整訊息，因為重點是它拒絕啟動而不是用預設值。
8. 最後開 Terminal 3 用 `SIGNING_KEY=lesson-12-key-b` 起 8006，然後跑 `curl -s http://127.0.0.1:8005/key-info` 和 `curl -s http://127.0.0.1:8006/key-info` 比較指紋，再用 `curl -i http://127.0.0.1:8006/profile -H "Authorization: Bearer $STUDENT"` 確認回 `401 Bad signature`。
9. **重啟 Terminal 1 的 Server**，然後跑 `for i in $(seq 1 31); do curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8005/open; done | sort | uniq -c`。截圖必須包含 `30 200` 與 `1 429`。接著 `curl -i http://127.0.0.1:8005/open`，截圖必須包含 `429` 與 `retry-after`。**重啟是必要的**：計數器存在記憶體裡，重啟才會歸零。
10. 不重啟，直接打 `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8005/nope` 和 `curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8005/profile`。兩張截圖必須**都是 `429`**，然後回答：為什麼 `/profile` 沒有因為你沒帶 token 而回 `401`？
11. 開三個新的 Terminal：`python csrf_server.py victim 8006`、`python csrf_server.py attacker 8007`、`python csrf_server.py guarded 8010`。**瀏覽器**打開 `http://127.0.0.1:8006/` 登入（`iris` / `lesson`），然後開新的分頁打 `http://127.0.0.1:8007/` 按那個按鈕。截圖必須包含 `victim` 終端機的 `TRANSFER 10000 from iris`，以及瀏覽器上「你已經是 iris」的那個畫面。**這兩張截圖要放在一起，因為重點是它們同時成立。**
12. 對照組：`python csrf_server.py bearer 8008`，執行 `curl -s -X POST http://127.0.0.1:8008/transfer -d "amount=10000"`，截圖必須包含 `401`。再執行 `curl -s -i -X POST http://127.0.0.1:8008/login -d "name=iris&password=lesson" | grep -c set-cookie`，截圖必須包含 `0`。**回答：同一個 `transfer` 路由，為什麼一支有 CSRF 風險、一支沒有？差別只有哪一個地方？**
13. 對 `guarded` 做三次請求，三張截圖都要有：`curl -s -X POST http://127.0.0.1:8010/transfer -H "Cookie: session=iris" -H "Origin: http://127.0.0.1:8010" -d "amount=100&csrf=lesson-12-csrf-token"`（成功）、加上 `-H "Origin: http://127.0.0.1:8007"`（`bad origin [403]`）、再把 `Origin:` 留空且 `csrf=` 留空（`bad csrf token [403]`）。**回答：`SameSite=Lax`、CSRF token、`Origin` 檢查，各自擋住了什麼？**
14. 最後送出 `-H "Origin:"` 且 `-d "amount=10000&csrf=lesson-12-csrf-token"`，截圖必須包含 `200`。**回答：這次成功了。這代表 `Origin` 檢查有什麼限制？為什麼這不代表真實瀏覽器上的攻擊可以成功？**

## 單元實作作業

在本地環境完成以下十四項操作，每一項的截圖與簡答都記錄下來。

1. 先打一個不存在的路徑，截圖必須同時包含 `404`、`x-request-id` 與 `x-trace`。用一句話回答：中介軟體有沒有真的執行？
2. 把兩個中介軟體的 block 對調，截圖必須同時包含 Terminal 1 的 `AttributeError` 與 curl 的 `500`。用一句話回答：為什麼對調之後是外面那個壞掉？
3. 登入管理員，解出 payload，截圖必須包含 `'role': 'intern'`。然後用這枚 token 打 `/admin`，截圖必須包含 `200`。回答：這枚 token 的 role 欄位被誰忽略了？
4. 接著用學生的 token 打 `/admin`，截圖必須包含 `403`。**和第 3 步並排，寫出這兩次的差異只有哪一個欄位。**
5. 然後 `POST /profile` 送 `{"nickname":"...","is_admin":true}`，截圖必須包含 `422`、`extra_forbidden` 與 `["body","is_admin"]`。回答：`extra="forbid"` 和單元 10 的預設行為差在哪？
6. 接著把 `SIGNING_KEY` 拿掉再執行 `python -c "import main"`，截圖必須包含 `RuntimeError` 與那句完整訊息。回答：為什麼這支程式選擇拒絕啟動，而不是印警告然後用預設值？
7. 然後開第二個 Terminal 用不同金鑰起 8006，截圖必須包含兩個 `/key-info` 的**不同指紋**，以及 `8006` 回 `401 Bad signature`。回答：換金鑰讓誰失效？
8. 最後用一句話回答：`exp` 兩小時的情況下，使用者被開除一個小時，他的 token 還能用多久？用這一堂課的兩個機制回答，不要只用其中一個。
9. 重啟 Server 後跑 `for i in $(seq 1 31); do curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8005/open; done | sort | uniq -c`，截圖必須包含 `30 200` 與 `1 429`。再 `curl -i http://127.0.0.1:8005/open`，截圖必須包含 `retry-after`。回答：為什麼這個數字每次跑都不一樣？
10. 接著跑 `python rate_limit.py fixed` 與 `python rate_limit.py sliding`，兩張截圖都要包含 `5 at t=56..59, then 5 at t=60..63`。**回答：同樣 10 個請求，為什麼固定視窗放行 10 個、滑動視窗只放行 5 個？`main.py` 現在用的是哪一種？**
11. 用 `grep -n "_hits" main.py` 找到那個 dict。回答：`_hits` 的 key 是什麼？這個 key 的數量有上限嗎？如果沒有，是什麼問題？
12. 最後回答：你在 Terminal 2 打 `/profile` 忘了帶 token，但因為剛剛超流而拿到 `429`。**你要怎麼分辨「我被限流了」跟「我忘記帶 token 了」？**這兩個狀況 Server 給的 Header 有什麼不同？
13. 照第 11 到 14 步在瀏覽器裡跑一次完整的 CSRF 實驗，截圖必須包含 `victim` 的 `TRANSFER 10000 from iris`、`bearer` 的 `401`、以及 `guarded` 的兩次 `403`。回答：`victim` 和 `guarded` 的差別只有防護，而 `bearer` 連 cookie 都沒有——**三組分別對應到哪一種「憑證會不會被瀏覽器自動附上」？**
14. 用一句話回答：假設你的期末專題現在把登入方式從 Bearer 改成 Cookie session，**你要多寫哪幾行**？那些行的作用分別是什麼？如果改成 Cookie 卻什麼都不加，**哪一個請求會成功、金額會是多少？**

把作業截圖與簡答筆記存入 `exercises/12-middleware/`，並以 Git 提交至個人儲存庫。提交前執行 `git status`，確認只包含作業檔案。這一課的作業重點不在截圖數量，而在第 3、4、8 三題的答案是否真的對照到指令輸出。

**不要**把你自己的 `SIGNING_KEY` 寫進 `main.py`、`.env` 或任何會被提交的檔案。真實的簽發金鑰由部署環境提供。
