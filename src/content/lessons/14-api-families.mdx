前三個單元你一直在讀 REST 的契約。這一課換一個角度：**同一個「拿到三筆筆記」的需求，五個家族會各自把它寫成什麼樣子，然後用什麼方式拒絕你。**

先啟動一支同時提供 REST 與 GraphQL 的 API：

<Terminal title="Terminal 1 — bash — start the API">{`
cd exercises/14-api-families
fastapi dev main.py --port 8007
`}</Terminal>

這支 API 有三筆資料：`welcome`、`api`，和一支 `name` 是 `title` 的空殼。

## 01. 先問一個錯的問題

REST 讀資料的方式是：拿一條路徑，決定要什麼。`GET /notes` 沒有任何參數可以表達「我只要 name 和 title」。

所以 Client 只能全部拿走，然後自己丟掉用不到的：

<Terminal title="Terminal 2 — bash — REST over-fetch" flavor="output">{`
> curl -s http://127.0.0.1:8007/notes
{"items":[{"name":"welcome","title":"Welcome","tags":["intro","start"]},{"name":"api","title":"API design","tags":["rest"]}]}
`}</Terminal>

`tags` 在這個畫面上完全沒有用途。**REST 的回應形狀由 Server 決定，不由 Client 決定。**這個現象叫 over-fetching，它不是 bug，是 REST 這個設計的直接後果。

現在走 GraphQL 那一條路，同一個 API、同一份資料：

<Terminal title="bash — the same need, asked for by name" flavor="output">{`
> curl -s -X POST http://127.0.0.1:8007/graphql \\
>   -H 'Content-Type: application/json' \\
>   -d '{"query":"{ notes { name title } }"}'
{"data":{"notes":[{"name":"welcome","title":"Welcome"},{"name":"api","title":"API design"}]}}
`}</Terminal>

`tags` 不見了。**GraphQL 的回應形狀由查詢字串決定**，所以 over-fetching 在這個家族裡不是被減少，而是根本不發生。

<Callout type="important" title="這是這一堂課的主詞">
  同一份資料、同一個需求，兩個家族給了不同大小的回應。差別不在效能，在**契約放在哪裡**：

  REST 把契約放在**文件**裡（`GET /notes` 永遠回三個欄位），Client 讀文件才知道要丟掉什麼。
  GraphQL 把契約放在**型別系統**裡（`notes` 的回應型別由你選的欄位決定），Client 用錯欄位編譯期就發現。
</Callout>

<Callout type="note" title="GraphQL 換來了另一個問題">
  over-fetching 消失的代價是 under-fetching：Client 想要 `name`、`title` 和「這個月有幾筆」三樣東西，就必須問三次，除非後端有 `notesWithStats` 這種聚合欄位可以一起選。

  實務上兩者都存在，所以 REST 的路徑設計和 GraphQL 的 resolver 設計，長期下來複雜度是同一個級別。**GraphQL 不是把 REST 的問題解決掉，是把問題換到另一個位置。**
</Callout>

## 02. 同一個錯誤，五種答案

現在送一個**明確錯誤**的請求給 GraphQL：查一個不存在的欄位。

<Terminal title="bash — asking for a field that does not exist" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8007/graphql \\
>   -H 'Content-Type: application/json' \\
>   -d '{"query":"{ notes { name nickname } }"}'
< HTTP/1.1 200 OK

{"data":null,"errors":[{"message":"Cannot query field 'nickname' on type 'Note'. Did you mean 'name'?","path":null}]}
`}</Terminal>

三件事值得停下來：

1. **訊息指名了欄位**，還給了建議：`nickname` 不存在，`Did you mean 'name'?`
2. **`data` 是 `null`**，不是部分結果。
3. **狀態碼是 `200`，不是 `4xx`。**

第三點最容易踩到。單元 07 講過 `4xx` 代表「這一次請求的問題」，而這裡確實是請求的問題，卻回 `200`。

<Callout type="warning" title="這個 200 是這支 Server 的選擇，不是規格的建議">
  查不到欄位是**驗證失敗**，GraphQL over HTTP 草案對這一類錯誤寫得很明確：「If the request does not pass GraphQL validation, status code `422` **SHOULD** be used.」

  同一份草案也說：「If the GraphQL result does not contain the `data` entry then it represents a GraphQL request error result and the server **MUST** reply with an appropriate `4xx` or `5xx` status code.」這裡的 `data` 正好是 `null`。

  所以**照規格，這一個請求應該是 `422`**，而這支練習 API 回 `200` 是它的作者選的。它之所以能這樣，是因為 `graphql_sync()` 回傳的結果已經把查詢擋掉了，route 只是把結果原樣包成 JSON。

  那麼「GraphQL 都回 200」這個說法從哪來？它來自**另一種錯誤**：查詢本身合法、執行到一半才錯，此時 `data` 有值而且不是 `null`，只有部分欄位失敗。那一種情況才真的沒有狀態碼可用——規格因此建議一個專門的 `294`，理由寫在草案的「Partial success」一節。

  **「三個欄位成功、一個欄位失敗沒有狀態碼可用」是對的，但那只適用於第二種錯誤，不適用於你剛剛送出的這個。**單元 10 講過 `422` 沒有跨實作一致性，這裡是同一個問題換了個家族。

  實務結論不變，而且更重要：**串接別人的 GraphQL API 時，不要只看狀態碼**，一律檢查 Body 裡有沒有 `errors`。`curl -f` 在這裡是沒用的。
</Callout>

現在做同一件事給 REST。送一個**多餘的欄位**：

<Terminal title="bash — the same mistake, REST's way" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8007/notes \\
>   -H 'Content-Type: application/json' \\
>   -d '{"name":"t1","title":"T","is_admin":true,"colour":"red"}'
< HTTP/1.1 200 OK

{"name":"t1","title":"T","tags":[]}
`}</Terminal>

**沒有錯誤。`is_admin` 和 `colour` 被安靜地丟掉了，狀態碼是 `200`。**

<Callout type="important" title="這一對就是整個單元">
  兩個家族收到同一種程度的錯誤輸入，答案完全不同：

  | | REST | GraphQL |
  | --- | --- | --- |
  | 多要一個不存在的欄位 | 丟掉，`200` | 指名，`200` + `errors` |
  | 少給一個必要欄位 | `422`（單元 07） | `errors`，`data: null` |
  | 誰能提前發現 | 無 | Client 端型別檢查 |

  **REST 對「多」的錯誤完全沉默，GraphQL 對「少」的錯誤也沉默。**沒有哪一個家族比較嚴謹，它們只是選擇了不同的沉默方式。

  這也是為什麼單元 10 要教 `extra="forbid"`：REST 的沉默是可以自己關掉的，預設不關。
</Callout>

## 03. 找不到資源：404 對 null

單元 04 講過 `404` 有一個容易誤用的狀況：「路徑拼錯」和「東西不存在」回同一個狀態碼。GraphQL 對這件事的答案不同。

<Terminal title="bash — REST: two different 404s" flavor="output">{`
> curl -i http://127.0.0.1:8007/notes/ghost | rg -i '^HTTP|detail'
< HTTP/1.1 404 Not Found
{"detail":"Note not found"}

> curl -i http://127.0.0.1:8007/nothing-here | rg -i '^HTTP|detail'
< HTTP/1.1 404 Not Found
{"detail":"Not Found"}
`}</Terminal>

同樣是 `404`，Body 不同。單元 07 講過 `detail` 是 FastAPI 的慣例，不同框架的 `404` Body 寫法不一樣，所以 Client 不該靠字串判斷。

同一個「找不到」的問題，GraphQL 的答案不是狀態碼：

<Terminal title="bash — GraphQL: a missing record is a value" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8007/graphql \\
>   -H 'Content-Type: application/json' \\
>   -d '{"query":"{ note(name: \"ghost\") { name } }"}'
< HTTP/1.1 200 OK

{"data":{"note":null}}
`}</Terminal>

`null`，沒有 `errors`。**「這筆不存在」在 GraphQL 裡是一個正常的值，不是錯誤。**

<Callout type="note" title="這是 schema 的選擇，而且是有意的">
  這支 API 的 schema 寫的是 `note(name: String!): Note`——回傳型別是 `Note` 而不是 `Note!`。`Note` 可以是 `null`，`Note!` 不行。

  所以 `{"note":null}` 完全符合 schema。如果改成 `Note!`，GraphQL 就會強制回 `errors` 並把整個 `data` 變成 `null`，連其他成功的欄位一起拖下水。

  **換一個 `!`，失誤的爆炸半徑就從一個欄位變成整個查詢。**這是讀別人的 GraphQL schema 時最該先看的一件事。
</Callout>

## 04. SOAP：契約在檔案裡

同一件事在 SOAP 那邊又不一樣了。SOAP 在單元 06 出現過一次，那時的重點是「把動作放進 Body」的取捨，而它真正特別的地方是**契約的產生地點**。

SOAP 1.1 讓伺服器端先產出一份 WSDL（Web Services Description Language），裡面有每個 operation 的名稱、參數型別和回傳型別，然後**各家語言的 client stub 是從那份檔案自動產生的**，不是手寫的。

| | 契約的載體 | Client 怎麼知道型別 |
| --- | --- | --- |
| REST | 文件（人寫的） | 沒有機制，靠人讀 |
| GraphQL | schema（Server 端宣告） | 執行期驗證 + 工具產生的型別 |
| SOAP | WSDL（Server 端產出） | **建置期**從檔案產生 stub |
| gRPC | `.proto` | **建置期**從檔案產生 stub |
| tRPC | TypeScript 型別 | **型別檢查期**推導 |

<Callout type="important" title="SOAP 的真實優勢是「型別錯誤在建置期就爆」">
  WSDL 一旦產出，Client stub 裡的每個型別都是真的編譯期型別。Client 寫 `getNote(bob).titel`（拼錯）會在編譯期紅，不會等到上線。

  REST 完全沒有這個機制——`{"titel": "..."}` 送到 Server，Server 若沒宣告就丟掉（單元 10），你會到 production 才知道。

  代價是 XML 肥大、瀏覽器不會用、很多防火牆擋掉。同一個「建立一個使用者」，`{"name":"bob"}` 是 14 個位元組，那個 SOAP envelope 是 267 個，約 19 倍。

  它現在活在金融、醫療與政府的系統整合裡。**你會在文件、log 與工程師對話中遇到它，而且會需要讀 WSDL。**
</Callout>

這一課不要求你寫 SOAP。要求的是：看到 `<soapenv:Envelope>` 知道那是本家族的封裝，看到 `Fault` 知道那是本家族的錯誤。

## 05. gRPC 與 tRPC：契約檔，不是端點

這兩個家族的東西放在 `exercises/14-api-families/` 裡，但不是可以跑起來的服務：

- `notes.proto` — gRPC 的契約
- `trpc-contract.ts` — tRPC 的契約

**它們不在這一堂課執行，因為它們的價值在「讀」，不在「跑」。**而且它們都不走 JSON。gRPC 走 Protocol Buffers 的二進位編碼，跑在 HTTP/2 上；tRPC 走 JSON，線上格式跟 REST 一樣；限制在**型別**——Client 的型別由 Server 的 router 推導出來，所以要用就得兩端在同一個 TypeScript 專案裡。

`notes.proto` 的關鍵在這裡：

<Terminal title="exercises/14-api-families/notes.proto" flavor="output">{`
message Note {
  string name = 1;
  string title = 2;
  repeated string tags = 3;
}

service NoteService {
  rpc ListNotes(ListNotesRequest) returns (ListNotesResponse);
  rpc GetNote(GetNoteRequest) returns (Note);
}
`}</Terminal>

`rpc ListNotes(ListNotesRequest) returns (ListNotesResponse)` 這一行同時說明了：方法名、輸入型別、輸出型別。**Client stub 是從這裡生成的**，所以 Client 呼叫 `getNote()` 少傳一個參數，編譯期就紅。

<Callout type="note" title="和 SOAP 的差別：誰產生 spec">
  SOAP 是**伺服器端**先產出 WSDL，你再去生成 stub。gRPC 是把 `.proto` 當成**原始碼**，Client 與 Server 各自從它生成自己的 stub，兩邊都不手寫。

  這是「contract-first」和「code-first」的差別。你在 `trpc-contract.ts` 裡看到的正是 code-first：契約寫在 Server 的 router 裡，Client 的型別由 TypeScript **推導**出來，所以不需要產生器，代價是跨語言時拿不到那份型別——其他語言仍然可以呼叫這支 API，只是變成未型別的 HTTP/JSON Client。

  **SOAP/gRPC 是跨語言的必要成本；tRPC 放棄跨語言的「型別」，換掉整個產生步驟。**它沒有禁止別的語言呼叫，只是那邊拿不到型別檢查。
</Callout>

## 06. 五個家族放在一起的樣子

<Terminal title="Terminal 2 — bash — put all five side by side" flavor="output">{`
> curl -s http://127.0.0.1:8007/notes | wc -c
161

> curl -s -X POST http://127.0.0.1:8007/graphql \\
>   -H 'Content-Type: application/json' \\
>   -d '{"query":"{ notes { name title } }"}' | wc -c
119

> curl -s -X POST http://127.0.0.1:8007/graphql \\
>   -H 'Content-Type: application/json' \\
>   -d '{"query":"{ notes { name title tags } }"}' | wc -c
170
`}</Terminal>

這三個數字是同一份資料的三種回應大小：REST 161、GraphQL 只要 name 和 title 給 119、GraphQL 加上 tags 給 170。

<Callout type="important" title="數字很小，所以重點不是大小">
  這裡省下 42 個位元組，毫無意義。真正的差別在**誰決定回應形狀**：

  REST 的回應形狀寫死在 Server 裡，Client 拿到的永遠是全部欄位。
  GraphQL 的回應形狀寫在查詢字串裡，Client 拿到的正好是它寫的。

  當 Client 要的東西比 Server 願意提供的少時（行動 App 只顯示列表、不顯示內文），這個差別會變成幾百 KB。**先看懂契約在哪裡，再選家族。**
</Callout>

把五個家族壓成一張可以帶走的表：

| | REST | SOAP | GraphQL | gRPC | tRPC |
| --- | --- | --- | --- | --- | --- |
| 傳輸格式 | JSON | XML | JSON | Protobuf（二進位） | JSON |
| 契約載體 | 文件 | WSDL | schema | `.proto` | TS 型別 |
| 誰決定回應形狀 | Server | Server | **Client** | Server | Server |
| 錯誤怎麼表示 | 狀態碼 | `Fault` | `errors` 陣列 | gRPC status code | TRPCError |
| 找不到資源 | `404` | `Fault` | `null` | `NOT_FOUND` | TRPCError |
| 跨語言 | 天然 | 需要產生器 | 天然 | 需要產生器 | 線上格式可以，**型別不行** |
| 瀏覽可直接呼叫 | 可以 | 幾乎不行 | 可以 | 不行 | 不行 |

<Callout type="note" title="這一課真正要記的是那一句">
  **沒有哪一個家族比較好。每一個都在某個軸上換取另一個軸。**

  REST 換掉型別安全性，換到跨語言與可讀性。
  SOAP 和 gRPC 換到建置期的型別安全，代價是產生器與二進位。
  GraphQL 換到 Client 控制回應形狀，代價是聚合複雜度與「狀態碼不再代表成功」。
  tRPC 換掉跨語言的型別安全，換掉整個產生步驟。

  你在職場上讀到一份 API 契約時，真正要問的是：**這份契約的作者把什麼換掉了？**因為那個取捨決定了它會在哪裡壞掉。
</Callout>

## 07. 終端實戰驗證

上面那張表是這一課唯一要背的東西。剩下五組指令是它的證據來源，Terminal 1 跑著 `fastapi dev main.py --port 8007`，Terminal 2 照順序跑：

1. 先 `curl -s http://127.0.0.1:8007/notes`，截圖必須包含 `tags`。用一句話回答：這個欄位是誰決定要給的？
2. 接著送 GraphQL 的 `{ notes { name title } }`，截圖必須**沒有** `tags`。回答：回應形狀現在由誰決定？
3. 然後送 `{ notes { name nickname } }`，截圖必須包含 `200 OK`、`"data":null`、`Did you mean 'name'?`。回答：為什麼這裡不是 `422`？
4. 再送 `POST /notes` 帶 `{"name":"t1","title":"T","is_admin":true,"colour":"red"}`，截圖必須包含 `200` 並且 Body **沒有** `is_admin`。和第 3 步並排，寫出這兩次的差異。
5. 最後 `curl -s http://127.0.0.1:8007/notes | wc -c`、`{ notes { name title } } | wc -c`、`{ notes { name title tags } } | wc -c` 三個數字都要截圖。
