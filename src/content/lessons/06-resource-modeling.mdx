## 01. 資源有名稱，動作交給 method

第二單元確認過：`path` 指出要操作的資源路徑，最後怎麼解讀由 Server 的路由決定。REST 的第一個設計選擇，就是讓 `path` 只負責「是哪一筆東西」，不負責「要做什麼」。

這一組 users 資源在路徑上有兩種位置：

| 路徑形態 | 這條路徑代表什麼 | 課堂 API 的實測結果 |
| --- | --- | --- |
| `/users` | 一整組 users（集合） | `POST` 回 `201`，`GET` 回 `405 allow: POST` |
| `/users/bob` | 集合裡的其中一筆（成員） | `GET` 回 `200`，`DELETE` 回 `405 allow: GET` |

`GET /users/bob` 回 `200`，代表 Server 手上真的有 `bob` 這一筆。換一個名字：

<Terminal title="bash — the member does not exist">{`
curl -i http://127.0.0.1:8000/users/ghost
`}</Terminal>

## 02. 動作不要寫進網址

把刪除動作塞進網址，是初學者最常見的寫法之一。它看起來像這樣：

<Terminal title="bash — the shape REST rejects">{`
curl -i 'http://127.0.0.1:8000/users/delete?id=bob'
`}</Terminal>

回來的是：

<Terminal title="bash — action written into the path" flavor="output">{`
< HTTP/1.1 404 Not Found
< content-type: application/json

{"detail":"User not found"}
`}</Terminal>

注意這不是語法錯誤，也不是 Server 拒絕服務。`delete` 在這條路徑裡被當成一個 username——`/users/delete` 就是「名叫 delete 的那一筆 user」，Server 找不到，所以回 `404`。動作被寫成資源名稱之後，它就只能被當成資源名稱處理。

把同一個意圖改寫成 method，Server 才有一個明確的位置可以判斷：

<Terminal title="bash — action expressed as a method">{`
curl -i -X DELETE http://127.0.0.1:8000/users/bob
`}</Terminal>

<Terminal title="bash — the route answers with 405" flavor="output">{`
< HTTP/1.1 405 Method Not Allowed
< allow: GET
< content-type: application/json

{"detail":"Method Not Allowed"}
`}</Terminal>

`405` 的意思是：這條路徑我認得，但沒有 `DELETE` 這個 method。`allow: GET` 告訴你這條路徑現在只接受哪一種 method。

真正危險的地方在 `GET`。瀏覽器預先載入、proxy 快取、爬蟲、email 掃描器與捷徑輪播，都會自動送出 `GET`，而且不會問你。只要刪除可以被 `GET` 觸發，這些自動行為就會變成刪除。

<Callout type="warning" title="把刪除寫成 GET 會發生什麼事">
  搜尋引擎爬蟲抓到 `GET /users/delete?id=bob`，就會照著執行。瀏覽器 prefetch 也一樣。這種 bug 很少在測試時出現，因為測試只會照著你寫的 method 呼叫；出事的是那些不是你呼叫的那一方。
</Callout>

<FieldNote marker="XML" eyebrow="FIELD NOTE 06" title="SOAP：把動作放進 Body 的另一個答案">
  另一個走過來的方向是 SOAP。它的 endpoint 幾乎永遠只有一條，動作與參數全部寫在 Body 裡。送一個「建立使用者」的 SOAP 訊息給任何 HTTP 端點：

  <Terminal title="bash — a SOAP envelope over curl">{`
  curl -i -X POST 'https://httpbin.org/anything/users' \\
    -H 'Content-Type: text/xml; charset=utf-8' \\
    -d '<?xml version="1.0" encoding="utf-8"?>
  <soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/" xmlns:ns="urn:115-backend">
    <soapenv:Body>
      <ns:CreateUser>
        <ns:name>bob</ns:name>
      </ns:CreateUser>
    </soapenv:Body>
  </soapenv:Envelope>'
  `}</Terminal>

  同一個「建立一個使用者」，REST 的 Body 是 `{"name":"bob"}` 共 14 個位元組，這個 SOAP envelope 是 281 個位元組，約 20 倍。回應的 `json` 欄位會是 `null`，因為它確實不是 JSON。

  SOAP 的設計比 REST 早了十年就有 contract-first：介面由 WSDL 定義，再產生各語言的 stub，所以型別錯誤在建置期就被抓到。代價是 XML 肥大、瀏覽器不會用、很多防火牆擋掉。它現在活在金融、醫療與政府的系統整合裡。你會在文件、log 與工程師對話中遇到它；`[SOAP 1.1 規格](https://www.w3.org/TR/2000/NOTE-SOAP-20000508/)` 定義了 `Envelope` 與 `Fault` 的結構。

  這一課不會要求你寫 SOAP。你需要認得它的 envelope 長什麼樣，以及它代表的是另一種分工選擇。
</FieldNote>

## 03. method 決定 Server 做什麼，也決定 Status Code

## 04. 201 Created 回來之後，它沒有替你做什麼

`201 Created` 的意思是 Server 已經建立了一筆新資源。把剛才那次 `POST` 的完整回應再看一次：

<Terminal title="bash — the full 201 response" flavor="output">{`
< HTTP/1.1 201 Created
< content-type: application/json
< content-length: 31

{"name":"bob","role":"student"}
`}</Terminal>

RFC 9110 對 `201` 的規定是：Server 應該在 `Location` Header 回報新資源的 URL，好讓 Client 知道剛建立的東西住在哪裡。這份回應沒有 `Location`。

<Callout type="note" title="為什麼沒有 Location">
  框架不會替你猜新資源的 URL。這個練習 API 用送進來的 `name` 當識別，但它沒有把 `/users/bob` 寫進 `Location`。要回這個 Header，必須由 route 自己決定；寫法在單元 08。
</Callout>

沒有 `Location` 的實際後果很具體：Client 只能從 Body 的欄位猜剛才那筆資源的識別。如果 Body 沒有回識別欄位（例如回 `{"ok":true}`），Client 就永遠拿不到 `bob` 這個位置，下一步連 `GET /users/bob` 都組不出來。

<Callout type="important" title="Status Code 是 Server 的答案，不是裝飾">
  第一單元說過：責任分界看打錯網址、遺漏參式，還是後端自己出錯。這一單元多一條規則：Client 送出 `method` 與 `path` 之後，Server 決定執行、拒絕，還是回 `405` 並告訴你它接受什麼。Client 不該從 `200` 推測一切正常，也不該把 `404` 當成空的資料。
</Callout>

## 05. 同一個 method 送兩次，結果不一定相同

第一單元提過 `GET` 是 safe method（讀取不該改動資源狀態），`POST` 通常不是 idempotent，也就是重送一次不會得到同樣的最終結果。現在用這支 API 把它看見。

讀三次，三次一模一樣：

<Terminal title="bash — read three times">{`
for i in 1 2 3; do curl -s http://127.0.0.1:8000/users/alice; echo; done
`}</Terminal>

<Terminal title="bash — three identical reads" flavor="output">{`
{"name":"Alice","note":"First HTTP example"}
{"name":"Alice","note":"First HTTP example"}
{"name":"Alice","note":"First HTTP example"}
`}</Terminal>

同一份 Body 建立兩次，兩次都回 `201`，但資料不是兩筆：

<Terminal title="bash — create the same name twice">{`
curl -s -X POST http://127.0.0.1:8000/users \\
  -H 'Content-Type: application/json' \\
  -d '{"name":"carol","role":"student"}'
echo
curl -s -X POST http://127.0.0.1:8000/users \\
  -H 'Content-Type: application/json' \\
  -d '{"name":"carol","role":"ta"}'
echo
curl -s http://127.0.0.1:8000/users/carol
echo
`}</Terminal>

<Terminal title="bash — the second call overwrote the first" flavor="output">{`
{"name":"carol","role":"student"}
{"name":"carol","role":"ta"}
{"name":"carol","role":"ta"}
`}</Terminal>

第三行是最後的狀態：只剩一份 `carol`，而且是第二次送的那份。這支練習 API 用 `name` 當 key，第二次的 `POST` 是「再執行一次建立」，所以覆蓋了第一次。

<Callout type="note" title="這不是 bug，是 POST 的定義">
  `POST` 沒有冪等性的保證。網路逾時、使用者重按按鈕、proxy 自動重試，都可能讓同一份 Request 被送兩次。真實系統的兩種做法：用 auto-increment id 或 UUID 當識別，讓每次建立都落在新的位置；針對付款、下單這類重複送出風險高的動作，另外帶一把 idempotency key，讓 Server 認得「這是同一次請求」。這一段屬於識別設計，本課不展開；期末專題會用到。
</Callout>

用不同名字建立三次，就是三筆：

<Terminal title="bash — three creates, three members">{`
for name in dan erin frank; do
  curl -s -o /dev/null -w "$name=%{http_code}\n" \\
    -X POST http://127.0.0.1:8000/users \\
    -H 'Content-Type: application/json' \\
    -d "{\\"name\\":\\"$name\\"}"
done
`}</Terminal>

## 06. N+1：回傳一模一樣的資料，問了 501 次

前五節都在講一個資源怎麼被建立和取回。這一節換一個角度：**同一份資料，用兩種方式取回，程式會問資料庫幾次。**

`n_plus_one.py` 有一張 `authors` 和一張 `notes`。目標很單純：用最少的語句，把每個作者和他的筆記一起取回來。

<Terminal title="bash — 20 個作者，21 條語句" flavor="output">{`
$ python n_plus_one.py small
1. Twenty authors, and every statement
    SELECT id, name FROM authors ORDER BY id
    SELECT title FROM notes WHERE author_id = 0 ORDER BY id
    SELECT title FROM notes WHERE author_id = 1 ORDER BY id
    SELECT title FROM notes WHERE author_id = 2 ORDER BY id
    SELECT title FROM notes WHERE author_id = 3 ORDER BY id
    SELECT title FROM notes WHERE author_id = 4 ORDER BY id
    ... and 15 more
    total: 21 statements for 20 authors
  n_plus_one, 20 authors
    statements: 21
    authors returned: 20
    total titles: 500
  join,       20 authors
    statements: 1
    authors returned: 20
    total titles: 500
    identical result: True
`}</Terminal>

<Callout type="important" title="`identical result: True` 是這一段的重點">
  **兩種寫法回傳完全相同的資料。** 一種問了 21 次，另一種問了 1 次。

  而且注意那個數字怎麼來的：`21 = 1 + 20`。先查一次拿到 20 個作者，然後**每個作者再查一次**。作者有幾個，就多幾次。

  這就是 N+1 的名字：**一條列表查詢，加上一條一條的查詢。**
</Callout>

### 06.1 先講清楚：這是量出來的，不是數出來的

`n_plus_one.py` 用 `set_trace_callback` 記錄 sqlite3 **實際執行**的每一條語句。所以輸出裡的 `21` 和 `1` 都是數來的。

<Terminal title="bash — 20 個作者和 500 個作者，程式碼完全一樣" flavor="output">{`
$ python n_plus_one.py scale
2. The same code, at 20 authors and at 500 authors
  n_plus_one, 20 authors
    statements: 21
  n_plus_one, 500 authors
    statements: 501
  join,       20 authors
    statements: 1
  join,       500 authors
    statements: 1
    the gap grew from 20x to 500x
`}</Terminal>

這裡我把程式印的 `time:` 那一行略掉了，因為它跟下面那個警告是同一件事：**每次跑都不一樣的數字，不該出現在你可能會截圖的地方。** 語句數留下來，因為那才是這一段的證據。

<Callout type="warning" title="本機的時間數字證明不了任何事，這裡要說清楚">
  你在自己機器上跑，500 次查詢確實很快，因為 SQLite 是一個檔案，就在你同一顆磁碟上。**但那個數字每次跑都不一樣** —— 這個檔案連跑四次，同一份工作是 28、66、175、218 毫秒。**6 倍的差距。**

  **本機的量測只證明一件事：語句數是 501。**

  所以 `n_plus_one.py latency` 的摘要行**刻意不放本地時間**，只放語句數和模擬成本：

  <Terminal title="bash — the same work, with a cost per statement" flavor="output">{`
    n_plus_one, 20 authors:  21 statements,     21 ms if each statement cost 1 ms
    n_plus_one, 500 authors: 501 statements,    501 ms if each statement cost 1 ms
    join,       20 authors:   1 statements,      1 ms if each statement cost 1 ms
    join,       500 authors:   1 statements,      1 ms if each statement cost 1 ms
  `}</Terminal>

  本地時間還在程式印出來的那幾個區塊裡，只是不在你可能會截圖的那一行。**一個會漂的數字不該放在那裡。**

  **500 條語句、每條 1 毫秒，就是半秒。** 而且是每一個 Request 都要等半秒，只為了顯示一模一樣的資料。
</Callout>

### 06.2 為什麼它活過 code review

<Callout type="important" title="因為開發時資料只有三列">
  你在本地開發，資料庫裡可能有 3 個作者。那就是 4 條語句，跑起來 1 毫秒，**你看不出任何問題。**

  上線之後變成 500 個作者，你也不會立刻發現——**它沒有錯誤**，只是某個頁面比別的慢，而那個頁面通常不熱門。

  N+1 是一種**不會自己浮出水面的 bug**：沒有例外、沒有錯誤訊息、沒有 log。它只有在流量和資料量同時長大之後才開始 costing 你，而且已經上線很久了。
</Callout>

<Callout type="note" title="所以怎麼在 review 時抓到它">
  **看迴圈裡有沒有查資料庫。** 這是唯一可靠的規則，因為它不依賴資料量。

  ```python
  for author in authors:
      notes = query("SELECT ... WHERE author_id = ?", author)   # ← 這就是 N+1
  ```

  只要查詢寫在迴圈裡面，而且查的是「跟迴圈元素有關的東西」，預設就當成 N+1 看待，除非你量過。
</Callout>

### 06.3 加索引救不了它

這是最值得講的一段，因為單元 05 剛教完索引，**很容易以為「加了索引就沒問題了」**——可是索引不會把你的 N+1 變成一條 `JOIN`。

<Terminal title="bash — with an index on notes(author_id)" flavor="output">{`
$ python n_plus_one.py indexed
3. Adding an index makes each query faster, and does not help
    with an index on notes(author_id): 501 statements
    the plan for the per-author query:
      SEARCH notes USING INDEX idx_notes_author (author_id=?)

   Every one of those statements is fast now. There are just 501 of them.
   An index makes a query cheap. It does not make 501 queries into one.
`}</Terminal>

<Callout type="warning" title="索引讓每一條變快，語句數沒有變">
  單元 05 第 07 節的索引讓查詢從 `SCAN` 變成 `SEARCH`，那條語句本身確實快了很多。

  **但還是 501 條。** 而每一條都要送出、等待、解析——不管它自己有多快。

  這兩件事要分開：
  - 索引解決「**一條**語句太慢」
  - N+1 解決「**太多**條語句」

  **有了索引，N+1 反而更難發現**，因為每一條都很快，你量不出那個總數。
</Callout>

### 06.4 修法：把 N 條變成 1 條

那要怎麼把它變成一條？`fetch_join` 用一個 `LEFT JOIN` 拿全部，然後在 Python 裡分組：

<Terminal title="the two queries, side by side" flavor="output">{`
# 21 or 501 statements
authors = connection.execute("SELECT id, name FROM authors ORDER BY id").fetchall()
for author_id, name in authors:
    notes = connection.execute(
        "SELECT title FROM notes WHERE author_id = ? ORDER BY id", (author_id,)
    ).fetchall()

# 1 statement
rows = connection.execute(
    "SELECT a.name, n.title FROM authors a "
    "LEFT JOIN notes n ON n.author_id = a.id "
    "ORDER BY a.id, n.id"
).fetchall()
`}</Terminal>

<Callout type="important" title="兩個容易出錯的地方">
  **一、要用 `LEFT JOIN`，不是 `JOIN`。**

  沒有筆記的作者，用 `JOIN` 會整個人消失。用 `INNER JOIN` 的話，作者數量會比預期少，而且少多少取決於資料——這種 bug 在測試資料齊全的時候看不出來。

  **二、分組要在 Python 裡做，不要再查第二次。**

  常見的錯誤寫法是：先 `JOIN` 拿到全部，再對每個作者**又**查一次確認細節。那是「1 + N 變成 1 + 1 + N」，更糟。
</Callout>

<Callout type="note" title="另一個選項：用 `IN`">
  ```sql
  SELECT * FROM notes WHERE author_id IN (1, 2, 3, ...)
  ```

  一條語句，效果跟 `JOIN` 一樣。差別是 `JOIN` 會把兩個表合成一個結果集，`IN` 讓你拿到兩份資料、自己在程式裡對應。

  **哪個比較好取決於你最後要回傳什麼形狀**，而那是單元 06 前五節在講的事。
</Callout>

### 06.5 這跟單元 05 的索引是同一課的兩半

<Callout type="important" title="一個關語句有多快，一個關語句有幾條">
  | | 問題 | 診斷 | 修法 |
  | --- | --- | --- | --- |
  | 索引 | 一條語句太慢 | `EXPLAIN QUERY PLAN` 顯示 `SCAN` | 加索引 |
  | N+1 | 語句太多 | **數語句數**，不是看時間 | 改成 `JOIN` 或 `IN` |

  兩個都會讓頁面變慢，症狀一模一樣，但原因和修法完全不同。

  **所以診斷順序是：先數語句數。** 如果一條，就去看有沒有 `SCAN`；如果是 N+1，先改結構，改完之後才輪到索引。

  反過來做——先看到慢就一路加索引——很可能會加到一條本來就很快的語句上，然後什麼都沒改善。
</Callout>

## 07. 把一個程式拆成兩個

前六節都在講「資源」，這裡要決定的事更難一點：**一個專題要不要變成兩個。**

先講結論。**多數初學專題在這個階段不該拆分，這門課的期末專題也不該**，理由如下：

<Callout type="important" title="拆分的理由不是「檔案太長」">
  長檔案很煩，但**不貴**。你不需要兩個行程、兩個部署、兩套監控，就能處理一個三千行的檔案。

  真正該拆的理由只有一個：**同一件事，因為兩個不同的原因而需要改動。**

  - 兩個團隊各自擁有它，而且更新的時間不同
  - 一部分需要往上擴充，另一部分必須留在原地
  - 一部分的可用性要求不同，所以一次部署不該有能力把另一部分弄掛

  其他理由都不是理由。**「看起來比較有規模」不是理由**，「有共用狀態所以先不要拆」也不是 —— 共用狀態正是拆分會讓它更糟的東西。
</Callout>

### 07.1 拆了之後，答案一模一樣

<Terminal title="bash — the same logic, measured both ways" flavor="output">{`
$ python split_demo.py inprocess
1. Two modules, one process

   orders logic lives in a function. users calls it directly.

   direct function call
     300 calls in 0.0 ms
     142 ns per call

$ python split_demo.py overhttp
2. The same logic, in a second process

   HTTP call to the other process
     300 calls in 88.6 ms
     295,438 ns per call

   over http : {'user_id': 3, 'orders': 21, 'total': 5250}
   direct    : {'user_id': 3, 'orders': 21, 'total': 5250}
   identical : True
`}</Terminal>

<Callout type="warning" title="先看最後一行，再看中間那兩個數字">
  **答案完全一樣。** 這很重要：拆分不會讓你的程式算錯任何東西。

  改變的是**每次呼叫的成本**。上面那兩個絕對值每次跑都會動，所以倍率不要用手指算 —— `python split_demo.py both` 會把兩條路都跑一次然後自己算：

  <Terminal title="bash — the ratio, computed by the program" flavor="output">{`
  $ python split_demo.py both
     in-process function call
       300 calls in 0.0 ms
       128 ns per call
     HTTP call to the other process
       300 calls in 131.2 ms
       437,193 ns per call

     ratio: 3,410x more expensive per call

     Do not quote that ratio. Across six runs with pauses it moved
     between about 1,500x and about 7,900x, because the HTTP side
     carries whatever else this machine is doing. What holds every
     time is the order of magnitude: hundreds of nanoseconds against
     hundreds of microseconds. Three orders, at least a thousandfold.
  `}</Terminal>

  **那個倍率不要引用。** 我第一次量它時連跑四次，落在 2,300 到 3,400，看起來很穩；**加上間隔再跑六次，它變成 1,476 到 7,851。** 同樣是那個 `both`，同一台機器，差距 5.3 倍 —— 因為 HTTP 那邊的成本裡面包含了這台機器當下在做什麼。

  **每次都成立的是數量級：幾百奈秒對上幾百微秒，三個數量級，至少千倍以上。** 這才是結論；具體幾千倍是這台機器、這個負載的性質，不是這堂課的。

  而且這還是兩台都在同一台機器、用 loopback 的最佳情況。真的跨機器再加上網路來回，數字只會更大。

  **所以「要不要拆」從來不是效能問題，是部署與擁有權的問題。** 想清楚那一點，就不會為了「跑得快」去拆。
</Callout>

### 07.2 真正改變的是失敗方式

上面兩個版本都成功，所以看不出**拆分**的代價。差別要等到**失敗**的時候才現形，而且那才是重點。

<Terminal title="bash — the same call, when the other side is too slow" flavor="output">{`
   Now make that other process too slow to answer.
   outcome   : client gave up after 1s (1.0s)
`}</Terminal>

<Callout type="important" title="這是一個拆分之前不存在的失敗模式">
  在同一個行程裡，被呼叫的函式**不可能被放棄**。它要嘛回傳答案，要嘛丟例外，而你就站在那裡。

  跨到網路之後就不一樣了：**對方可以活著但不回應。**

  行程沒死、port 還開著、CPU 還在跑，只是太慢了。這種狀況在你把兩個東西放進同一個行程時**不存在**。
</Callout>

<Callout type="warning" title="而且它會一路連鎖到別的章節">
  呼叫會逾時 → 逾時就要重試 → 重試可能重複執行副作用 → 副作用必須 idempotent。

  **單元 03 第 08 節（請求期限）和第 07 節（背景工作、沒有人在等）就是這張帳單的兩半。** 換句話說，拆分不是多寫一個部署設定，是把一整串本來不必處理的問題變成必須處理。
</Callout>

### 07.3 拆分之後你會失去的三樣東西

<Callout type="important" title="同一個交易不能再保證了">
  同一個行程裡，你可以這樣做：

  ```python
  order = create_order(...)
  decrement_stock(...)      # 這裡失敗了，整件事 rollback
  ```

  拆成兩邊之後，「這裡失敗了要怎麼辦」變成一個**分布式系統的問題**，而沒有免費的答案。

  標準做法是 **Saga**：把一筆交易拆成一串可以各自成功的步驟，每一步記錄自己做到哪裡，失敗時照著已完成的步驟往回撤。

  **這件事的複雜度是真的。** 它也是「初學專題不該拆」最實際的理由。
</Callout>

<Callout type="warning" title="2. 記憶體裡的東西變成別人的記憶體">
  同一個行程裡，一個 `dict` 就是大家共用的。拆分之後它變成**另一個服務的內部狀態**，而你只能透過它的 API 去碰。

  這通常是拆分之後最貴的一條：**所有「我就直接改一下」的捷徑全部消失。**
</Callout>

<Callout type="warning" title="3. 除錯變成兩台電腦的事">
  單元 15 教過用 request id 把 log 接起來。拆分之後，同一個使用者動作的 log 散在兩個行程、兩份 log、可能兩個時區。

  **除錯成本上升的不是一點，是一個量級。** 而且這是永久的，不是過渡期。
</Callout>

### 07.4 拆分換來的三樣東西

<Callout type="important" title="公平地講，它換來的是真的">
  - **各自部署。** 改訂單不必等使用者功能排期。
  - **各自擴充。** 訂單服務|scale 到十份，使用者服務一份就夠。
  - **故障隔離。** 單元 17 講過連鎖故障；如果兩邊本來就有不同的可用性需求，隔離本身就是需求。

  **所以它是對的工具，只是昂貴。** 判斷的問題從來不是「好不好」，而是「**我現在這個痛是真的嗎**」。
</Callout>

<Callout type="note" title="一個誠實的順序">
  1. 先讓它變成**一個行程裡的好模組**。檔案分開、依賴方向清楚、測試分開。
  2. 真的痛到受不了了，再上網路。
  3. 上網路之前，先確認你已經會 timeout、會重試、知道什麼叫 idempotent。

  **第 3 步最常被跳過，而跳過之後第 2 步就會變成一串難以除錯的隨機失敗。**

  順帶一提，這門課的期末專題基本上應該停在第 1 步。你會需要一個真的很大的系統才會感覺到第 2 步的痛 —— 而「感覺不到痛」正是**不該拆**最好的判斷依據。
</Callout>

## 08. 終端實戰驗證：四組對照

`LEFT JOIN` 那一組和 N+1 那一組，回傳的資料逐字相同，差別只有語句數。**這是本課最後一個結論的證據，第五步會用 curl 之外的方式再量一次。**

三次讀取與兩次建立的差別看過了，N+1 的差別也看過了。接著把這一課的結論各跑一次：前四步的結果都在 `curl` 的輸出裡，第五步開始換成數語句。

### 第一步：讀取不會改動狀態

<Terminal title="bash — step 1" flavor="output">{`
for i in 1 2 3; do curl -s http://127.0.0.1:8000/users/alice; echo; done
`}</Terminal>

三行輸出必須完全相同。不同，就表示你的 API 有問題。

### 第二步：建立會改動狀態

讀取不改狀態，上一步那三行輸出就是證據。反過來問：`POST` 會不會改？

<Terminal title="bash — step 2">{`
curl -i -X POST http://127.0.0.1:8000/users \\
  -H 'Content-Type: application/json' \\
  -d '{"name":"iris","role":"student"}'
curl -i http://127.0.0.1:8000/users/iris
`}</Terminal>

第一個 `201`、第二個 `200`。這是 `POST` 改動了 Server 狀態最直接的證據。

### 第五步：數語句，不是數時間

<Terminal title="bash — step 5, the count that matters" flavor="output">{`
$ python n_plus_one.py scale
  n_plus_one, 20 authors
    statements: 21
  n_plus_one, 500 authors
    statements: 501
  join,       500 authors
    statements: 1
`}</Terminal>

**看 `statements` 那一行，不要看 `time`。** 本機的時間證明不了任何事，語句數才是證據。

### 第六步：同一段邏輯，兩種呼叫方式

前五步的時間都不值得看，這一步要看的是另一種成本。第六步把它搬到第二個行程，然後比較**每次呼叫**的代價。

<Terminal title="bash — step 6, the same logic both ways" flavor="output">{`
$ python split_demo.py inprocess
     142 ns per call

$ python split_demo.py overhttp
     295,438 ns per call

   identical : True

$ python split_demo.py both
   ratio: 3,410x more expensive per call
`}</Terminal>

**答案一樣，慢了幾千倍。** 具體幾千倍每次跑都不一樣（我量到的區間是 1,476 到 7,851），所以看 `both` 印的那個 `ratio:` 知道量級就好，不要自己用兩個絕對值去算，也不要把某一次的數字寫進報告。

這就是呼叫跨過行程的價格，而這還只是同一台機器上的 loopback，還沒真的上網路。

### 第三步：撞到 method 的牆

第 03 節看過 `405` 是怎麼來的，這裡換一個 method 再確認一次——**同一條路徑，method 換了，答案就換了**：

<Terminal title="bash — step 3" flavor="output">{`
> curl -i -X DELETE http://127.0.0.1:8000/users/iris
< HTTP/1.1 405 Method Not Allowed
< allow: GET
`}</Terminal>

`allow` 這個 Header 要記下來。它是 Server 親口告訴你「這條路徑現在只接受哪一種 method」——之後寫 Client 遇到 `405`，第一個反應就是讀它。

### 第四步：動作寫進網址的下場

<Terminal title="bash — step 4" flavor="output">{`
> curl -i 'http://127.0.0.1:8000/users/delete?id=iris'
< HTTP/1.1 404 Not Found

{"detail":"User not found"}
`}</Terminal>

`delete` 被當成一個 username。這就是為什麼 method 與 path 要分開負責。
