有同學問：兩個請求同時進來，假設是真的同時搶到 DB lock 會怎樣？先把問題修正：以 SQLite 這套檔案資料庫引擎來說，那個假設不成立。寫鎖是獨佔的，同一時間只有一個請求能持有它。

第二個請求收到的 `database is locked` 是一句拒絕訊息，不是資料損毀的通知。資料庫用它告訴你：這次寫入沒有發生，你可以決定下一步。

## 一、先看答案：鎖只有一個贏家

把「同時搶到」換成「同時想拿」。兩個請求同時呼叫 `BEGIN IMMEDIATE`，SQLite 只讓其中一個拿到鎖，另一個等到 `busy_timeout` 到期就收到拒絕。

<Callout type="note" title="同時抵達是真的，同時持有是假的">
  兩個請求確實可以在同一瞬間抵達，甚至在同一時脈週期發出指令。不可能的是「兩邊都拿到同一把獨佔鎖」。SQLite 官方文件明說同時只有一個 `RESERVED` 與一個 `EXCLUSIVE`；把文件裡的 process 換成 thread 也一樣成立。
</Callout>

這和上一課的 `users.json` 對照最清楚。文字檔的 lost update 會讓兩個 writer 都報成功，其中一筆被安靜蓋掉；資料庫的拒絕則讓輸家知道自己沒寫進去。

### 同時起跑：閘門實驗

上一個實驗讓 loser 等 holder 先拿到鎖。要回答「會不會同時摸到鎖」，得讓兩條執行緒真的同時出發。

`threading.Barrier(2)` 讓兩條執行緒過同一道閘，誰也不比誰早。`busy_timeout = 0` 讓沒拿到鎖的一方立刻回錯，不給「等一下再拿到」的模糊空間。每一輪換一個新的資料庫檔案。

輸出有兩件事。贏家有時是 A、有時是 B，代表起跑真的同時，順序並不固定。但每一輪都只有一個贏家，`rows=1` 也說明沒有人寫出第二筆。

20 輪是可驗證證據：它證明這台機器上的實作符合契約。有限次實驗不能證明「永遠不可能」。保證來自機制：取得鎖是一次原子操作，核心把同時到達的呼叫排成先後。SQLite 規格也明說同時只有一個 `RESERVED` 與一個 `EXCLUSIVE`。

前提是檔案系統的鎖正常。SQLite 官方文件警告 NFS 的 advisory locking 有實作問題；那種情況下保證會破，資料可能損毀。

## 二、親手跑一次

回到可以自己改的那支脚本。它把剛才的保證攤開成可見的步驟：holder 持有寫鎖一秒，loser 在同一秒內連續嘗試寫入。

<Terminal title="bash — run the contention demo">{`
$ cd exercises/05b-db-locks
$ rm -f locks.db
$ python retry_the_lock.py
`}</Terminal>

<Terminal title="output — one winner, one safe retry" flavor="output">{`
holder: BEGIN EXCLUSIVE -> write lock acquired
loser: attempt 1 -> database is locked
loser: attempt 2 -> database is locked
holder: COMMIT -> lock released
loser: attempt 3 -> committed
replay: same loser id inserted again -> rows for loser = 1
winner rows: 1, loser rows: 1
`}</Terminal>

輸出有兩件事要分開看。holder 從 `BEGIN EXCLUSIVE` 到 `COMMIT` 之間，loser 兩次都拿到 `database is locked`。holder commit 之後，第三次嘗試才成功。

最後兩行是第二次證明。replay 把同一個 `loser` id 再送一次，`rows for loser = 1` 沒有變成 2。

## 三、輸家該怎麼辦

鎖拒絕的不是你的程式，而是這一次寫入。接下來四件事，缺一件就會把拒絕變成資料錯帳。

#### 1. 接住鎖衝突，不要全吞

Python 的 `sqlite3` 把鎖衝突丟成 `sqlite3.OperationalError`。腳本只接住訊息裡有 `locked` 的錯誤，其他錯誤照樣往上拋。把所有例外都吞掉，連程式 bug 都會被當成鎖衝突。

#### 2. 退避重試，而且要有上限

每次失敗等 50ms、100ms、200ms，最多試 10 次。上限很重要：鎖永遠不釋放時，程式要停下來回報，不能無限重試。

#### 3. 唯一約束讓重試冪等

重試解決了拿不到鎖的問題，卻帶來新問題：第一次和重試可能各寫一次同一筆。表格的 `id` 是 `PRIMARY KEY`。`INSERT ... ON CONFLICT(id) DO NOTHING` 讓同一筆重送只留一列；`rows for loser = 1` 就是證據。

#### 4. 拿不到就回 503

唯一約束處理的是重複，不是等待。重試用完還拿不到鎖，API 回 `503 Service Unavailable` 加 `Retry-After`。Client 因而知道這是暫時失敗，不是資料已寫入。

<Callout type="important" title="拒絕是可以處理的訊號">
  鎖的作用正是讓「兩個人都以為自己寫成功」這件事不可能發生。文字檔會安靜丟資料，SQLite 會明確拒絕；拒絕可以被接住、被重試、被記錄。
</Callout>

## 四、邊界：不是所有資料庫都鎖同一層

PostgreSQL 與 MySQL 用列鎖，兩個交易可以同時改不同列；改同一列時，其中一個等待，形成死結時資料庫會放棄其中一個交易。

那是同一個原則的實作差異，本課沒有在本機驗證，所以不示範。你在這裡學到的是可驗證的部分：寫鎖只有一個贏家，輸家要自己處理失敗。
