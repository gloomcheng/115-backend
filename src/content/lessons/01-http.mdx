## 01. Request 與 Response：網路傳輸的純文字真相

HTTP 的基本單位是一組 Request 與 Response。Client 先送 Request，Server 收到後才回 Response。

<img src={withBase('/images/lessons/01/request-response.webp')} alt="ELI5 Request 與 Response 封包傳輸示意圖" width="1672" height="941" loading="lazy" decoding="async" />

用 `curl -v` 把這一組 Request 與 Response 的真實內容印出來時，畫面大致會出現這兩段：

<Terminal title="HTTP — wire view" flavor="output">{`
> GET /status/200 HTTP/1.1
> Host: httpbin.org
> User-Agent: curl/8.x
> Accept: */*
>
< HTTP/1.1 200 OK
< Content-Type: text/html; charset=utf-8
< Content-Length: 0
`}</Terminal>

`/status/200` 是這行 Request 的目標路徑（path），告訴 Server 你想要操作哪個位置；完整的網址結構會在下一個單元詳細拆解。

觀察上面的封包結構：Request 的第一行包含 Method、目標路徑與協定版本。Response 的第一行包含協定版本、Status Code 與 reason phrase；`reason phrase` 是跟在狀態碼後的簡短文字，例如 `OK`。第一行後面是 Header，用來傳遞附加欄位資訊；空白行代表 Header 結束；空白行之後則是 Body，用來承載訊息本身的內容資料。

這條傳輸在網路線上完全是純文字。每一行結尾的換行，在 HTTP/1.1 規格中嚴格規定使用 **CRLF**（`\r\n`，共兩個位元組）：`CR`（Carriage Return，回車，`\r`）源自機械打字機把字車滾筒推回最左端，`LF`（Line Feed，換行，`\n`）則是將打字紙向上捲動一行。當接收端讀到連續兩組換行形成的空白行（即 `\r\n\r\n`）時，就知道所有 Header 已經結束，接下來是 Body。

<Callout type="note" title="curl -v 開頭那幾行 * 是什麼？TCP 三向交握">
  執行 `curl -v` 時，你會看到 `> GET` 之前有幾行以 `*` 開頭的輸出：

  ```text
  * Trying 54.208.105.16:443...
  * Connected to httpbin.org (54.208.105.16) port 443
  * SSL connection using TLSv1.3
  ```

  HTTP 是應用層協定，傳輸時必須依賴底層的 **TCP（傳輸層協定）** 建立可靠連線。在 Client 送出第一個 HTTP 字元之前，雙方必須先透過三次封包往返確認彼此的收發能力，這就是 **TCP 三向交握（Three-Way Handshake）**：

  1. **第一次交握（SYN）**：Client 向 Server 發送同步請求，說：「我想連線，這是我的初始序號。」（對應終端機的 `* Trying...`）
  2. **第二次交握（SYN-ACK）**：Server 回應確認與同步，說：「我收到你的要求了，我也想連線，這是我的初始序號。」
  3. **第三次交握（ACK）**：Client 回傳最後確認，說：「我收到你的確認了，連線正式建立！」（對應終端機的 `* Connected to...`）

  三次回合確認雙方通道都暢通後，TCP 連線才算成功建立（若走 HTTPS 還會緊接著執行 TLS 加密協商）。直到連線就緒，終端機才會出現 `> GET`，正式開始發送第一行 HTTP 純文字。
</Callout>

### Stateless 到底少了什麼

在這條純文字傳輸鏈上，HTTP 是無狀態協定（stateless protocol）。意思是每一次 Request 都是獨立的，協定本身不會替你保存上一次操作的狀態。

如果應用程式需要知道使用者的身分或購物車內容，不能依賴 HTTP 自動記住，必須由應用程式在每次 Request 自行帶上識別資料。這也是為什麼後續單元會介紹在 Header 帶上認證憑證。

<Callout type="note" title="單元 11 再處理登入">
  登入後，瀏覽器通常會在後續 Request 帶 Cookie 或 Token。這一單元先認得 Header 的位置，不展開認證流程。
</Callout>

在展開更多欄位前，先釐清這一去一回中的兩個角色：誰送出 Request，誰決定 Response。

## 02. Client 與 Server：決定權與責任邊界

Client 是主動送出 Request 的程式。Server 在指定位置等待 Request，執行對應邏輯，再決定 Response。

<img src={withBase('/images/lessons/01/client-server.webp')} alt="ELI5 客戶端與伺服器角色契約與決定權示意圖" width="1672" height="941" loading="lazy" decoding="async" />

Client 決定何時送出、使用哪個 Method、請求哪個 target，以及要帶哪些 Header 或 Body。瀏覽器、手機 App 與 `curl` 都可以是 Client。

Server 決定這個 target 是否存在、目前使用者能不能操作、程式要做什麼，以及最後回哪個 Status Code。後續章節我們用 Python 寫的後端程式在等待請求時，它就是 Server。

角色不是看機器大小。你的筆電可以同時跑 curl 與後端程式；前者是發出請求的 Client，後者是處理請求的 Server。

當系統發生錯誤時，責任分界非常清楚：如果是打錯網址、遺漏參數或格式錯誤，責任在 Client；如果是後端程式出錯、資料庫斷線或邏輯崩潰，責任在 Server。

## 03. HTTP Methods：不只是名字，而是行為契約

Request 第一行的第一個單字是 Method。它描述 Client 想對指定資源執行的操作動作，不是裝飾用的標籤。這裡的資源（resource）指 Server 上可識別的一筆資料或內容。

<img src={withBase('/images/lessons/01/http-methods.webp')} alt="ELI5 HTTP 五大動詞與冪等性示意圖" width="1672" height="941" loading="lazy" decoding="async" />

這五個最核心的 HTTP Method 具有明確的語意分工：

- `GET /items`：讀取 items 清單或單一資源，不應修改任何資料。
- `POST /items`：在 items 集合下建立一筆新資料，或觸發一個非冪等的運算流程。
- `PUT /items/7`：用 Request Body 帶來的完整內容，替換指定資源的全部狀態。
- `PATCH /items/7`：修改指定資源的一部分欄位，例如只更新姓名或密碼。
- `DELETE /items/7`：刪除指定資源。

這些語意是 Client 與 Server 之間的共同契約，不是標籤。怎麼把動作放進這個契約、而不放進網址，是單元 06 的主題。

要讀懂這份契約，先要分清兩組看起來很像、維護責任卻不同的性質：safe 與 idempotent。

### Safe 與 Idempotent 的嚴格區別

**safe method** 只要求讀取，不應改變伺服器上的資源狀態。`GET` 屬於 safe method。

**idempotent（冪等性）**指的是：同一個 Request 執行一次或多次，對伺服器資源產生的最終效果相同。`GET`、`PUT`、`DELETE` 屬於 idempotent 操作；`POST` 通常不是。

例如刪除同一筆資料兩次：第一次刪除時，伺服器移除了該筆記錄；第二次再執行刪除時，伺服器可能回傳 404，但資料庫中「該筆資料不存在」的最終狀態完全相同。因此 `DELETE` 仍然是 idempotent 操作。

相反地，如果用 `POST /orders` 建立訂單，連續送出兩次可能會在資料庫中產生兩筆不同的訂單，導致重複扣款。這正是為什麼線上付款時畫面常提示「請勿重複點擊送出」。

<IdempotentDemo client:visible />

Client 送出 Method 提出操作動作；而 Server 處理完成後，則用 Status Code 回報處理結果。

## 04. Status Codes：責任歸屬的五大家族

Response 第一行裡的三位數是 Status Code。它是 Server 用來告訴 Client 這次請求處理結果的狀態數字。

<img src={withBase('/images/lessons/01/status-codes.webp')} alt="ELI5 HTTP 狀態碼責任判定示意圖" width="1672" height="941" loading="lazy" decoding="async" />

狀態碼的第一個數字決定了責任與處理狀態的五大類別：

- `1xx (Informational)`：請求已接收，繼續處理中；最常見於 WebSocket 升級連線（`101 Switching Protocols`）。
- `2xx (Successful)`：Request 已成功被伺服器接收、理解並接受。常見的有 `200 OK`、`201 Created`（通常伴隨 `Location` Header 指向新資源）與 `204 No Content`（操作成功但不需要回傳內容，常見於 DELETE）。
- `3xx (Redirection)`：Client 還要採取另一個動作才能完成請求。最常見的是 `301 Moved Permanently`（永久轉址）與 `302 Found`（暫時轉址），瀏覽器會依 Response 裡的 `Location` Header 自動導向新網址。
- `4xx (Client Error)`：Server 判定目前的 Request 無法照要求處理，責任在 Client。例如 `400 Bad Request`（語法錯誤）、`404 Not Found`（資源不存在）、`405 Method Not Allowed`（用了伺服器不支援的動詞）與 `422 Unprocessable Content`（資料驗證失敗）。
- `5xx (Server Error)`：Server 在嘗試處理一個合法的 Request 時內部發生錯誤，責任在 Server。常見的有 `500 Internal Server Error`（後端程式未捕捉的 Exception）、`502 Bad Gateway`（反向代理找不到後端）與 `504 Gateway Timeout`（後端運算逾時）。

Status Code 的第一碼只能先分類，不能取代完整代碼。`400`、`401`、`403`、`404` 都是 4xx，但修復手段完全不同。

在所有 4xx 錯誤中，最容易混淆的是身分與權限的差別。

<Callout type="important" title="401 與 403">
  <code>401 Unauthorized</code> 通常表示 Request 缺少有效的認證資訊（例如未登入），Response 會用 <code>WWW-Authenticate</code> 說明認證方式。<code>403 Forbidden</code> 表示 Server 理解 Request，但拒絕執行；就算確認了身分，目前的使用者也沒有執行這項操作的權限。
</Callout>

`Unauthorized` 這個 reason phrase 容易讓人誤會成「沒有權限」，但 401 實務上處理的是「你是誰」（認證）的問題，403 才是「能不能做」（授權）的問題。判斷時看數字與協定語意，不要只翻譯英文單字。

<FieldNote marker="418" eyebrow="FIELD NOTE 01" title="不是 419：茶壺把玩笑寫進 HTTP">
  1998 年 4 月 1 日發布的 RFC 2324 定義了 `418 I'm a teapot`：拿茶壺煮咖啡時，Server 可以拒絕。它原本是愚人節 RFC，不是一般 API 應該採用的錯誤語意。

  <Terminal title="bash — teapot">{`
curl -i https://httpbin.org/status/418
  `}</Terminal>

  httpbin 目前真的會回 `418` 與一個 ASCII 茶壺。更意外的是，這個玩笑被實作得太廣，RFC 9110 後來把 418 列為 `Unused` 並保留，避免它被重新分配。規格不是只由文件決定，已部署的程式也會反過來影響規格。

  來源：[RFC 2324](https://www.rfc-editor.org/rfc/rfc2324) · [RFC 9110 §15.5.19](https://www.rfc-editor.org/rfc/rfc9110.html#name-418-unused)
</FieldNote>

<FieldNote marker="402" eyebrow="FIELD NOTE 02" title="402 Payment Required：為數位付費預留的位置">
  HTTP 早在早期就預留了 `402 Payment Required`，原本設想瀏覽器未來能直接原生處理線上支付。雖然數十年來各家金流服務多半以自訂流程或轉址實現付款，使得 402 在一般網頁中極少出現；但在現代的微服務與 API 計費探索中，這個狀態碼依然是規格中極具啟發性的設計。不論業務流程如何變化，在網路傳輸層次上，它依然遵循標準的 Request 與 Response。

  來源：[RFC 9110 §15.5.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-402-payment-required)
</FieldNote>

在認識了各種狀態碼之後，不論伺服器回傳的是成功（2xx）還是錯誤（4xx），Client 最終都會收到一份包含 Status Line、Header 與 Body 的純文字 Response。接下來要解答的核心問題是：這些純文字封包，最後是如何在瀏覽器中變成視覺畫面的？

## 05. Response 如何變成畫面：視角穿透

瀏覽器正是負責把這些文字封包繪製成畫面的 HTTP Client。它具備 HTML / CSS 排版引擎與 JavaScript 執行環境，先送出 Request，收到 Response 後再依 Header 與 Body 決定如何呈現內容。

<img src={withBase('/images/lessons/01/browser-vision.webp')} alt="ELI5 從封包到瀏覽器畫面繪製的視角穿透圖" width="1672" height="941" loading="lazy" decoding="async" />

假設 Server 回傳的 Header 與 Body 是：

<Terminal title="HTTP — response wire trace" flavor="output">{`
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<h1 style="color: red;">Hello World</h1>
`}</Terminal>

Terminal 的 curl 只會忠實印出這串純文字。但瀏覽器收到這個 Response 時，會先檢查 `Content-Type` Header：發現是 `text/html`，便啟動 HTML 解析器建立 DOM 樹，計算樣式，最後在螢幕上繪製出一個紅色的「Hello World」大標題。

如果 Server 回傳的是 `Content-Type: application/json`，瀏覽器預設就不會進行排版繪製，而是直接顯示 JSON 文字結構，或是交由前端 JavaScript 程式碼解析處理。

後端除錯時要沿這條四步驟的鏈條逐一排查：Client 送了什麼、Server 收到什麼、Server 程式計算後回了什麼、Client 最後如何顯示。不要把畫面上的任何錯誤全部盲目歸咎給後端。

## 06. 終端實戰驗證：觀察真實連線與極簡 Server

現在打開兩個終端機視窗，進行 3 小時課堂的核心實作驗證。

### 第一步：觀察不同的狀態碼行為

依序執行 `curl -v` 觀察伺服器回傳的不同狀態碼，特別注意 Status Line 以及 301 轉址時的 `Location` Header：

<Terminal title="bash — inspect status codes">{`
curl -v https://httpbin.org/status/200
curl -v https://httpbin.org/status/404
curl -v https://httpbin.org/status/301
`}</Terminal>

觀察 301 的輸出：Server 回傳了 `< HTTP/1.1 301 Moved Permanently`，並附帶了 `< Location: /redirect/1`。這證明了「轉址」並非魔法，而是 Server 明確要求 Client 重新發出請求去抓取新位置。

接著如果加上 `-L` 參數，curl 就會像瀏覽器一樣自動追蹤轉址：

<Terminal title="bash — follow redirect">{`
curl -v -L https://httpbin.org/status/301
`}</Terminal>

這時終端機中會印出兩組完整的 Request 與 Response：第一組收到 301，第二組自動發往新網址並收到 200。

### 第二步：親手啟動極簡 Python 伺服器

在你的電腦上啟動一個最簡單的本機 HTTP 伺服器，親眼看見它如何監聽與印出連線紀錄：

<Terminal title="bash — local python server">{`
python3 -m http.server 8000
`}</Terminal>

<CommandAnatomy client:visible />

接著打開另一個終端機視窗，向自己的電腦發出請求：

<Terminal title="bash — local curl request">{`
curl -v http://localhost:8000
`}</Terminal>

回到執行 Python 的終端機視窗，你會看到一行由這個伺服器印出的標準 log：包含了發出請求的本機 IP、時間戳記、`"GET / HTTP/1.1"` 以及狀態碼 `200`。**同一個程式，同一個 Terminal，你剛才扮演了 Client，現在扮演了 Server。**
