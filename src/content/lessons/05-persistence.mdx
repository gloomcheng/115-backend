## 01. dict 活不過一次執行

先看前兩行輸出：

<Terminal title="bash — the dict case" flavor="output">{`
$ python store.py dict-add
added carol to a dict, held by this process only

$ python store.py dict-list
dict sees: ['alice']
`}</Terminal>

`dict-add` 確實把 `carol` 放進去了。`dict-list` 也確實是一個新的執行——它看不到 `carol`，因為 `carol` 住在**剛才那個行程的記憶體裡**，而那個行程已經結束了。

這就是為什麼 `fastapi dev` 沒有 `--reload` 時，你重啟一次 Server，先前 `POST /users` 建立的資料就會不見。`examples/http-api/main.py:8` 的 `users` 就是這種東西。

<Callout type="important" title="這不是 bug，是 dict 的定義">
  Python 的 `dict` 是一個執行行程內的物件。行程結束，它就結束。要讓資料活過行程結束，必須寫進**行程之外**的東西。接下來兩種寫法，都在做這件事。
</Callout>

## 02. 文字檔：活下來了，但只是一串字

<Terminal title="bash — the JSON case" flavor="output">{`
$ python store.py json-add
added carol to users.json

$ python store.py json-list
users.json sees: ['alice', 'carol']

$ ls -l users.json
-rw-r--r--  1 you  staff  56 users.json

$ cat users.json
{"alice": {"name": "Alice"}, "carol": {"name": "Carol"}}
`}</Terminal>

`carol` 活過了行程結束。檔案裡的 56 個位元組就是你用 `cat` 看到的東西——**沒有藏起來的東西**。你可以用任何文字編輯器改它，`git diff` 也看得懂它改了什麼。

這是文字檔最大的優點，也是它最大的問題：因為它是純文字，**兩個程式同時改它時，沒有任何機制會告訴你其中一個改動不見了。**

<Terminal title="bash — two writers, one text file">{`
$ python json_race.py A & python json_race.py B & wait
writer A: read the file, writing back in 1 second
writer B: read the file, writing back in 1 second
writer A: wrote the file
writer B: wrote the file

$ cat users.json
{"alice": {"name": "Alice"}, "writer-B": {"name": "B"}}
`}</Terminal>

**`writer-A` 不見了，而兩個 writer 都說「我寫好了」。** 沒有錯誤訊息、沒有例外、沒有任何地方留下紀錄。

`json_race.py` 的核心只有四行（先讀、再加一個 key、最後寫回），你可以自己去讀：兩個行程都「讀整個檔案 → 加一個 key → 寫回整個檔案」。B 讀到的版本裡還沒有 A 的改動，所以它寫回去的時候，把 A 的改動一併蓋掉了。這種「兩個同時寫入、彼此蓋掉」的結果就叫 lost update—— 資料蓋掉了，而且沒有人知道。

<Callout type="warning" title="這一課最該記住的一句話">
  資料不見了，而且沒有任何人被告知。這是文字檔最危險的地方——不是它存不住資料，是它在**存不住的那一次完全沒有聲音**。單元 08 CRUD 與單元 10 驗證會處理怎麼預防它。
</Callout>

## 03. SQLite：檔案裡連結構一起存

<Terminal title="bash — the SQLite case" flavor="output">{`
$ python store.py sqlite-add
added carol to notes.db

$ python store.py sqlite-list
notes.db sees: ['carol']

$ ls -l notes.db
-rw-r--r--  1 you  staff  8192 notes.db
`}</Terminal>

同一筆資料，檔案是 8192 bytes 而不是 56。多出來的不是資料，是**結構**。

先確認這不是文字檔：

<Terminal title="bash — the file itself" flavor="output">{`
$ file notes.db
notes.db: SQLite 3.x database, last written using SQLite version 3053004, file counter 2, database pages 2, cookie 0x1, schema 4, UTF-8, version-valid-for 2
`}</Terminal>

然後問它自己有什麼表：

<Terminal title="bash — the structure lives inside the file" flavor="output">{`
$ python store.py sqlite-schema
CREATE TABLE notes (id INTEGER PRIMARY KEY, text TEXT NOT NULL)
`}</Terminal>

`NOT NULL`、`INTEGER PRIMARY KEY` 這些規則**寫在檔案裡**，不是寫在你的 Python 程式裡。這是關鍵差異：你的程式結束了、換了一個人維護，規則還在。

<Callout type="note" title="為什麼一個檔案要 8192 bytes">
  SQLite 把磁碟空間切成固定大小的 page（預設 4 KB），一次配置兩頁。空的資料庫也會占掉這些空間。檔案大小不是資料量，這一點在單元 08 討論磁碟與容量時會再遇到。
</Callout>

## 04. SQLite 會替你守住型別

規則既然在檔案裡，就會被執行。試著塞一個不合型別的值：

<Terminal title="bash — a type violation the file will not accept">{`
$ sqlite3 notes.db "INSERT INTO notes (id, text) VALUES ('carol','x');"
Error: stepping, datatype mismatch (20)

$ sqlite3 notes.db "SELECT id, typeof(id) FROM notes;"
1|integer
`}</Terminal>

`id` 宣告成 `INTEGER PRIMARY KEY`，餵 `'carol'` 進去被拒絕了，而且 `typeof(id)` 確認留下來的是 `integer`。

同一件事用 JSON 做會怎樣？文字檔沒有「欄位型別」這種東西，因為它本來就只是字串。要擋下來，你得自己在 Python 裡寫檢查，而且每一個寫入的地方都要寫一次。

<Callout type="important" title="這是資料庫的真正價值">
  不是「資料存在檔案裡」——文字檔也有。是**規則跟資料放在同一個地方**，而且由同一個引擎執行。這一點到單元 08 講交易時會變得更清楚：規則和資料在同一處，才能一起被保護。
</Callout>

## 05. 同時寫入：一個拒絕，一個不說話

把第 02 節那個安靜的失敗，和 SQLite 放在同一個實驗裡。`hold_the_lock.py` 讓 writer A 獨占寫入鎖三秒：

<Terminal title="Terminal 1 — take the write lock">{`
$ python hold_the_lock.py hold
writer A: holding the write lock for 3 seconds
`}</Terminal>

三秒內在 Terminal 2 送出第二個 writer：

<Terminal title="Terminal 2 — write anyway" flavor="output">{`
$ python hold_the_lock.py write
writer B: refused -> database is locked
`}</Terminal>

兩段都跑完之後，資料庫裡是什麼：

<Terminal title="bash — nothing was silently lost">{`
$ sqlite3 notes.db "SELECT id, text FROM notes;"
1|carol
2|writer A
`}</Terminal>

**writer B 被拒絕了，而這正是重點。** 它知道自己沒寫進去，所以它可以重試、可以回報給使用者、可以在 log 留下紀錄。

把兩個實驗並排看：

| | `users.json` | `notes.db` |
| --- | --- | --- |
| 兩個 writer 同時寫 | 兩邊都回報成功 | 第二個收到錯誤 |
| 丟掉的資料 | 有，靜靜地丟 | 沒有 |
| 你知道出事了嗎 | **不知道** | 知道 |

<Callout type="important" title="拒絕比丟資料好">
  `database is locked` 是一句你可以在程式裡接住的訊息。你可以讓它等待、可以重試、可以回 `503` 給 Client。一個沒有錯誤的資料遺失，你連從哪裡開始查都不知道。
</Callout>

## 06. 併發：把「同時」看清楚

第 05 節看的是資料庫怎麼**拒絕**同時寫入。但真實的後端很少有「只有一個人會動」的時刻——你的 API 同時有幾個 Request 在跑，每一個都是一個執行緒。

要看出差別，最好的方式是讓同一件事壞三次。`race_fix.py` 把「讀→改→寫」寫成三種，同一組資料，跑三次。

<Terminal title="bash — two processes, no protection" flavor="output">{`
$ rm -f race.json race.lock
$ python race_fix.py naive A & python race_fix.py naive B & wait
B: read {}, writing back in 1s
B: wrote the file
A: read {}, writing back in 1s
A: wrote the file

$ cat race.json
{"A": {"at": 1790996440.988849}}
`}</Terminal>

**兩個行程都讀到空物件，兩個都說寫成功了，檔案裡只有一個。**沒有任何一行輸出提到出錯。

把同一組指令再跑一次，這次遺失的可能是 `B`：

<Terminal title="bash — and again, a different one is lost" flavor="output">{`
$ rm -f race.json race.lock
$ python race_fix.py naive A & python race_fix.py naive B & wait
$ cat race.json
{"B": {"at": 1790996439.915694}}
`}</Terminal>

**誰消失是不確定的。**這就是第 05 節說的 lost update：沒有任何一行輸出告訴你出了事。

<Callout type="warning" title="「讀→改→寫」這三步之間，任何東西都可以插進來">
  `read()` 返回之後、`write()` 之前，是一段真空。另一個行程完全可以在這段裡面讀到同樣的舊資料、算出自己的版本、寫回去，把你的改動蓋掉。

  這個視窗在真實系統裡不是一秒，是**你把資料從網路讀完、算完、寫回去的所有時間**——可能幾百毫秒。單機上你用 `sleep(1)` 才看得到；線上它天天發生，而且通常只在尖峰時才出現。
</Callout>

### 06.1 計數器：更安靜的遺失

第三種寫法更常見：把「加一個 key」換成「把數字加一」。瀏覽次數、庫存、購物車數量、投票數，用的都是這一行。

<Terminal title="bash — two increments, count ends at one" flavor="output">{`
$ rm -f race.json race.lock
$ python race_fix.py counting A & python race_fix.py counting B & wait
B: read count=0, writing back in 1s
B: wrote count=1
A: read count=0, writing back in 1s
A: wrote count=1

$ cat race.json
{"count": 1, "A": {"at": 1790996442.054744}}
`}</Terminal>

**兩個行程各加一次，檔案裡的 `count` 是 1。**

這比遺失一個 key 更難發現：key 消失你會注意到檔案少東西，計數器少加一次，**沒有任何東西看起來不對**。

<Callout type="important" title="這是後端最常見、也最貴的一類 bug">
  計數器少算，庫存賣超賣，投票少計。這些錯誤上線之後不會自己復原——資料已經錯了，而且沒有任何機制會把它修回來。

  判斷標準只有一句：**這個值是「算出來的」還是「讀出來的事實」？** 讀出來的事實不會自己變；算出來的東西每一次計算都可能踩到同一段真空。
</Callout>

### 06.2 加鎖：讓真空消失

正確的作法是把「讀→改→寫」整段圈起來，讓第二個行程進來之前必須等：

<Terminal title="bash — the same race, serialised" flavor="output">{`
$ rm -f race.json race.lock
$ python race_fix.py locked A & python race_fix.py locked B & wait
A: hold lock, read {}, writing back in 1s
A: wrote the file, released lock
B: hold lock, read {'A': {'at': 1790996459.28441}}, writing back in 1s
B: wrote the file, released lock

$ cat race.json
{"A": {"at": 1790996459.28441}, "B": {"at": 1790996460.289021}}
`}</Terminal>

**兩個都在。**而且注意第二行程讀到的是 `{'A': ...}`——它讀得到 A 剛剛寫進去的東西，代表 A 確實已經寫完並釋放鎖，B 才進來。

跑三次，三次都是 `["A", "B"]`，而 `naive` 跑三次遺失的是不同的一個。**這不是運氣好，是機制。**

<Terminal title="race_fix.py — the part that actually does the work" flavor="output">{`
def acquire_lock() -> int:
    # O_CREAT without O_TRUNC: open the lock file without destroying it.
    # The returned fd must stay open for the whole critical section. flock is
    # tied to the open file description, so closing it early releases the lock.
    lock = os.open("race.lock", os.O_CREAT | os.O_RDWR, 0o644)
    fcntl.flock(lock, fcntl.LOCK_EX)
    return lock

lock = acquire_lock()
data = read()
time.sleep(1)
data[label] = {"at": time.time()}
write(data)
fcntl.flock(lock, fcntl.LOCK_UN)
os.close(lock)
`}</Terminal>

<Callout type="warning" title="我第一版寫錯了，而它是這裡最值得學的一件事">
  我第一次寫的 `acquire_lock()` 是開檔、`flock`、然後**立刻 `close()`**。跑起來結果是資料照樣遺失。

  原因是 `flock` 綁在「開啟檔案的那個敘述」上，不是綁在那個檔案路徑上。你一 close，鎖就立刻被釋放——所以它從來沒有生效過，只是一段看起來很專業的程式碼。

  **這是併發最典型的失敗模式：防禦看起來在那裡，實際上不在。**你在測試時幾乎不會發現，因為測試通常一次只跑一件事。只有當兩個行程真的同時進來，你才會知道那把鎖是假的。
</Callout>

### 06.3 三個詞分清楚

這三個詞常被混用，但它們回答的是不同問題：

| 詞 | 解決什麼 | 誰來管 |
| --- | --- | --- |
| **臨界區段**（critical section） | 哪一段程式碼不該同時被兩個執行緒執行 | **你**要畫出範圍 |
| **鎖**（lock） | 不讓別人同時進來 | 作業系統提供機制 |
| **交易**（transaction） | 一組操作要嘛全成功要嘛全不做 | 資料庫保證 |

<Callout type="important" title="為什麼上一節 SQLite 直接就解決了">
  `hold_the_lock.py` 沒有手寫任何鎖，它靠 `BEGIN EXCLUSIVE` 就擋住第二個 writer。那個 `BEGIN` 同時做了兩件事：畫出臨界區段，並且替你取得鎖。

  **這就是優先用資料庫的理由。**你手寫 `flock` 時要自己決定鎖哪裡、鎖多久、忘了釋放會怎樣；資料庫已經把這些規則收進去了。

  所以實務上的順序是：**先問「資料庫能不能幫我擋」，可以就用資料庫；只有在它擋不住的時候（例如兩個行程各自快取了一份資料）才自己加鎖。**
</Callout>

## 07. Index：資料庫怎麼跳過大部分資料

到這裡你會寫 `SELECT ... WHERE`，但你從來不知道資料庫**實際上**做了什麼。它是從第一列讀到最後一列，還是直接跳到你要的那一列？

這兩件事在 5 萬列的差別是幾百倍。`indexes.py` 用一張 5 萬列的 `notes` 表把它量出來。

<Terminal title="bash — one author out of 50000 rows, no index" flavor="output">{`
$ python indexes.py plan
1. One author out of 50000 rows, no index
  author = 'user0042'
    plan : SCAN notes
    rows : 10
    time : 218 ms for 50 runs
`}</Terminal>

<Callout type="important" title="`SCAN` 的意思不是「查不到」，是「整張表都看過了」">
  你的條件是「作者是 `user0042`」，符合的只有 **10 列**。但 `SCAN` 這個字的意思是：資料庫從頭到尾讀了 50 000 列，每一列都檢查一次「這列的 author 是不是 `user0042`」，只有 10 列通過。

  **它繞了 50 000 圈，只為了拿出 10 筆。** 而且它很誠實地在 plan 裡寫出來了。
</Callout>

<Terminal title="bash — the same query, after CREATE INDEX" flavor="output">{`
$ python indexes.py index
2. The same query, after CREATE INDEX
  author = 'user0042'
    plan : SEARCH notes USING INDEX idx_notes_author (author=?)
    rows : 10
    time : 1 ms for 50 runs
   the primary key was already an index — that is why id was never slow:
  id = 42000
    plan : SEARCH notes USING INTEGER PRIMARY KEY (rowid=?)
    rows : 1
    time : 0 ms for 50 runs
`}</Terminal>

同一條查詢，**218 ms 變 1 ms**，而且回傳的資料一模一樣。差別只有一行：

```sql
CREATE INDEX idx_notes_author ON notes (author)
```

<Callout type="important" title="Index 沒有改變你的資料，也沒有改變你的結果">
  這是初學者最常搞錯的一件事。有人以為「有 index」跟「沒 index」是兩種資料。

  不是。`notes` 裡的 5 萬列，索引前後一模一樣。索引只是**另外抄一份排序過的清單**，讓資料庫知道要跳到哪一頁。

  所以刪掉 index 不會刪掉資料，只會讓查詢變慢。反過來，**有 index 也不等於查詢會快**——下面 07.3 會看到資料庫自己放棄使用它的情況。
</Callout>

### 07.1 你其實早就有一個 index 了

注意第二段：`SEARCH notes USING INTEGER PRIMARY KEY (rowid=?)`。

`id INTEGER PRIMARY KEY` 這行——第 03 節講型別約束的時候提到過——在 SQLite 裡不只是「不能重複」，它**就是 `rowid` 本身**，資料庫本來就把它排好序了。所以 `WHERE id = ?` 從來不需要你自己建索引。

<Callout type="note" title="所以在建 index 之前，先問一句：這張表的主鍵是什麼？">
  主鍵本來就有一個 index。這是最便宜的一次查詢最佳化，因為你不用做任何事。
</Callout>

### 07.2 讀 plan 那一行，不要靠猜

<Terminal title="bash — what the plan line actually tells you" flavor="output">{`
$ python indexes.py composite
3. Reading the plan line: it says exactly what happened
   both columns named, both usable:
  WHERE author = ? AND tag = ?
    plan : SEARCH notes USING INDEX idx_tag_author (tag=? AND author=?)
   same query, conditions written in the other order — no difference:
  WHERE tag = ? AND author = ?
    plan : SEARCH notes USING INDEX idx_tag_author (tag=? AND author=?)
   only the right-hand column named — SQLite still uses the index:
  WHERE author = ?
    plan : SEARCH notes USING INDEX idx_tag_author (ANY(tag) AND author=?)
   add the selected column to the index and the plan says COVERING:
  SELECT title WHERE author = ? AND tag = ?
    plan : SEARCH notes USING COVERING INDEX idx_cover (author=? AND tag=?)
   a pattern match on the front of a string is not the same as = :
  WHERE author LIKE 'user0042%'
    plan : SCAN notes
    rows : 10
    time : 329 ms for 50 runs
`}</Terminal>

四件事，全部直接寫在 plan 那一行裡：

**一、`WHERE` 裡條件的先後順序不影响資料庫。** 前兩段的 plan 完全一樣，雖然你寫的順序相反。資料庫會自己把條件排到跟索引一致的順序。

**二、索引的最左欄沒有被指定，它還是會被用。** 第三段出現 `ANY(tag)`——意思是「我不確定 tag 是哪一個，但我知道 author 一定是 `user0042`，所以我把 8 個 tag 各查一次」。這跟教科書上「最左欄必須出現」的說法不一樣，**SQLite 實際上就是這樣做的**。

**三、出現 `COVERING` 代表更快。** 第四段把 `title` 也放進索引，資料庫就完全不必回到資料表取資料。這叫「覆蓋索引」。

**四、`LIKE 'user0042%'` 不等於 `=`。** 資料庫一樣在比對 author，條件長得幾乎一樣，最後一段的 plan 卻從 `SEARCH` 掉回 `SCAN`：329 ms 對 1 ms。

<Callout type="warning" title="第四點為什麼會這樣，而修好它的代價不是零">
  SQLite 的 `LIKE` 預設**不分大小寫**。要它走索引，索引的排序必須跟「大小寫無關的相等」一致，所以要加上 `COLLATE NOCASE`：

  ```sql
  CREATE INDEX idx_nocase ON notes (author COLLATE NOCASE);
  ```

  實測之後，`LIKE 'user0042%'` 確實變成了 `SEARCH notes USING INDEX idx_nocase (author>? AND author<?)`。

  **但代價在這裡**：只留 `idx_nocase` 的時候，`WHERE author = ?` 反而退回 `SCAN notes`。

  <Terminal title="bash — the two indexes are not interchangeable" flavor="output">{`
  $ sqlite3 indexes.db "CREATE INDEX idx_nocase ON notes (author COLLATE NOCASE); ANALYZE;"
  $ sqlite3 indexes.db "EXPLAIN QUERY PLAN SELECT title FROM notes WHERE author = ?;"
  SCAN notes

  $ sqlite3 indexes.db "CREATE INDEX idx_author ON notes (author); ANALYZE;"
  $ sqlite3 indexes.db "EXPLAIN QUERY PLAN SELECT title FROM notes WHERE author = ?;"
  SEARCH notes USING INDEX idx_author (author=?)

  $ sqlite3 indexes.db "EXPLAIN QUERY PLAN SELECT title FROM notes WHERE author LIKE 'user0042%';"
  SEARCH notes USING INDEX idx_nocase (author>? AND author<?)
  `}</Terminal>

  兩個都要建：一個給 `=`，一個給 `LIKE '...%'`。**這正是為什麼規則是「去看 plan」而不是「記住哪種查詢要配哪種索引」**——只靠記憶的話，你很可能會蓋掉一個本來好好的索引。
</Callout>

<Callout type="important" title="所以「什麼時候該建 index」的答案不是背規則">
  規則是：**`WHERE`、`JOIN`、`ORDER BY` 裡出現的欄位，考慮建 index。**其餘的都可以先不管。

  然後**每一條查詢都看一次 plan**，確認它真的被用了。資料庫有權不聽你的——第 02 節就是例子：沒有索引時，`tag = 'sql'` 符合 6 250 列，佔全表的八分之一，那時候整表掃描就是對的選擇。
</Callout>

### 07.3 索引是有代價的

<Terminal title="bash — the same writer, with and without indexes" flavor="output">{`
$ python indexes.py cost
4. What an index costs the writer
    2000 inserts, no index   : 4 ms
    2000 inserts, 2 indexes : 9 ms
    the writer got 2.0x slower
    (median of 3 runs, one transaction, your numbers will differ)
`}</Terminal>

每一筆新資料進來，資料庫不只要把它寫進資料表，**還要把它插進每一個索引裡**——而索引必須維持排序，所以是插到正確位置，不是 append 到最後面。

<Callout type="important" title="讀取變快，寫入變慢。這是同一個決定的一體兩面">
  你每次加一個 index，都讓某些查詢變快，同時讓所有寫入變慢。

  所以 index 不是越多越好。它的判斷標準只有一句：**你已經量過這條查詢很慢，而且慢的那個 plan 不是 `SCAN notes`。**沒量過就別加。
</Callout>

### 07.4 沒人用的索引，是純粹的浪費

<Terminal title="bash — an index nobody can use" flavor="output">{`
$ python indexes.py unused
5. An index nobody queries
    file, before the index : 4.7 MB
    file, after it         : 8.1 MB
    indexes on notes now:
      idx_notes_body
    the one indexed column is body, and nothing here filters on it:
  WHERE author = ?
    plan : SCAN notes
    rows : 10
    time : 250 ms for 50 runs
    dropping it and compacting the file gives the space back:
    file, after DROP INDEX + VACUUM : 4.7 MB
`}</Terminal>

<Terminal title="sql — the one query that counts" flavor="output">{`
$ sqlite3 indexes.db "SELECT COUNT(*) FROM sqlite_master WHERE type = 'index';"
1
`}</Terminal>

檔案從 4.7 MB 變成 8.1 MB，這個索引**沒有讓任何一條查詢變快**，而上一節那個寫入代價照樣要付。

<Callout type="warning" title="`DROP INDEX` 之後檔案沒有立刻變小，這不是 bug">
  最後一行印出 4.7 MB，但那是因為還多跑了一個 `VACUUM`。`DROP INDEX` 只是把那些頁面標記成「空的，可以再用」，檔案不會自己縮。

  **這是資料庫裡少數你會親眼看到「空間還在，但別人拿不到」的情況。**
</Callout>

<Callout type="note" title="ANALYZE 做的事，和它不做的事">
  索引要靠統計資料才知道值的分佈。`ANALYZE` 會把估算寫進 `sqlite_stat1`：

  <Terminal title="bash — what ANALYZE recorded" flavor="output">{`
  $ sqlite3 indexes.db "ANALYZE;"
  $ sqlite3 indexes.db "SELECT * FROM sqlite_stat1;"
  notes|idx_author|50000 10
  notes|idx_nocase|50000 10
  `}</Terminal>

  `50000 10` 讀作：這張表約 5 萬列，每個不同的 `author` 約對應 10 列。這就是資料庫決定「掃描還是搜尋」的依據——第 07.2 節 `tag = 'sql'` 符合 6 250 列，佔全表八分之一，那時它算完覺得整表掃描比較划算。

  **注意 `sqlite_stat1` 記的是估計值，不是使用次數。**它不會告訴你「這個索引有沒有人用」。要看一條查詢實際怎麼跑，只有一個辦法：`EXPLAIN QUERY PLAN`。
</Callout>

## 08. Cache：你手上開始有兩份資料

第 07 節的索引已經是一份「抄本」了——只不過那一份是 SQLite 自己抄、自己維持，而且**永遠跟你的一致**。快取是同一個想法，只是抄本的管理變成你的工作。

<Terminal title="bash — the whole benefit, in one line" flavor="output">{`
$ python cache.py stale
1. A cache that never expires
  first read (cache miss)                        value=100  queries=1  (database says 100)
  second read (cache hit)                        value=100  queries=1  (database says 100)
   queries stopped at 1. That is the entire benefit of a cache.
   after the database changed to 200              value=100  queries=1  (database says 200)

   The caller got 100 from a database that says 200.
   queries is still 1, so nothing in the log shows the write happened.

   Unit 06 already showed a silent wrong answer: json_race.py returns a
   200 with data missing. A cache is the second source, and the two are
   worth telling apart:
     a race loses writes that were meant to happen
     a cache returns a value that was correct, and then stopped being so
`}</Terminal>

<Callout type="important" title="盯著 `value` 和 `queries` 這兩欄看">
  第三次讀取，回傳 `value=100`，而括號裡的 `database says 200` 是程式直接去資料庫查到的真相。

  **同一個程式裡，兩個數字不一樣。**而且 `queries` 還是 1 —— 沒有錯誤、沒有警告、沒有例外，**連 log 都不會記錄到那個 write**。讀取成功、回應 200、數字是舊的。

  這是快取最難查的一類問題：**它不告訴你，只給你一個錯的答案。**
</Callout>

### 08.1 TTL 限制的是「錯多久」，不是「會不會錯」

最常見的直覺做法是給每筆資料加一個到期時間。這個 TTL 有用，但它的作用跟你想的不一樣。

<Terminal title="bash — a 30 second TTL" flavor="output">{`
$ python cache.py ttl
2. A cache with an expiry
   TTL is 30 seconds. t is in seconds since the server started.
  t=0  first read                                value=100  queries=1
  t=10 read again                                value=100  queries=1
   the database changed to 200, and nobody told the cache
  t=20 still inside the TTL                      value=100  queries=1  (database says 200, stale)
  t=40 TTL has passed                            value=200  queries=2  (database says 200, correct)

   A TTL does not make the cache correct. It bounds how wrong it can be.
`}</Terminal>

看 `t=20` 那一次，TTL 明明還沒到：它是**錯的**，而且沒有任何機制會告訴你它錯了。`t=40` 之所以正確，只是因為它恰好過期了。

<Callout type="important" title="所以要決定的是：可以忍受不對多久">
  - 顯示商品價格：錯 30 秒通常沒關係 → 給 TTL。
  - 顯示轉帳餘額：錯 30 秒就是資安問題 → **不能只靠 TTL。**

  這是政策決定，不是技術決定。**先決定你能忍受多久不對，再去選機制**，而不是先加一個 TTL 再想它夠不夠。
</Callout>

### 08.2 寫入時清掉

<Terminal title="bash — invalidation on write" flavor="output">{`
$ python cache.py invalidate
3. Invalidate on write
  after two reads: queries=1
  after a write that cleared the cache: value=200 queries=2

   The rule is simple and it is easy to forget:
     every write path must clear, or the next reader gets the old value.
   One UPDATE statement that forgets is enough to ship a wrong number.
`}</Terminal>

把規則寫出來很簡單，簡單到不像工程：**每一條寫入路徑都要清快取**，不管那個寫入是使用者按的、TTL 觸發的，還是腳本跑的。

問題在於「每一條」。第 04 節的 `PUT` 和 `PATCH` 是兩條，第 07 節的遷移腳本是第三條，後臺工作、資料修正、第三方匯入，每一個都是一條。**少清一條，就是一個會上線的錯誤數字。**

<Callout type="warning" title="這就是 cache invalidation 為什麼出了名地難">
  新增快取本身很簡單——一個 dict，兩行 code。難的是**你必須窮舉所有寫入路徑，而且不能漏**。

  漏掉的時候不會有任何症狀，只會在有人真的去比對數字的時候才發現。這是這門課裡少數「寫錯了也不會壞掉」的主題。
</Callout>

### 08.3 一個行程裡的快取，不是一個快取

這一節是最後一塊拼圖，也是最容易被忽略的：`worker`。兩個 worker，兩份快取。

<Terminal title="bash — two workers, two caches" flavor="output">{`
$ python cache.py workers
4. Two workers, two caches
  worker A read: queries=1, value=100
  worker B read after the write: value=200
  worker A read again:            value=100

   database says 200
   worker B is correct. worker A is not, and it will stay wrong
   until its own entry expires or that worker handles a write.

   A cache inside the process is not one cache. It is one cache per worker,
   and invalidation only ever reaches the worker that performed the write.
`}</Terminal>

**worker B 正確，worker A 不正確，而 A 會一直錯下去。**

<Callout type="important" title="這是單元 16 與 17 的伏筆">
  你現在用 `fastapi dev` 跑，只有一個行程，所以第 08.2 節那種寫法「看起來沒問題」。

  部署之後會用多個 worker（第 16、17 單元）。**那時一份行程內的快取變成 N 份**，而「寫入時清掉」只清得到剛才那一份。

  所以正確的順序是：**先假設你有多個行程來設計。**要嘛把快取放在行程外面（Redis 這類，所有行程共用一份），要嘛接受它不一致，並且明確決定哪些資料可以不一致。
</Callout>

<Callout type="note" title="那什麼時候不該用快取">
  問自己：**這份資料被改變之後，讓讀取者看到舊值，會產生問題嗎？**

  - 會（價格、餘額、權限）→ 不要用行程內快取，或者 TTL 要短到可以接受。
  - 不會（商品說明、圖片路徑、幾乎不改的設定）→ 快取很好用，而且 TTL 可以給很長。

  **先量過再說。**第 07 節那個 `218 ms 對 1 ms` 給了 217 倍的空間，值得那份複雜度。第 08.1 節第一次讀取 `queries=1`——如果本來就只要 1 次查詢，快取連賺都沒賺到。
</Callout>

## 09. Migration：改資料庫的順序

前三節都在改變「怎麼讀資料」，資料本身一直沒動。這一節要動結構了——而且動的是**已經有真實資料在裡面**的那個結構。

<Callout type="important" title="Migration 和 `CREATE TABLE` 差在哪">
  `CREATE TABLE` 是你在空地上蓋房子。**Migration 是在已經有人住的房子裡施工**，而且住戶還在裡面走動。

  差別在於：`CREATE TABLE` 失敗了就是沒蓋成，沒有後果。Migration 失敗了，可能已經改了一半。
</Callout>

### 09.1 Runner 就是一份編號清單加一本帳

`migrations.py` 示範一個最小的 runner：每一步有個編號，跑完就把編號記進資料庫。

<Terminal title="bash — applying nine steps" flavor="output">{`
$ python migrations.py runner
1. A migration runner is just a numbered list and a ledger
  applied 0001
    users columns: ['name', 'role']

  applied 0004
    users columns: ['name', 'role', 'email']
    row: ('iris', 'student', None)
    row: ('root', 'admin', None)

  applied 0005
    users columns: ['name', 'role', 'email']
    row: ('iris', 'student', 'iris@example.test')
    row: ('root', 'admin', 'root@example.test')
`}</Terminal>

<Callout type="note" title="0004 和 0005 是兩步，不是一步，這個安排是刻意的">
  `0004` 先加一個可以存 `NULL` 的欄位，所以既有的兩列都變成 `None`。

  `0005` 才把值補回去。

  **為什麼要分兩次？**因為如果合併成一步「加一個 NOT NULL 欄位並且填好」，你就必須在同一個動作裡同時改結構和改資料——中途失敗會留下半完成的狀態。拆開之後，`0004` 失敗了資料還在，`0005` 失敗了也只是沒補完，兩種都可以重跑。
</Callout>

這份帳本（ledger）就是 runner 真正在做的事：

<Terminal title="bash — running it a second time" flavor="output">{`
  ledger: ['0001', '0002', '0003', '0004', '0005', '0006', '0007', '0008', '0009']

  Run it again and nothing happens:
  every version was already in the ledger, so every step was skipped

  The ledger is the whole point. Without it you cannot tell which
  migrations ran, and re-running INSERT would duplicate rows.
`}</Terminal>

<Callout type="important" title="帳本讓「重跑」變成安全的事">
  沒有帳本的話，你第二次執行 runner 會再做一次 `INSERT`，資料變兩倍。有了帳本，runner 就變成**冪等**的——跑幾次結果都一樣。

  這也是為什麼 migration 的編號要進 Git：**它是程式碼，要跟著部署走。**記在某個人的筆記裡等於沒有記。
</Callout>

### 09.2 SQLite 拒絕幫你做三件事

<Terminal title="bash — what SQLite will not do" flavor="output">{`
$ python migrations.py limits
2. Three things SQLite will not do
  change a column's type: refused
    OperationalError: near "TYPE": syntax error
  add a NOT NULL column with no default: refused
    OperationalError: Cannot add a NOT NULL column with default value NULL

  The same column WITH a default is accepted:
    age exists, every row has 0
    users columns: ['name', 'role', 'age']
    row: ('iris', 'student', 0)
`}</Terminal>

<Callout type="warning" title="第二個錯誤是整個資料庫設計的核心問題">
  `Cannot add a NOT NULL column with default value NULL`

  翻譯：**新欄位要說每一列舊資料的值，但舊資料不知道自己該是什麼。**

  SQLite 拒絕是對的，因為它沒有辦法猜。`iris` 的 `age` 該是 0、18、還是 `NULL`？這是**你的業務決定，不是資料庫的決定**。

  這也是上一節 `0004` 為什麼要分兩步：先用可空的欄位佔位，再補值，最後才收緊成 `NOT NULL`。
</Callout>

<Callout type="note" title="它能做、你以為它不能做的事">
  SQLite 3.25 之後支援 `RENAME COLUMN`，3.35 之後支援 `DROP COLUMN`——這兩個在舊版本是做不到的。

  **但它從頭到尾沒有 `ALTER COLUMN`。**改欄位型別、幫既有欄位加約束、改欄位名稱以外的任何事，都要靠下一節那條路。
</Callout>

### 09.3 換欄位型別，唯一不丟資料的做法

這三個拒絕記下來之後，先看一個真實的改欄位需求：`role` 存文字不好用，要改成 `role_id INTEGER`。SQLite 沒有 `ALTER COLUMN`，所以答案不在「怎麼改」而在「繞開」。

答案是**不要改欄位**。另外建一個新形狀，把資料轉過去，再把舊的刪掉。

<Terminal title="bash — the order, with both tables visible at every step" flavor="output">{`
$ python migrations.py expand
3. Changing a column, without losing data
    before
    users columns: ['name', 'role']
    row: ('iris', 'student')
    row: ('root', 'admin')
    row: ('ada', 'student')

    expand: the new table exists, the old one is untouched
    users columns: ['name', 'role']

    and the new one starts empty
    users_new columns: ['name', 'role_id']

    backfill: rows copied and converted, nothing dropped yet
    users_new columns: ['name', 'role_id']
    row: ('iris', 0)
    row: ('root', 1)
    row: ('ada', 0)

    reads can switch to users_new here, while users is still intact
    if this release breaks, roll back by pointing reads at users again

    contract: the old table is gone
    users: does not exist

    and the new one is still complete
    users_new columns: ['name', 'role_id']
    row: ('iris', 0)
    row: ('root', 1)
    row: ('ada', 0)

    final shape
    users columns: ['name', 'role_id']
    row: ('iris', 0)
    row: ('root', 1)
    row: ('ada', 0)

  Three rows in, three rows out. The old column went away with a DROP,
  and by then nothing was reading it.
`}</Terminal>

<Callout type="important" title="expand → backfill → contract，中間隔著一次部署">
  這個順序最重要的不是四行 SQL，是**中間那個部署**。

  1. **expand**：加上新欄位或新表，舊的完全不動。**這個版本可以安全部署**，因為沒有東西被破壞。
  2. **backfill**：把資料搬過去。這可以是一個 migration，也可以是一段背景作業。
  3. **部署一次**，讓程式改讀新欄位。**舊欄位還在**，所以出問題時改回去就好。
  4. **contract**：確認沒有人讀舊的了，才 `DROP`。

  <Callout type="warning" title="第 3 步和第 4 步之間，必須真的隔一段時間">
    如果你把四個動作放在同一次部署裡，expand 的保護就等於不存在——舊表在你確認新程式運作正常之前就已經被刪了。

    **「確認沒有人在讀」需要時間，而時間是唯一的證據。**這也是為什麼大型系統的 migration 有時會跨好幾個禮拜。
  </Callout>
</Callout>

### 09.4 在你的機器上 0.1 秒，在正式環境可能是幾分鐘

<Callout type="important" title="這是本節唯一真正會造成 production 事故的規則">
  你在這台 Mac 上跑 `ALTER TABLE` 只需要幾毫秒，因為資料只有兩三列。

  正式環境的資料表可能有幾千萬列。`ADD COLUMN` 在很多資料庫上是**便宜的**（只改結構描述），但**`CREATE INDEX` 要重寫整張表**——第 07 節那個 50 000 列的表建索引要幾秒，幾千萬列就是幾十分鐘，而那段時間裡那張表可能整個被鎖住。

  <Callout type="warning" title="所以有兩件事必須在寫 migration 之前想">
    1. **這個動作在正式環境要跑多久？**如果答案需要估算，去找有幾百萬列的測試環境實測，不要用本機的時間推估。
    2. **跑的時候，那張表還能被讀寫嗎？**如果不能，你就是在讓整個服務停機。

    這兩個問題的答案決定了你能不能在維護時段做，還是必須改用「在線新增索引」那種工具——而那些工具在 SQLite 上不存在，因為 SQLite 本身就是一個檔案。
  </Callout>
</Callout>

<Callout type="note" title="這一課的取捨，你現在應該能自己說出來了">
  第 08 節的快取和第 07 節的索引，都是在**讀**的路上加東西。Migration 是在**寫**的路上動東西。

  三者的風險剛好是遞增的：索引弄錯了查詢變慢，快取弄錯了資料不準，**migration 弄錯了資料沒了。**

  所以 migration 是這三個裡面最需要慢下來的一個，而它最需要的東西也一樣：**先量，再改。**
</Callout>

## 10. 什麼時候該用哪一種

這一課不需要你背規則。只需要問三個問題：

| 你在做的事 | 用哪一種 | 為什麼 |
| --- | --- | --- |
| 暫存資料、測試用、單一使用者 | `dict` | 行程結束就丟，正好是你要的 |
| 設定檔、要進 Git 的資料、人工要能讀能改 | 文字檔 | `git diff` 看得懂，人手改得動 |
| 會被讀寫的資料、多個程式會同時動它 | SQLite | 規則跟資料同住，並發時會拒絕你 |
| 同一份資料被重複讀取很多次、而且可以忍受短暫不對 | 快取 | 用記憶體換時間，代價是第 08 節那些一致性問題 |

**判斷的關鍵不是資料量，是「會不會有別的程式同時寫」。** 單機、單一行程的筆記本工具，文字檔完全夠用，強迫自己上資料庫只會增加複雜度。反過來，一旦有第二個執行緒或第二個程式會動同一份資料，文字檔的安靜失敗就變成你必須處理的問題。

真實系統還有第三層：一個跑在別台機器上的伺服器（PostgreSQL、MySQL），行為規則跟 SQLite 相同，但多了網路與權限。單元 08 會先讓你在本機的 SQLite 上把規則與交易看清楚，再談放到網路上。

<Callout type="note" title="這門課用的是 Python 內建的 sqlite3">
  `import sqlite3` 就有了，不需要安裝任何東西，也不需要啟動一個資料庫伺服器。它是一個函式庫，直接操作一個檔案。這是它最適合課堂練習的原因。
</Callout>

## 11. 終端實戰驗證：三次對照

上面每一節的結論都要自己重跑一次才會記住。三種存法、三組對照，全部在 `exercises/05-persistence/` 執行，先清掉舊檔案讓結果乾淨：

<Terminal title="bash — clean start">{`
cd exercises/05-persistence
rm -f users.json notes.db
`}</Terminal>

### 第一步：dict 活不過執行

<Terminal title="bash — step 1" flavor="output">{`
$ python store.py dict-add
added carol to a dict, held by this process only
$ python store.py dict-list
dict sees: ['alice']
`}</Terminal>

`carol` 不在裡面。ls 也證明它沒留下檔案。

### 第二步：文字檔活著，而且你看得懂

<Terminal title="bash — step 2">{`
$ python store.py json-add && python store.py json-list
$ ls -l users.json
$ cat users.json
`}</Terminal>

`carol` 在裡面，而且檔案是純文字。

### 第三步：SQLite 活著，而且檔案裡有規則

<Terminal title="bash — step 3">{`
$ python store.py sqlite-add && python store.py sqlite-list
$ ls -l notes.db
$ file notes.db
$ python store.py sqlite-schema
`}</Terminal>

`CREATE TABLE notes (id INTEGER PRIMARY KEY, text TEXT NOT NULL)` 這行是從檔案裡讀出來的。

### 第四步：把兩個 writer 的結果比一比

<Terminal title="bash — step 4, text file">{`
$ rm -f users.json
$ python store.py json-add
$ python json_race.py A & python json_race.py B & wait
$ cat users.json
`}</Terminal>

對照第 02 節那個安靜的失敗：文字檔這邊兩邊都說寫好了，其中一筆不見了。

<Terminal title="bash — step 4, SQLite">{`
$ python hold_the_lock.py hold &
$ python hold_the_lock.py write
$ sqlite3 notes.db "SELECT id, text FROM notes;"
`}</Terminal>

writer B 被拒絕，而資料庫裡沒有任何一筆是缺的。

### 第五步：把「同時」跑三次

第四步是資料庫擋下來的情形。現在換成沒有資料庫保護的三種寫法，看同一件事怎麼壞掉。

<Terminal title="bash — step 5, three ways to lose data">{`
$ rm -f race.json race.lock
$ python race_fix.py naive A & python race_fix.py naive B & wait
$ cat race.json
{"A": {"at": 1790996440.988849}}

$ rm -f race.json race.lock
$ python race_fix.py counting A & python race_fix.py counting B & wait
$ cat race.json
{"count": 1, "A": {"at": 1790996442.054744}}

$ rm -f race.json race.lock
$ python race_fix.py locked A & python race_fix.py locked B & wait
$ cat race.json
{"A": {"at": 1790996459.28441}, "B": {"at": 1790996460.289021}}
`}</Terminal>

這三種寫法唯一的差別是有沒有保護，但結果完全不同：**第一次遺失一個 key、第二次加兩次只得到 1、第三次兩個都在。**這就是第 06 節的整個重點。

### 第六步：看資料庫怎麼讀

第五步是兩個程式搶同一個檔案。現在換一個方向：不搶，讓資料庫做同一件事，只是做得更聰明。

<Terminal title="bash — step 6, the same query twice">{`
$ rm -f indexes.db
$ python indexes.py plan
  author = 'user0042'
    plan : SCAN notes
    rows : 10
    time : 218 ms for 50 runs

$ python indexes.py index
  author = 'user0042'
    plan : SEARCH notes USING INDEX idx_notes_author (author=?)
    rows : 10
    time : 1 ms for 50 runs
`}</Terminal>

**回傳的資料一模一樣，差的是 `SCAN` 變成 `SEARCH`。** 這就是索引的全部意義。

### 第七步：讓自己手上多一份資料

第六步是讓資料庫少讀一點。第七步反過來，是讓**應用程式**少查一點——而這一步會產生一個新的問題。

<Terminal title="bash — step 7, the cache goes stale" flavor="output">{`
$ python cache.py stale
  first read (cache miss)                        value=100  queries=1  (database says 100)
  second read (cache hit)                        value=100  queries=1  (database says 100)
   after the database changed to 200              value=100  queries=1  (database says 200)
`}</Terminal>

**第三次那行的 `value` 和括號裡的數字不一樣。**這個問題就是快取的全部代價，而結構改錯的後果比它更重。

### 第八步：改結構，而不是改資料

第七步是資料本身不對。第八步換成比較嚴重的情況：**結構要變，而資料已經在裡面了。**

<Terminal title="bash — step 8, the runner and its ledger" flavor="output">{`
$ python migrations.py runner
  applied 0004
    users columns: ['name', 'role', 'email']
    row: ('iris', 'student', None)
  applied 0005
    users columns: ['name', 'role', 'email']
    row: ('iris', 'student', 'iris@example.test')
`}</Terminal>

<Terminal title="bash — step 8, retyped without losing a row" flavor="output">{`
$ python migrations.py expand
    before
    users columns: ['name', 'role']
    row: ('iris', 'student')
    row: ('root', 'admin')
    row: ('ada', 'student')

    final shape
    users columns: ['name', 'role_id']
    row: ('iris', 0)
    row: ('root', 1)
    row: ('ada', 0)
`}</Terminal>

`users` 三列進、`users_new` 三列出。**資料沒有少，舊的結構也還沒被碰。**中間每一個狀態下那張舊表都在——這就是 expand 的全部意義。
