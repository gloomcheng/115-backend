公司已經有一台 VPS。你在裡面啟動 FastAPI，自己也看得到 `{"ok":true}`。但同事在她的電腦輸入同一個網址，畫面只顯示無法連線。

這一課要做到的結果很具體。在**自己的電腦**執行：

<Terminal title="bash — final result">{`
curl -i https://api.example.com/health
`}</Terminal>

最後要看到：

<Terminal title="HTTP — final response" flavor="output">{`
HTTP/2 200
content-type: application/json

{"ok":true}
`}</Terminal>

`api.example.com` 是範例。你會把它換成公司的真實網域。HTTP 版本也可能顯示 `HTTP/1.1`；這不影響這次驗收。

<Callout type="note" title="這一課先固定一條路線">
  以下步驟使用 Ubuntu 24.04 或 26.04 LTS、單台 VPS、單一 FastAPI container 與一個可管理 DNS 的網域。這條路線適合課程專題、內部工具與低流量服務。多台主機、零停機、異地容災與資料庫復原不在這一課處理。
</Callout>

## 01. 先分清兩台電腦

在那之前先說清楚「伺服器」是什麼。**它不是某一種特別的機器：只要一個程式正在等 Request、收到後回 Response，這個程式此刻就是伺服器。**

例如你在筆電上執行 `fastapi dev main.py`，FastAPI 等著 `curl` 來問它。這時：

- `curl` 是 Client，因為它主動送 Request。
- FastAPI 是 Server，因為它等 Request，再回 Response。

兩個程式就算都在同一台筆電，角色也沒變。

VPS 是一台放在網路上、可以長時間運作的遠端電腦。這一課會在同一台 VPS 上跑兩個伺服器程式：

- Nginx 在公開網路上等同事的 Request。
- FastAPI 只在 VPS 裡等 Nginx 轉交的 Request。

這一課會一直在兩個 Terminal 之間切換：

- **自己的電腦**：你正在使用的 Mac、Windows WSL 或 Linux。它負責登入 VPS，也扮演最後驗收的 Client。
- **VPS**：向業者租用、放在網路上的 Linux 電腦。FastAPI 與 Nginx 會在這台電腦執行。

每個指令區塊的標題都會寫明要用哪一台。如果你不確定自己在哪裡，先打：

<Terminal title="bash — either computer">{`
hostname
whoami
pwd
`}</Terminal>

這張圖只證明一件事：外部 Request 只直接連到 Nginx；FastAPI 的 `8000` port 留在 VPS 裡面。

<img src={withBase('/images/lessons/17/vps-public-entry.webp')} alt="ELI5 VPS 公開入口示意圖：外部 Client 以 HTTPS 443 連到 Nginx，Nginx 再透過 VPS 內部的 127.0.0.1:8000 轉交給 FastAPI，外部直連 8000 被阻擋。" width="1672" height="941" loading="lazy" decoding="async" />

先記住三個位置：

- Nginx 在 `443` 等外部 Request。
- FastAPI 在 `127.0.0.1:8000` 等 VPS 內部 Request。
- `127.0.0.1` 永遠是「當前這台電腦」。在 VPS 上指 VPS；在同事的筆電上，就指她的筆電。

## 02. 先拿到三個真實值

打開 VPS 業者與網域的管理畫面，找到：

1. **VPS public IP**：這台電腦在網路上的數字位址。
2. **SSH 使用者名稱**：業者告訴你用哪個帳號登入。Ubuntu cloud image 常見是 `ubuntu`，但不是每家都一樣。
3. **網域**：同事最後會輸入的名稱，例如 `api.example.com`。

在**自己的電腦**把它們存成 shell 變數：

<Terminal title="bash — your computer">{`
export SERVER_IP='203.0.113.10'
export SSH_USER='ubuntu'
export DOMAIN='api.example.com'

printf 'server=%s\nuser=%s\ndomain=%s\n' "$SERVER_IP" "$SSH_USER" "$DOMAIN"
`}</Terminal>

`203.0.113.10` 與 `api.example.com` 是專供文件舉例的保留值，不會連到你的 VPS。

<Callout type="warning" title="先停下來換值">
  如果 <code>printf</code> 還顯示 <code>203.0.113.10</code> 或 <code>api.example.com</code>，不要繼續。先把它們換成業者與公司實際提供的值。
</Callout>

### 讓網域指向 VPS

在 DNS 管理畫面新增一筆：

| Type | Name | Value |
| --- | --- | --- |
| `A` | `api` | VPS public IP |

在 DNS 設定中，`A` record 的意思就是：當有人查 `api.example.com`，回答這台 VPS 的 IPv4。如果你用的是根網域，`Name` 常寫成 `@`。

這條 DNS record 更新可能不會立刻到達每個 resolver。先把它設好，等待的時間可以繼續在主機上安裝設定。

### 在業者畫面開三個入口

主機上的 Port 可以先理解成一個有編號的網路入口。這一課只用到四個號碼：

| Port | 誰會用 | 是否對外開放 |
| --- | --- | --- |
| `22` | 你用 SSH 管理 VPS | 開，來源限制為公司或你當前的 public IP |
| `80` | Nginx 接 HTTP | 開 |
| `443` | Nginx 接 HTTPS | 開 |
| `8000` | Nginx 在 VPS 內連 FastAPI | **不開** |

業者的畫面可能叫 Firewall、Security Group 或 Inbound Rules。新增 TCP `22`、`80`、`443`，不要新增 `8000`。`22` 的 Source 如果有 `My IP` 選項，先選它；`80` 與 `443` 才允許公開網路連入。

<Callout type="note" title="IPv6 先不開">
  這一課先使用 IPv4。在 VPS 與防火牆尚未設好 IPv6 前，不要新增 DNS <code>AAAA</code> record。
</Callout>

## 03. 先確定你能進入 VPS

在**自己的電腦**執行：

<Terminal title="bash — your computer">{`
ssh "$SSH_USER@$SERVER_IP"
`}</Terminal>

第一次連線會詢問是否信任這台主機。把 Terminal 顯示的 fingerprint 與 VPS 業者提供的指紋比對。對得上才輸入 `yes`。

登入後，這個 Terminal 已經在 **VPS** 裡。先確認：

<Terminal title="Ubuntu — VPS">{`
hostname
cat /etc/os-release
whoami
`}</Terminal>

`/etc/os-release` 應顯示 Ubuntu 24.04 或 26.04。使用者也必須能執行 `sudo`。接著安裝這一課會用的工具：

<Terminal title="Ubuntu — VPS">{`
sudo apt update
sudo apt upgrade -y
sudo apt install -y ca-certificates curl git nginx ufw
`}</Terminal>

VPS 業者的防火牆是第一層。UFW 是 Ubuntu 這台主機自己的第二層。先允許 SSH，再啟用 UFW：

<Terminal title="Ubuntu — VPS">{`
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status numbered
`}</Terminal>

應該看到 `22/tcp`、`80/tcp`、`443/tcp` 是 `ALLOW`，清單中沒有 `8000`。

不要關現在的 SSH。在**自己的電腦**另開一個 Terminal，重新執行：

<Terminal title="bash — second terminal">{`
ssh "$SSH_USER@$SERVER_IP"
`}</Terminal>

第二條 SSH 也能登入，才關閉其中一個。

## 04. 先讓 FastAPI 只在 VPS 裡回答

確認 SSH 連線安全無虞後，接著在主機安裝 Docker。Docker 負責把應用程式與它需要的軟體一起啟動。這一課不要自行寫 Dockerfile，直接部署 repository 裡已驗證的範例。

在 **VPS** 加入 Docker 官方 apt repository：

<Terminal title="Ubuntu — VPS">{`
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "\${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
`}</Terminal>

先確認 Docker 真的能執行 container：

<Terminal title="Ubuntu — VPS">{`
sudo systemctl status docker --no-pager
sudo docker run --rm hello-world
sudo docker compose version
`}</Terminal>

`hello-world` 必須印出成功訊息。如果失敗，先停在這裡處理 Docker，不要繼續設 Nginx。

抓取課程 API，先跑 tests，再啟動：

<Terminal title="Ubuntu — VPS">{`
git clone https://github.com/gloomcheng/115-backend.git
cd 115-backend/examples/http-api
sudo docker compose run --rm --build test
sudo docker compose up -d --build
sudo docker compose ps
`}</Terminal>

測試應顯示 `4 passed`。`docker compose ps` 的 `api` 應是 `running`，健康檢查完成後會顯示 `healthy`。

現在還在 **VPS**。直接問 FastAPI：

<Terminal title="Ubuntu — VPS">{`
curl -i http://127.0.0.1:8000/health
sudo ss -ltnp | grep ':8000'
`}</Terminal>

應該看到：

<Terminal title="HTTP — VPS only" flavor="output">{`
HTTP/1.1 200 OK
content-type: application/json

{"ok":true}

LISTEN ... 127.0.0.1:8000 ...
`}</Terminal>

`127.0.0.1:8000` 表示這個入口只綁在 VPS 本機。回到**自己的電腦**做一次反向檢查：

<Terminal title="bash — your computer">{`
curl --connect-timeout 3 "http://$SERVER_IP:8000/health"
`}</Terminal>

這次應該失敗。這不是 bug，而是「外部不能繞過 Nginx 直接連 FastAPI」的證據。

<Callout type="important" title="Docker port 不能只靠 UFW 擋">
  Docker published port 可能繞過 UFW。範例的 Compose 明確使用 <code>127.0.0.1:8000:8000</code>，不是 <code>8000:8000</code>。這個綁定才是 FastAPI 不直接公開的關鍵證據。
</Callout>

## 05. 再讓 Nginx 接住公開 Request

現在 FastAPI 只會在 VPS 裡回答。Nginx 的工作是在公開 port 接到 Request，再轉交給 `127.0.0.1:8000`。這種「先接到，再轉交」的程式叫 reverse proxy。

回到 **VPS** 的 Terminal。先重新設定真實網域；自己電腦上的 shell 變數不會自動帶進 SSH：

<Terminal title="Ubuntu — VPS">{`
export DOMAIN='api.example.com'
printf 'domain=%s\n' "$DOMAIN"
`}</Terminal>

確認已換成真實網域後，產生 Nginx 設定：

<Terminal title="Ubuntu — VPS">{`
cd ~/115-backend/examples/http-api
sed "s/api\\.example\\.com/$DOMAIN/g" deploy/nginx/backend-api.conf \\
  | sudo tee /etc/nginx/sites-available/backend-api > /dev/null

sudo ln -sfn /etc/nginx/sites-available/backend-api /etc/nginx/sites-enabled/backend-api
sudo nginx -t
sudo systemctl reload nginx
`}</Terminal>

`nginx -t` 必須顯示 `syntax is ok` 與 `test is successful`。這項檢查通過後才 reload，不要帶著錯誤設定繼續做 HTTPS。

這份設定的核心是：

<Terminal title="Nginx — the handoff" flavor="output">{`
location / {
    proxy_pass http://127.0.0.1:8000;
}
`}</Terminal>

`location /` 接住這個網域的 path。`proxy_pass` 把同一個 path 轉交給 FastAPI。

在**自己的電腦**先直接指定 VPS IP，不等 DNS：

<Terminal title="bash — your computer">{`
curl -i --resolve "$DOMAIN:80:$SERVER_IP" "http://$DOMAIN/health"
`}</Terminal>

這條指令只替這一次 `curl` 指定「這個網域要去這個 IP」。它不修改系統 DNS。看到 `200` 與 `{"ok":true}`，代表業者防火牆、UFW、Nginx、FastAPI 已連成一條路。

現在查真實 DNS：

<Terminal title="bash — your computer">{`
dig +short A "$DOMAIN"
printf 'expected=%s\n' "$SERVER_IP"
`}</Terminal>

兩個 IP 相同後，不加 `--resolve` 再發出一次 HTTP 請求驗證：

<Terminal title="bash — your computer">{`
curl -i "http://$DOMAIN/health"
`}</Terminal>

## 06. 最後把 HTTP 換成 HTTPS

確認上述 HTTP 請求能正常回應後，接著處理傳輸加密。HTTP 上的內容是明文。HTTPS 會加密 Client 到 Nginx 這一段連線，並用憑證讓 Client 檢查自己連的是哪個網域。

Certbot 會向 Let’s Encrypt 取得憑證，並修改 Nginx 設定。在 **VPS** 執行：

<Terminal title="Ubuntu — VPS">{`
sudo snap install --classic certbot
sudo test -e /usr/local/bin/certbot || sudo ln -s /snap/bin/certbot /usr/local/bin/certbot
sudo certbot --nginx -d "$DOMAIN"
`}</Terminal>

Certbot 會詢問 email、服務條款，以及是否把 HTTP 轉向 HTTPS。這一課選 redirect，讓 `http://` 自動轉到 `https://`。

驗證憑證未來能自動更新：

<Terminal title="Ubuntu — VPS">{`
sudo certbot renew --dry-run
sudo nginx -t
sudo systemctl status nginx --no-pager
`}</Terminal>

回到**自己的電腦**。這是第一次完整驗收：

<Terminal title="bash — your computer">{`
curl -I "http://$DOMAIN/health"
curl -v "https://$DOMAIN/health"
curl -sS "https://$DOMAIN/request-info"
`}</Terminal>

三個結果要一起看：

1. HTTP 回 `3xx`，`Location` 指向 `https://`。
2. HTTPS 沒有憑證錯誤，Status Code 是 `200`，Body 是 `{"ok":true}`。
3. `/request-info` 的 `scheme` 是 `https`，`host` 是你的網域。

最後用瀏覽器開 `https://你的網域/docs`。瀏覽器送 Request，Nginx 處理 HTTPS，FastAPI 回傳 API 文件，瀏覽器才把 Response Body 畫成頁面。

<Callout type="important" title="FastAPI 為什麼相信 Nginx">
  範例使用 <code>--forwarded-allow-ips=*</code> 讀取 Nginx 加入的 <code>X-Forwarded-*</code> Header。這只在 FastAPI 的 <code>8000</code> 綁定 <code>127.0.0.1</code>、外部無法繞過 Nginx 直連時成立。如果你把 <code>8000</code> 開到公開網路，這個信任邊界就不存在。
</Callout>

## 07. 沒有成功時，只查停住的那一關

先看**自己的電腦**收到哪一種結果：

| 畫面上看到的字 | Request 停在哪裡 | 下一條檢查 |
| --- | --- | --- |
| `Could not resolve host` | 還沒找到 VPS IP | `dig +short A "$DOMAIN"` |
| `Connection timed out` | 業者防火牆、UFW 或 Nginx 沒接到 | `sudo ufw status` 與 `sudo ss -ltnp` |
| `502 Bad Gateway` | Nginx 已接到，但 FastAPI 沒回答 | `sudo docker compose ps` |
| `500 Internal Server Error` | FastAPI 已接到，但 route 執行失敗 | `sudo docker compose logs --tail=100 api` |
| Certbot 驗證失敗 | Let’s Encrypt 無法透過 DNS 與 port `80` 找到 Nginx | 重做第 02 與第 05 節 |

在 **VPS** 收集完整證據：

<Terminal title="Ubuntu — VPS">{`
sudo ss -ltnp | grep -E ':(22|80|443|8000)\\b'
sudo nginx -t
sudo journalctl -u nginx -n 50 --no-pager
cd ~/115-backend/examples/http-api
sudo docker compose ps
sudo docker compose logs --tail=100 api
curl -i http://127.0.0.1:8000/health
`}</Terminal>

從最外層開始：DNS → firewall → Nginx → FastAPI。哪一關沒有預期證據，就只修那一關。不要一次改四個地方，也不要重安裝整台 VPS。

## 08. 公開成功後，把檢查變成門禁

手動 `curl` 證明這一次有通。它不會在下一次改**程式碼**時自動再跑，也不會阻止密碼被**提交**。所以部署還需要四道自動檢查。

### Test 同時檢查 Status Code 與 Body

`examples/http-api/tests/test_main.py` 的最小**測試**是：

<Terminal title="Python — tests/test_main.py" flavor="output">{`
def test_health_returns_200_and_expected_body():
    response = client.get("/health")

    assert response.status_code == 200
    assert response.json() == {"ok": True}
`}</Terminal>

只檢查 Body 不夠。`200` 也是 API **契約**的一部分。範例還會測不存在的 user 是 `404`，以及 POST 建立後能再用 GET 讀回來。

在**開發電腦的 repository root** 執行：

<Terminal title="bash — your development computer">{`
npm run test:api
`}</Terminal>

預期是 `4 passed`。production image 不會收進 `pytest` 與 `tests/`。

### `.gitignore` 擋不住已經 staged 的密碼

`.gitignore` 只擋「還沒被加進索引的檔案」。一旦 `git add` 過，它就在索引裡了，刪掉檔案也不會從索引消失——所以要靠這個範例檔把流程走對。**要放進 repo 的只有沒有真實值的範例檔**：

<Terminal title="dotenv — safe template" flavor="output">{`
APP_ENV=production
DATABASE_URL=
APP_SECRET=
`}</Terminal>

真實**密碼**、API key、private key、database URL 與 Token 不能出現在程式碼、Compose 檔案、test fixture、截圖或 commit message。程式從環境讀取：

<Terminal title="Python — read from the environment" flavor="output">{`
import os

database_url = os.environ["DATABASE_URL"]
`}</Terminal>

每次 clone repository 後，啟用 commit 前檢查：

<Terminal title="bash — your development computer">{`
npm run setup:hooks
git config --get core.hooksPath
npm run test:security
npm run security:scan
`}</Terminal>

`core.hooksPath` 必須回 `.githooks`。`secret-harness.mjs` 會擋 `.env`、private-key file 與明文 credential pattern；Gitleaks 會再掃已知憑證格式與 Git history。GitHub Actions 會在 push 後重跑這些檢查。

<Callout type="warning" title="如果真實 secret 已經 commit 或 push">
  先到憑證發行端 revoke 或 rotate。下一個 commit 刪掉它，不會清除 Git history、fork、cache 與別人的 clone。需要重寫共用 history 時，由 repository 管理者協調，不要自行 force-push。
</Callout>

### 部署設定與真實網站各查一次

<Terminal title="bash — your development computer">{`
npm run check:deployment
npm run check:deployment -- \\
  --url="https://$DOMAIN" \\
  --expected-ip="$SERVER_IP"
`}</Terminal>

第一條檢查 Compose 是否只綁定 `127.0.0.1:8000`、runtime 是否以非 root 使用者執行，以及 Nginx 是否轉交到正確位址。第二條從外部檢查 DNS、HTTP redirect、HTTPS `200` 與 public `8000` 無法直連。

## 09. 下一次更新，仍然先驗收再交付

程式有新 commit 時，先在 **VPS** 確認沒有人手動改檔，再更新：

<Terminal title="Ubuntu — VPS">{`
cd ~/115-backend
git status --short
git pull --ff-only
cd examples/http-api
sudo docker compose run --rm --build test
sudo docker compose up -d --build
sudo docker compose ps
curl -f http://127.0.0.1:8000/health
`}</Terminal>

`git status --short` 有輸出就先停下來。VPS 裡沒有 commit 的程式修改，會讓你無法確定正在運行哪個版本。

回到**自己的電腦**：

<Terminal title="bash — your computer">{`
curl -f "https://$DOMAIN/health"
npm run check:deployment -- \\
  --url="https://$DOMAIN" \\
  --expected-ip="$SERVER_IP"
`}</Terminal>

`curl -f` 遇到 `4xx` 或 `5xx` 會回傳失敗。`{"ok":true}` 與 live deployment harness 都通過，這次更新才結束。

## 10. 把第 08 與第 09 節交給機器

第 08 節結尾說了一句「GitHub Actions 會在 push 後重跑這些檢查」，第 09 節則是一整串手動的 deployment 指令。

這兩段都停在關鍵的一半：**誰保證那些指令真的被執行？** 這一節把那個保證補上。

<Terminal title="bash — this repository's pipeline, on every push" flavor="output">{`
$ gh run list --limit 3

success api-tests            Deploy course to GitHub Pages
success deployment-contract  Deploy course to GitHub Pages
success course-harness       Deploy course to GitHub Pages
success build                Deploy course to GitHub Pages
success deploy               Deploy course to GitHub Pages
`}</Terminal>

<Callout type="important" title="「CI」和「CD」是兩件事，多數人把它們混著講">
  - **CI（Continuous Integration）**：push 之後自動跑檢查，**決定這次能不能過**。
  - **CD（Continuous Delivery / Deployment）**：通過之後自動把它部署上去。

  這門課的 repository **只有 CI**。第 09 節那串部署指令仍然是手動的，而這是刻意的——理由在 10.5 節。

  先把 CI 講清楚，因為它是 CD 的前提。**沒有通過檢查就自動部署，等於自動把壞的東西推給使用者。**
</Callout>

### 10.1 門禁只有在跳不過的時候才是門禁

<Terminal title="bash — the two copies of the same check" flavor="output">{`
$ npm run check

[1/16] Running Secret Policy Guard... PASSED
[2/16] Running Secret Harness Tests... PASSED
...
[16/16] Running Accessibility (A11y) & Font Size Guard... PASSED
ALL CHECKS PASSED in 8.51s. Ready for publishing & peer review.
`}</Terminal>

<Terminal title="bash — the point of the same command" flavor="output">{`
$ python pipeline_demo.py gate
1. A gate only works if nothing can walk past it

   The repository runs its checks with one command:

     npm run check

   Sixteen checks, and a failure in any one of them stops the build.
   That command is the pipeline. It is not a GitHub feature.

   What makes it a gate rather than advice:

     you can run it            -> catches mistakes before you push
     the server runs it too     -> catches what you did not run

   So there are two copies of the same check, not one check and a
   separate review process. If they ever disagree, the disagreement
   is itself the bug.
`}</Terminal>

<Callout type="important" title="這十六項不是 GitHub 的功能，是這個 repository 的一個指令">
  `npm run check` 在你的電腦上跑，和在 GitHub 上跑的是**同一個指令**。

  所以 pipeline 的第一個設計問題不是「怎麼設定 GitHub Actions」，而是「**我要檢查什麼**」。檢查還沒想清楚就先去接 CI，接出來的只是一台跑得很貴的空機器。
</Callout>

### 10.2 環境不同，同一段程式碼會有兩種結果

這是 CI 存在的主要理由，而它可以自己跑出來：

<Terminal title="bash — the same code, with the variable missing" flavor="output">{`
$ env -u SIGNING_KEY python pipeline_demo.py env
2. The same code, two environments

   SIGNING_KEY is not set

   Starting the app anyway...

   RuntimeError: SIGNING_KEY is not set.

   This is unit 12's rule, and this is why it exists.
   The app refuses to start instead of falling back to a default
   that would work on your laptop and fail on the server.

   On your computer you have the variable in your shell, so you
   never see this. On a fresh machine there is no shell profile,
   no .env you forgot to copy, and no muscle memory.

   The pipeline is the first place that fresh machine exists.
`}</Terminal>

<Terminal title="bash — with the variable present" flavor="output">{`
$ SIGNING_KEY=demo-key python pipeline_demo.py env
2. The same code, two environments

   SIGNING_KEY is set

   App started. Every check passed.
`}</Terminal>

<Callout type="warning" title="你已經學過這個規則，只是不知道它在哪裡被用到">
  單元 12 的 `main.py` 有一行 `RuntimeError`，要求 `SIGNING_KEY` 不存在就拒絕啟動。當時的理由是「金鑰不能寫在程式碼裡」。

  **那個 RuntimeError 的第二個理由就是 CI。**

  一段在你自己機器上跑得很好的程式，在一台沒有你的 shell 設定、沒有你的 `.env`、沒有你的肌肉記憶的機器上，會因為一個環境變數而拒絕啟動。

  **那台機器就是 CI。** 單元 12 教的不是「多寫一行防禦」，是「**讓失敗發生在可以被看到的地方**」。
</Callout>

<Callout type="note" title="同一個道理的其他版本">
  - 開發用 `localhost` 連資料庫，CI 上沒有那台資料庫。
  - 你有 `.env`，repository 沒有，而且不該有。
  - 你的 Python 是 3.11，伺服器是 3.14（`workflow` 裡寫死）。
  - macOS 檔名大小寫不敏感，Linux 敏感——`import Users.py` 在你的機器上過，在 CI 上失敗。

  最後一個尤其值得記：**它在你寫程式的那個小時裡完全不會發生，然後在你最沒時間的時候發生。**
</Callout>

### 10.3 Pipeline 的四個部分

<Terminal title="bash — every pipeline has these four" flavor="output">{`
$ python pipeline_demo.py steps
3. What a pipeline is made of

   Four steps, and every real pipeline has all four whether or not
   the author named them:

     1. get the code          checkout the exact commit
     2. install what it needs  dependencies, pinned
     3. run the checks         the same command you run locally
     4. decide                 pass means continue, fail means stop

   Step 3 is the one people mean when they say CI. Steps 1, 2 and 4
   are where the surprises live.
`}</Terminal>

<Callout type="important" title="用這個 repository 的 workflow 對照這四步">
  <Terminal title=".github/workflows/deploy-pages.yml — security job" flavor="output">{`
  jobs:
    security:                       # 3. run the checks
      steps:
        - uses: actions/checkout@v7  # 1. get the code
          with:
            fetch-depth: 0          #     完整 history，secret 才掃得到舊 commit
        - run: node scripts/secret-harness.mjs --all
        - run: (install gitleaks)
        - run: gitleaks detect ...
  `}</Terminal>

  - **步驟 1** 是 `checkout`。注意 `fetch-depth: 0`：secret 要掃的是**所有歷史**，只抓最新一版 commit 會漏掉三年前 commit 進去的密碼。
  - **步驟 2** 在別的 job（`course-harness` 裡 `bun install --frozen-lockfile`）。`--frozen-lockfile` 就是「步驟 2 必須釘住」的意思。
  - **步驟 3** 是 `bun run check`，和本機同一個指令。
  - **步驟 4** 是 `needs`：

    <Terminal title="the gate itself" flavor="output">{`
    build:
      needs: [security, api-tests, deployment-contract, course-harness]
    deploy:
      needs: build
    `}</Terminal>

    **`deploy` 不會在 `build` 之前跑，`build` 不會在任何一項檢查失敗時跑。** 這四個 job 各自獨立執行（所以總時間是最慢的那個，不是四個相加），任何一個失敗就整條停住。
</Callout>

<Callout type="important" title="「會顯示紅字」不等於「門禁」">
  一個只報告失敗、但部署仍然繼續的 pipeline，是**報表**，不是門禁。

  `needs` 這兩行才是門禁本體。如果沒有它們，紅字會出現在通知裡，然後部署照跑，網站壞掉，而沒有人把兩件事連起來。
</Callout>

### 10.4 第一次看 pipeline 失敗

<Terminal title="bash — what a red run looks like" flavor="output">{`
$ gh run list --limit 1
FAIL   security   Deploy course to GitHub Pages

$ gh run view --log-failed
security  Scan Git history with Gitleaks  WRN  leaks found: 5
`}</Terminal>

<Callout type="note" title="那次失敗是真的，而且原因是正確的">
  這份教材第一次加上 WebSocket 時，CI 就在這裡擋下來了。

  擋下的不是密碼——是 RFC 6455 公開範例裡的 nonce，被 gitleaks 誤判成 API key。而允許清單寫的是新語法，執行的掃描器版本太舊看不懂，所以沒有生效。

  **這件事值得說明，因為它正好是本節的內容：**

  - 門禁**有**生效。它擋住了一個 push，沒有東西被部署。
  - 修法有兩種：把允許清單降級成舊語法（CI 退步），或者升級掃描器（今天的做法）。
  - 「修正」和「讓檢查變得比較不嚴」是兩件事，後者要寫得出理由才做。

  這個 repository 現在把掃描器版本和它的 checksum 一起釘在 workflow 裡，就是那次失敗的結果。
</Callout>

### 10.5 為什麼這裡沒有自動部署到 VPS

<Callout type="warning" title="CD 是有風險的，而且風險不在部署，在「部署錯了沒人知道」">
  自動部署很吸引人：一個 commit 進去，網站更新，你不用做事。

  但它有兩個前提，而且第二個通常不成立：

  1. 通過檢查就代表可以上線——**幾乎不成立。** 檢查證明的是契約沒被破壞，不是「這個功能是對的」。
  2. 部署失敗時有人會看到——**這一點最常被忽略。** 自動部署把「網站掛了」變成一個沒有人通知的事故，可能持續幾小時。

  所以第 09 節的部署仍然是手動的，而這是一個**決定**，不是還沒做完。
</Callout>

<Callout type="note" title="成熟的順序通常是反過來的">
  1. 先有可靠的手動部署（第 09 節）。
  2. 自動化那個**已經可靠**的部署。
  3. 加上自動回滾。
  4. 最後才讓部署不需要人按。

  **從第 1 步跳到第 4 步的後果，是某個星期五晚上有個沒有人看過的 push 直接上了線。**

  順帶一提，這份教材的網頁部署**確實**是自動的（`deploy` 那個 job），因為 GitHub Pages 沒有 production 資料庫、沒有金鑰、沒有別人的 VPS。**自動化程度要跟「弄壞了會怎樣」成反比。**
</Callout>

<Callout type="important" title="這一課的最後一句">
  第 08 節說「把檢查變成門禁」，第 09 節說「先驗收再交付」，這一節說的是：**這兩件事不該由你一個人記得做。**

  pipeline 的價值不在於跑得快，而在於它**每天都會跑，而且你繞不過去**。
</Callout>

## 11. Code review：唯一沒有人教過的那件事

第 10 節講完 CI 之後，還有一個沒有被處理的問題。前面那些單元教了你寫程式、測試它、把它部署到公開網址，**沒有任何一課教你要怎麼讓別人讀你的程式碼**，而那件事恰好也**沒辦法自己驗證**。

第 10 節是整門課最後一個可以自己驗證的機制。這一節是最後一個沒辦法的。

而且這件事有個比其他所有主題都難的地方：**它不是一個可以驗證的技術。** 你可以跑測試證明契約沒壞，但沒有辦法跑測試證明有人真的讀過你的 diff。

所以這一節盡量講可以直接量出來的東西，而且量的對象是這份教材自己。

### 11.1 先量這份教材自己的 commit

<Terminal title="bash — the size of the diffs this repo asks you to review" flavor="output">{`
$ python review_demo.py sizes
1. How large are the diffs this repository asks someone to review?

   commits measured      : 50
   median lines changed  : 886
   75th percentile       : 1268
   90th percentile       : 2100
   largest single commit : 9208
`}</Terminal>

<Callout type="note" title="這個數字每次 commit 都會變">
  `review_demo.py sizes` 量的是**這個 repository 到今天為止的 git 歷史**，所以每多一個 commit 它就重算一次。上面是寫這段文字當時的值，你現在跑會看到不同的數字。

  **要看的不是那個數字，是「中位數是不是大到離譜」。** 它是三位數，那結論就成立；它掉到兩位數，那是我後來把 commit 切細了，同樣是好事。
</Callout>

<Callout type="warning" title="這不是稱讚，這是問題">
  **中位數 886 行。** 這是這份教材過去每一個 commit 的規模，而它是我一個人寫的、沒有別人 review。

  人的工作記憶不會隨著 diff 長大。超過幾百行之後，讀的人就開始用「這個改動看起來該長什麼樣」去判斷，而不是真的讀。

  所以正確的結論是：**中位數將近九百行的 commit 是不該被 review 的**，而這正是第 10.5 節說「大改動要拆成幾塊送」的原因。

  這支程式是在拿這份教材量它自己。**如果你在自己的專題上跑它而數字很好看，那多半表示你最近沒有真的在送東西上去。**
</Callout>

### 11.2 機器能查的，和只有人能查的

<Terminal title="bash — four greps against this repository" flavor="output">{`
$ python review_demo.py mechanical
2. What a script can check

   scanning 26 exercise files, excluding this one

   bare except
     0 hit(s): nothing
   todo left behind
     0 hit(s): nothing
   printed instead of logged
     554 hit(s): exercises/02-url/multipart_demo.py:35, ...
   hardcoded host and port
     28 hit(s): exercises/02-url/multipart_demo.py:15, ...
`}</Terminal>

<Callout type="note" title="你那邊的數字會不一樣，而且那才是重點">
  這四條量的是**這份教材練習目錄裡的檔案**，所以它會隨著教材增減而變動。寫下來是 554，換一個 repo 可能完全不同。

  **要看的不是那個數字，是「它是零還是不是零」。** 零代表這份程式碼裡沒有那個問題；數百代表規則跟這個目錄的寫法不相容。
</Callout>

**四條全部都是 grep 加正規表示式。** 沒有模型、沒有判斷、不需要理解任何事——這是它們的優點，也是它們的極限。**而這份清單有反方向。**

<Callout type="important" title="那個五百多次是這一節的重點，不是雜訊">
  「不要用 print，用 log」這條規則**沒有錯**，但是在這 26 個檔案裡有五百多個 `print(`。

  因為它們是**命令列教材程式，stdout 就是它們的介面**。每一個 `print` 都是正確的。那條規則是針對網頁服務的，而那裡的 stdout 有別的用途。
</Callout>

<Callout type="warning" title="五百多個誤報，比沒有這條規則更糟">
  一個在一個禮拜內就會被關掉的規則，等於沒有規則。

  **關掉的檢查不會抓到任何東西**，而且更貴的是：它讓人不再習慣讀輸出。半年後你重新打開它，還是會忽略。

  所以「開啟這個 linter」本身是一個需要判斷的決定，而那個判斷只有人能做。
</Callout>

<Callout type="important" title="反方向也一樣真實">
  單元 05 的併發練習**故意**包含一個會丟資料的 race。一個把它標成錯誤的檢查，那個檔案上就是錯的。

  **所以重點不是「規則有沒有道理」，是「它在這個檔案上講不講道理」。** 而那個判斷需要知道檔案在做什麼。
</Callout>

<Terminal title="bash — the other list" flavor="output">{`
$ python review_demo.py human
3. What only a person can check

     Intent      Does this change what we said it changes? A diff shows
                 what happened, never why it was wanted.

     Duplication Three places that know the role is admin is fine.
                 Three places that know how to parse a date is a
                 decision that was never made deliberately.

     Naming      Nothing fails when a function is called handle().
                 The cost is paid by whoever reads it in six months.

     Scope       This commit changed the rate limit and the colour of a
                 log line. One of those is a security control. Both are
                 now unreviewable as separate things.

     Consequences A test proves the contract holds. It cannot tell you
                 the contract is the right one.
`}</Terminal>

<Callout type="important" title="左邊那份清單是免費的，右邊那份是你被付費做的">
  linter 查的是左邊。

  **右邊每一項都無法寫成正規表示式，而且每一項都真實發生過。** 改錯了方向、測試全綠、CI 全綠，然後半年後沒有人知道為什麼會這樣。

  這就是 review 的價值所在：**不是抓 bug，是抓那些沒有壞、但走錯了路的東西。**
</Callout>

### 11.3 Review 最常見的三種失效

<Callout type="warning" title="一、蓋章式批准">
  「看起來沒問題，approve。」

  這是最貴的一句話，因為它**讓一整個 commit 沒有被讀過**，而且還留下「有人看過」的紀錄。下一個人會相信那個紀錄。

  誠實的版本是：「我讀了，但沒有足夠時間看懂 X。」那會產生一個 action item，而不是一個假象。

  **可驗證的問題**：你能不能在_review 裡說出**這次改動可能做壞什麼**？說不出來，就是沒讀。
</Callout>

<Callout type="warning" title="二、把 review 當成尋找完美風格的地方">
  「這裡可以用 `dict.get`。」如果那不是錯的，這個 comment 的成本是真實的：作者要停下來、解釋、決定、可能改。

  Review 的成本會互相競爭。**在 diff 裡追格式，會擠掉真正重要的那三行。**

  格式應該交給工具——這就是第 11.2 節那份清單存在的原因。
</Callout>

<Callout type="warning" title="三、只讀新增的那一半">
  diff 有兩邊。`+` 的那邊是新程式碼，`-` 的那邊是被刪的。

  **刪掉的那一半最少被看，也最容易藏問題。** 刪掉一個看起來多餘的檢查，其實那個檢查擋著某條路徑。

  讀 diff 的時候先看 `-`，再看 `+`。這一個習慣就能擋住一類很難查的 bug。
</Callout>

### 11.4 最便宜的 review 是自己先看

<Terminal title="bash — read your own diff before anyone else does">{`
$ git diff
$ git diff --stat
$ git diff origin/main...HEAD
`}</Terminal>

<Callout type="important" title="為什麼自己的 review 有效">
  因為**你手上有動機**。別人 review 你的程式碼是在花他的時間，你 review 自己的是在救自己的時間。

  而「自己先看」最實際的一個用途是：**它會讓你發現自己解釋不清楚的那個地方。** 你寫 commit message 的時候卡住，就代表那個 commit 太大、或者動機不明顯——兩個都是別人會退回來的原因。

  所以正確的順序是：**先自己讀一次 diff，再送出。** 不是禮貌，是把你會被問的問題先自己問一遍。
</Callout>

<Callout type="note" title="一句話把這節收掉">
  機器查「這段程式碼有沒有犯錯」，人查「這段程式碼是不是我們要的」。

  **前者已經有工具了，後者還沒有。** 所以 review 這個技能在 AI 能寫程式之後沒有變得不重要，它只是**從「抓 typo」移到了「抓方向」**。
</Callout>

## 單元實作作業

這一單元的作業分成三塊，**第一塊是把 FastAPI 部署到 VPS**，證據全部來自真實的 VPS。

### 第一塊：部署一個 FastAPI 服務到 VPS（作業 1 到 6）

1. `npm run test:api` 顯示 `4 passed`，`npm run security:scan` 通過。
2. DNS `A` record 回傳 VPS public IP。
3. `sudo ufw status numbered` 沒有 `8000`，`sudo ss -ltnp` 顯示 `127.0.0.1:8000`。
4. `sudo nginx -t` 與 `sudo certbot renew --dry-run` 通過。
5. 從另一台電腦執行 `curl -v https://你的網域/health`，同時看得到 Request Line、`200` Status Line 與 `{"ok":true}`。
6. Live deployment harness 回傳 exit status `0`。

### 第二塊：pipeline（第 10 節，作業 7 到 10）

7. 在你自己的 repository（期末專題）加一個 GitHub Actions workflow，只做兩件事：跑 `npm run test:api`，然後在失敗時讓 `build` 不能執行。截圖必須包含一次**綠燈**的 run 和一次**紅燈**的 run。**紅燈那一次要真的改壞一個測試去產生，不能假造。**
8. 執行 `env -u SIGNING_KEY python pipeline_demo.py env` 與 `SIGNING_KEY=demo python pipeline_demo.py env`，兩張截圖並排。回答：同一段程式碼，差別只有一個環境變數，為什麼結果不同？這跟單元 12 那個 `RuntimeError` 有什麼關係？
9. 打開你的 workflow 檔，回答：`fetch-depth` 沒寫（預設淺層）的話，secret 掃描會漏掉什麼？`needs:` 那一行如果刪掉，pipeline 會變成什麼？
10. 回答：你的專題要不要自動部署到 VPS？**用第 10.5 節的順序（先手動、後自動化、再回滾、最後才全自動）寫出你現在在哪一步**，以及你憑什麼判斷。

### 第三塊：code review（第 11 節，作業 11 到 14）

11. 執行 `python review_demo.py sizes`，截圖必須包含 `median lines changed` 那一行。**回答：你的專題最近十個 commit 的中位數是多少行？用第 11.1 節的標準判斷，那個數字可不可以被好好 review？**
12. 執行 `python review_demo.py mechanical`，截圖必須包含四個檢查的 hit 數字。**回答：`printed instead of logged` 有那麼多 hit，你會把這條規則打開還是把 linter 關掉？寫出你的判斷和理由。**
13. 用 `git diff --stat origin/main...HEAD` 看你的專題目前的完整改動，然後只讀 `-` 開頭的那一半（刪掉的程式碼），截圖或筆記列出**至少兩個你原本會漏掉的刪除**。回答：刪掉一行程式碼，可能改變什麼行為而沒有任何錯誤？
14. 找一個你最近寫過的函式，寫出它在六個月後被讀到時，你希望它叫什麼。**回答：它現在叫什麼？兩個名字差多少？**

截圖前遮住公司 IP、SSH 使用者名稱、email、Token 與密鑰。對外公開的服務網域可以保留。
