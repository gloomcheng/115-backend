## 01. 方向 A：這件事技術上可行嗎

貼文的主張拆成五條，逐條判斷。以下每一條都附上**我們實際去 assembly.gov.taipei 看到的證據**，而不是猜測。

### A.0 實證：我們真的去看了網站

<Terminal title="bash — 觀察一個真實的 HTTP 請求（不用登入就能跑）">{`
curl -v https://assembly.gov.taipei/PolicePeople/ 2>&1 | head -20
`}</Terminal>

<Terminal title="bash — 登入端點回傳的 JSON（需要 reCAPTCHA token）">{`
curl -s -X POST https://assembly.gov.taipei/PolicePeople/api/Home/ReCaptchaPassed \
  -H 'Content-Type: application/json; charset=utf-8' \
  -d '{"applyPid":"A123456789","robot":"<reCAPTCHA response>"}'
`}</Terminal>


我們打開 `https://assembly.gov.taipei/PolicePeople/`，讀它的 HTML 與 JavaScript bundle（`/bundles/home?v=...`），找到以下事實：

1. **登入端點是公開的 API**：`POST /PolicePeople/api/Home/ReCaptchaPassed`，body `{applyPid, robot}`，其中 `robot` 是 reCAPTCHA 的 response token。Server 回 `{ErrorCode, List:[{AT, RT, ET}]}`，前端把 `AT`（access token）、`RT`（refresh token）、`ET` 存進 `sessionStorage`。**token 真的發給 client，client 拿得到。**
2. **XSRF token 也從 client 取**：登入成功後呼叫 `getXsrfToken()`，把值存進 `sessionStorage.xsrfToken`。查詢案件的 `api/Home/GetRallyTable`（POST）要求 headers `Anti-CSRF: <token>` 與 `X-XSRF-TOKEN: <sessionStorage.xsrfToken>`。**XSRF token 是 client 端可讀的值，不是 HttpOnly cookie。**
3. **reCAPTCHA sitekey 公開**：`6Lew80gUAAAAACxa_sjPJIRdM4jyCxWdj-Il-rXn`（Google reCAPTCHA v2）。這是公開值，本來就該公開——但這也意味著攻擊者知道要用哪一把 key 去解。
4. **前端是 jQuery + ASP.NET**：所有請求都是 `$.ajax`，沒有額外的 client-side 加密或混淆。網路上有工程師發文附影片，示範「用 jQuery 就可以搶」——與我們看到的程式碼結構一致。
5. **我們沒有找到 `addAssemblyCase` 的提交端點**（需要登入後的 session 才看得到 Apply 頁面的 bundle），但表單結構與 token 取得流程已足以證明：**client 持有的 token 都能被腳本重用**。

<Callout type="important" title="實證結論">
  貼文說的「Anti-Forgery／XSRF／JWT／session 都拿得到」——**真**，而且我們在原始碼裡看到它們確實被存進 `sessionStorage`、被 `$.ajax` 帶進 header。防禦的確只提高取得成本，不是牆。
</Callout>

### A.1 純手速：不可行

表單先選日期、選完才能填個人資料、最多往後選一個月。這種順序依賴讓你無法事先把整張表填好等著按送出。一個正常人從空白表單到送出，至少數十秒。**0.3 秒送出不是手速。**

### A.2 腳本打 API：可行，但有前提

送出端是 `POST /PolicePeople/addAssemblyCase`（multipart/form-data），要同時過四類驗證：

| 驗證 | 腳本拿得到嗎 | 理由 |
| --- | --- | --- |
| Anti-Forgery cookie + `X-XSRF-TOKEN` header | 是（但要先過 reCAPTCHA） | 實證：`ReCaptchaPassed` 回傳 token，`getXsrfToken()` 取 XSRF 值；GetRallyTable 要帶 `Anti-CSRF` + `X-XSRF-TOKEN` header。同源政策只擋跨站 JS，第一方腳本不受限 |
| JWT token（Anti-CSRF header，300 秒有效） | 是 | 輸入身分證後打對應 API 拿得到 |
| `RallyPeopleSessId`（session） | 是 | 沒登入就有、沒設過期 |
| Google reCAPTCHA | **否（直接造不出）** | 由 Google 鑄造、綁私鑰，腳本自己造不出來 |

對照上表，前 3 個都是「提高取得成本」，不是牆。**第 4 個才是真牆**——但也有旁路（見 A.3）。

<Callout type="important" title="這就是「後端無法完全信任 client」">
  瀏覽器能構造的請求，腳本基本都能複製。JWT、CSRF token、session id 都是「client 持有的憑證」，client 持有的東西 client 就能拿去用。防禦的本質是提高成本，不是完全阻止。
</Callout>

### A.2.1 jQuery 與 AJAX：網站怎麼送請求，腳本怎麼複製

接著看送出端怎麼發請求：大二生可能沒碰過 jQuery。先補充：**jQuery 是 2006 年出現的一個 JavaScript 函式庫**，目的是讓「操作網頁元素」和「送 HTTP 請求」變得簡單。它不是新技術，而是那個年代的標準工具——這個政府網站用它，因為它穩定、老舊瀏覽器也能跑。

網站的 JavaScript 長這樣（從 bundle 擷取）：

```javascript
// 登入：把身分證與 reCAPTCHA 結果送給 Server
$.ajax({
  contentType: "application/json; charset=utf-8",
  dataType: "json",
  type: "POST",
  url: rootsite + "api/Home/ReCaptchaPassed",
  data: JSON.stringify({ applyPid: apply_pid, robot: recaptcha_response })
}).done(function (res) {
  // Server 回傳 AT / RT / ET，存進 sessionStorage
  sessionStorage.setItem("AT", res.List[0].AT);
  sessionStorage.setItem("RT", res.List[0].RT);
  sessionStorage.setItem("ET", res.List[0].ET);
  getXsrfToken();  // 再去拿 XSRF token
});

// 查詢案件：帶 token 送請求
$.ajax({
  url: rootsite + "api/Home/GetRallyTable",
  type: "POST",
  data: formData,
  headers: {
    "Anti-CSRF": token,
    "X-XSRF-TOKEN": sessionStorage.getItem("xsrfToken")
  }
});
```

**原理：HTTP 請求只是純文字。** 瀏覽器送出去的 `POST /api/Home/GetRallyTable`，其實就是一段文字：請求行、Header、Body。jQuery 只是幫你把 JavaScript 物件組成這段文字、送出去、解析回應。**任何程式（Python、curl、Node.js）都能組出完全相同的文字。**

所以腳本「搶」的方法是：

1. **先登入一次**：手動完成 reCAPTCHA，拿到 AT / RT / ET / XSRF，存起來。
2. **預熱連線**：在開放前先把 TCP + TLS 連線建好、keep-alive 掛著。
3. **開放瞬間**：用同一份 token、同一個連線，把 `POST /addAssemblyCase` 的 body（已序列化好的 multipart/form-data）送出去。

網站的 `$.ajax` 送的是什麼，腳本就送什麼——因為 HTTP 不認得「是誰送的」，只認得「這段文字對不對」。

<Callout type="note" title="大二生 takeaway">
  jQuery 的 `$.ajax` 只是「把物件轉成 HTTP 文字、送出去」的便利函式。腳本搶的不是 jQuery，而是 **HTTP 請求本身**。這也是為什麼「後端無法完全信任 client」——client 送的每一 byte，Server 都要自己驗證。
</Callout>

### A.2.2 AT / RT / ET / XSRF：各自做什麼？（系統設計角度）

網站回傳四個值：`AT`、`RT`、`ET`、`XSRF`。它們不是隨便取的名字，各自有明確的職責。一步一步拆：

> **名詞來源**：AT/RT/ET 是業界標準用語，不是這個網站自創的。`AT` = Access Token、`RT` = Refresh Token、`ET` = Expiration Time，來自 OAuth 2.0（RFC 6749）與 JWT（RFC 7519）的慣例，這個網站只是把名字縮寫了。正課（第 11 課）只講了「一枚 JWT token」（本質上就是 Access Token），沒有講 refresh token 的換發流程，所以這一節是新內容。CSRF 的攻擊手法則在正課第 12 課（08.6 節）教過——本課 A.5 是把那個機制套到這個真實網站上。

#### AT（Access Token，存取權杖）

- **做什麼**：每次呼叫受保護的 API（例如 `GetRallyTable`、`addAssemblyCase`）時，帶在 header 裡證明「我是登入過的使用者」。
- **壽命**：短（幾分鐘到幾小時）。偷走也只偷到短時間的權限。
- **為什麼短**：降低被盜用的影響範圍。AT 外洩，攻擊者最多用幾分鐘。

#### RT（Refresh Token，更新權杖）

- **做什麼**：當 AT 過期時，用 RT 去換一張新的 AT，不用重新登入、不用重新解 reCAPTCHA。
- **壽命**：長（幾天到幾週）。
- **為什麼要分開**：如果只有一個 token，要嘛壽命短（使用者頻繁重新登入，體驗差）、要嘛壽命長（外洩後攻擊者長時間可用）。分開之後，短命的 AT 負責日常請求，長命的 RT 只在「換新 AT」時用一次，降低 RT 被用到的頻率。

#### ET（Expiration Time，到期時間）

- **做什麼**：告訴 client「AT 什麼時候過期」，client 可以在過期前主動用 RT 去換新 AT，避免請求失敗。
- **為什麼需要**：client 不用每次請求都猜 AT 還活著沒有；ET 是契約，client 照著 ET 提前更新。

#### XSRF Token（跨站請求偽造防護權杖）

- **做什麼**：防 CSRF 攻擊。Server 發一個 token 給 client，client 每次送請求時帶在 header。Server 驗證 header 裡的 token 與 cookie 裡的 token 是否匹配。
- **為什麼需要**：沒有它，惡意網站可以偽造請求、利用瀏覽器自動帶 cookie 的特性攻擊你。
- **為什麼存 sessionStorage 而不是 HttpOnly cookie**：因為 SPA（單頁應用）的 JavaScript 需要讀到 token 才能帶進 header。代價是 client 可讀 → 腳本可重用。

#### 設計取捨總結

| Token | 職責 | 壽命 | 存放位置 | 防什麼 |
| --- | --- | --- | --- | --- |
| AT | 證明身分、授權 API 呼叫 | 短 | sessionStorage | 被盜用的影響範圍 |
| RT | 換新 AT，避免重新登入 | 長 | sessionStorage | 使用者體驗（不用頻繁登入） |
| ET | 告訴 client AT 何時過期 | 與 AT 同 | sessionStorage | client 提前更新，避免請求失敗 |
| XSRF | 防 CSRF 跨站偽造 | 與 session 同 | sessionStorage | 其他網站偽造請求 |

<Callout type="important" title="為什麼這套設計擋不住腳本">
  AT/RT/ET/XSRF 全部存在 `sessionStorage`，client 可讀。**它們的設計目的是「讓合法使用者順暢操作 + 防跨站攻擊」，不是「防使用者自己跑腳本」。** 腳本就是 client 本身，它讀得到所有 token、帶得出所有 header。要防腳本，必須在 Server 端加限流、稽核、reCAPTCHA —— 這就是方向 B 的內容。
</Callout>

### A.3 reCAPTCHA：真牆，但可預解

reCAPTCHA 在**送出那一下**要帶 token。它守的是「改資料」的動作：

- v2 在瀏覽器收集滑鼠軌跡、IP／封包行為、過去 session 狀態，判斷是不是人；可疑就請你選圖片。
- 通過後前端把 site key 送 Google，拿到 token，連同表單送後端。
- 後端把 token + secret key 送 Google `siteverify` 驗證。

token 由 Google 鑄造、綁 Google 私鑰，腳本造不出來。**但 token 有 120 秒效期**——可以在 23:59:00 先人工解一個握著，讓腳本在 00:00:00 送出，60 秒還在效期內。而且 reCAPTCHA token **單次使用**，每個請求要一枚。

<Callout type="note" title="代解服務（EZCaptcha）不是更快">
  代解服務的 API 不是秒回（背後可能是人工或 AI 滑鼠），對單發搶件來說自己按搞不好還更快。所以「人機配合」比「純機器人」更實際。
</Callout>

### A.4 網路 + 資料庫：可行

- DNS 解析：事先解好。
- TCP + TLS：把 HTTP/2 connection 先建起來、keep-alive 掛著，並狂搓 refresh token API 讓 JWT 一直是新鮮的。
- request body：先序列化到記憶體。
- 預熱完，當下只剩「送出 request」+「server 處理（含寫 DB）」，不包括 response 回來時間。
- 送出 request 本身是 kernel network stack 的 overhead，µs 等級。
- DB：INSERT + UPDATE，用 connection pool 長連線，寫進記憶體 + WAL。100ms 都算久了（除非瞬間流量真的很大）；正常範圍 5–20ms。

後端還要打一趟 Google `siteverify`（server→Google 往返，幾十～上百 ms），但 0.3 秒內仍很有機會—— server 是用它**收到的時間**驗證，可在 23:59:59 就送請求。

### A.5 直接塞資料庫：需要 DB 權限

「直接塞資料庫」需要資料庫寫入權限，前端瀏覽器做不到。如果真的發生，那是後端或 DB 權限管理的問題，不是前端腳本能做到的。

### A.6 事實查核結論

| 主張 | 判定 | 前提／反例 |
| --- | --- | --- |
| 純手速 0.3 秒 | **假** | 表單順序依賴 |
| 腳本打 API 0.3 秒 | **真** | 前 3 類 token 可取得 + reCAPTCHA 可預解 + 連線預熱 |
| reCAPTCHA 無法破解 | **半真** | 無法偽造 token，但可預解並在效期內使用 |
| 直接塞 DB | **需 DB 權限** | 非前端能做到 |
| 0.3 秒到資料入庫 | **真** | DB 正常、無鎖競爭 |

<Callout type="warning" title="反方觀點（評論區）">
  DB update 理論上 5–20ms，100ms 算太久了；DNS 要花時間但可預熱反駁。這些討論的本質是：工程師算的數百毫秒多是單趟延遲，不是人填表時間。要查真相要看 access log、IP 來源與稽核紀錄，不能只看毫秒數。
</Callout>

### A.5 XSRF 與跨站請求偽造（CSRF）：為什麼 sessionStorage 的 token 擋不住腳本

本課 A.0 看到 `X-XSRF-TOKEN` 從 `sessionStorage` 取值、帶進 `$.ajax` header。很多人會以為「有 token 就安全了」。這裡把 CSRF 的機制拆開，說明它擋什麼、不擋什麼。

**CSRF（Cross-Site Request Forgery，跨站請求偽造）的攻擊模型：**

1. 你登入過網站 A，瀏覽器存了 A 的 session cookie。
2. 你打開惡意網站 B。B 的頁面裡藏了一個會自動送出、target 指向 A 的表單（或 `<img src="https://A/...">`）。
3. 瀏覽器送往 A 的請求**會自動附帶 A 的 cookie**（不管請求從哪個網站發起），所以 A 後端看到合法的 session，就把偽造的請求當成你發的處理了。

**Anti-Forgery cookie + `X-XSRF-TOKEN` header 的防禦原理：**

- Anti-Forgery cookie 由 Server 設定、瀏覽器自動附帶（依目的地網域）。
- `X-XSRF-TOKEN` **不**存在 session 裡，要進入正確的網站 A 打 API 才拿得到，再隨請求放進 header。
- 惡意網站 B 的 JS 想打 A 的 API 去拿 token？**同源政策（Same-Origin Policy）** 讓 B 的 JS 讀不到 A 回應的內容，所以抄不到 token。
- 因此 B 偽造的請求帶不出 `X-XSRF-TOKEN`，Server 拒絕。**CSRF 擋的是「其他網站偽造請求」。**

**這道 CSRF 防線擋不住腳本——因為腳本代表你自己：**

- 腳本是第一方發的請求，沒有「跨站偽造」，瀏覽器的同源限制對它不適用。
- 腳本可以自己打 API 拿 token（就像 `ReCaptchaPassed` 回傳 AT/RT/ET、`getXsrfToken()` 取 XSRF 值），再把 token 帶進 header 送出。
- **CSRF 防禦的設計假設是「攻擊者控制別的網站」，不是「使用者自己跑腳本」。** 這兩種威脅模型不同，需要不同的防線（reCAPTCHA、限流、稽核）。

<Callout type="important" title="一句話記住">
  CSRF 擋的是「別的網站偽造你的請求」，不是「你自己的腳本」。`X-XSRF-TOKEN` 在 `sessionStorage` 裡，腳本讀得到、帶得出去——所以它保護不了速度戰。
</Callout>

**設計含意：**
- 把 CSRF token 放 `sessionStorage`（client 可讀）是為了方便 SPA，代價是腳本可重用。
- 若要防腳本，不能靠 CSRF，要靠 reCAPTCHA（提高機器人成本）、限流（提高頻率成本）、稽核（提高被發現成本）。
- 這就是本課方向 B 的五道防線：CSRF 是第 0 道（擋跨站），其餘四道才是防自動化。

## 02. 方向 B：後端怎麼設計才公平

接著進入方向 B。速度戰的本質問題：**先到先得 + 開放瞬間 + 自動化** = 誰的腳本快誰贏。公平不能靠速度，要靠設計。

### B.1 Server 是唯一真相來源

設計的起點是：所有判斷都在 Server 做。Client 送什麼都不可信——`role`、`user_id`、時間戳、申請順序，全部 Server 重算或重蓋。

### B.3 關鍵設計細節

#### 1. 唯一性約束（資料庫層）

```sql
-- 每身分每窗口只能有一筆申請
CREATE UNIQUE INDEX ux_application_per_identity_window
  ON applications (identity_id, window_id);

-- 同一路段同時段不可重複
CREATE UNIQUE INDEX ux_road_time_slot
  ON applications (road_segment, start_time, end_time)
  WHERE status IN ('pending', 'approved');
```

重複送出在 DB 層就擋下，回 `409 Conflict`，不是 `200` 後再發現。

#### 2. 伺服器時鐘

同樣地，時間也由 Server 判定，提前送出要和重複送出一樣在後端擋下來：

```python
if now() < window.open_at:
    raise HTTPException(425, "Too Early")
if now() > window.close_at:
    raise HTTPException(410, "Gone")
```

也就是說，Client 送來的時間戳一律忽略，Server 用自己的時鐘蓋章。

#### 3. 限流（per identity / per IP / per device）

- 同樣由 Server 計數：每身分每分鐘 N 次（如 5 次）。
- 每 IP 每分鐘 M 次（防多帳號）。
- 超過回 `429 Too Many Requests` + `Retry-After`。

#### 4. 排隊／抽籤取代速度戰

接著換掉速度戰本身，比較幾種配置：

| 策略 | 優點 | 缺點 |
| --- | --- | --- |
| 先到先得（FCFS） | 簡單、直覺 | 速度戰、自動化優勢大 |
| FIFO 排隊加等候號碼 | 平滑流量、可預期 | 仍可能有人用腳本搶排隊位置 |
| 抽籤（lottery） | 完全消除速度優勢 | 使用者體驗較差、需公告規則 |
| 兩階段（意願登記、抽籤、確認） | 兼顧公平與確認 | 流程較長 |


建議：熱門資源用「意願登記窗口 + 抽籤 + 確認」；一般資源用 FIFO 排隊 + 限流。

#### 5. reCAPTCHA 的定位

另外，reCAPTCHA 守的是「改資料」的動作，不是「讀資料」。後端要把 reCAPTCHA token 的驗證放在**寫入路徑**（`POST /addAssemblyCase`），且 token 單次使用、短效期。但 reCAPTCHA 不是公平機制——它只提高機器人的成本，不解決速度戰。公平要靠 B.2 的第 4 道。

#### 6. 稽核與可追溯

- 每筆申請記錄：身分、IP、user-agent、申請時間（Server 時鐘）、token 發行紀錄、reCAPTCHA 驗證結果。
- 開放後公開統計（各路段申請時間分佈），讓公眾驗證公平。
- 提供申訴管道與複查機制。

### B.4 不可少的契約（API 層）

| 狀況 | Status Code | 說明 |
| --- | --- | --- |
| 未登入／token 無效 | `401` + `WWW-Authenticate` | Client 重新登入 |
| 已登入但權限不足 | `403` | 使用者換權限或聯絡管理員 |
| 請求太快／超過限流 | `429` + `Retry-After` | Client 退避重試 |
| 開放前送出 | `425 Too Early` | Client 等到開放時間 |
| 重複申請 | `409 Conflict` | 資源已被佔用 |
| 路段衝突 | `409 Conflict` | 選其他路段或時段 |

<Callout type="important" title="401 與 403 的分工仍然成立">
  「你是誰」（401）與「能不能做」（403）是兩件事。限流用 429、時序用 425、衝突用 409 —— 每個錯誤都有自己的語意，Client 才知道該做什麼。
</Callout>

## 03. 課堂練習：設計你的公平申請系統

### 練習 1：事實查核表

對照本課 A 節，回答：
1. 貼文說「純手工不可能 0.3 秒送出」——你的判斷與理由？
2. 貼文說「腳本打 API 是絕對可行的」——列出它的 3 個前提。
3. 你認為「直接塞資料庫」在前端腳本情境下是否可能？為什麼？

### 練習 2：設計 API 契約

為「道路使用申請」設計 3 個 endpoint 的 request/response 與錯誤碼：
- `POST /applications`（送出申請）
- `GET /applications/{id}`（查詢申請）
- `POST /applications/{id}/cancel`（取消申請）

每個 endpoint 列出可能的 status code 與觸發條件。

### 練習 3：公平策略選擇

假設你負責設計一個「熱門場地預約系統」，開放時間固定、名額有限。選擇並論證：
- 你採用哪種公平策略（FCFS / FIFO 排隊 / 抽籤 / 兩階段）？
- 你如何防止自動化搶佔？
- 你如何讓結果可被公眾驗證？

### 練習 4：SQL 約束

寫出防止「同一身分在同一窗口重複申請」與「同一路段同時段重複核准」的 SQL 約束（唯一索引或檢查約束）。
