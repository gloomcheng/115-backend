## 01. 路由表是一筆資料

上一單元說「比對路由表」，那張表到底是什麼？打開課堂 API 的程式，最下面兩條路由是這樣寫的：

<Terminal title="examples/http-api/main.py — the routing table" flavor="output">{`
@app.get("/users/{name}")
def get_user(name: str):
    ...

@app.post("/users", status_code=201)
def create_user(body: dict):
    ...
`}</Terminal>

`@app.get("/users/{name}")` 不是註解。它在 Server 啟動時，把三樣東西登記進一張表：

| 登記的東西 | 這條路由的值 |
| --- | --- |
| method | `GET` |
| path 樣板 | `/users/{name}` |
| 對應的函式 | `get_user` |

`@app.post("/users", status_code=201)` 又登記一筆。這張表就是「哪些 method 配哪些 path 會執行什麼」的全部依據。

<Callout type="note" title="為什麼要講成資料">
  如果路由只是寫在函式上面的裝飾器，你就無法回答「這個 path 到底接受哪些 method」。把它想成資料之後，`405` 附帶的那個 `allow` 就有了來源：Server 是照著自己那張表列出可用的 method。
</Callout>

## 02. 先寫一條你自己的路由

到目前為止你都在讀別人的路由表。現在把 `main.py` 打開，在 `health()` **上面**加兩條自己的路由——加在上方是為了讓它們比現有的 `/users/{name}` 先被比對到，這一課的觀察才乾淨：

<Terminal title="Terminal 1 — edit main.py, above health()" flavor="output">{`
@app.get("/notes")
def list_notes():
    return {"notes": ["buy milk"]}


@app.get("/notes/{note_id}")
def read_note(note_id: int):
    return {"id": note_id, "text": "buy milk"}


@app.get("/health")
def health():
    return {"ok": True}
`}</Terminal>

`fastapi dev` 會自動重載。存檔後立刻在 Terminal 2 送一次：

<Terminal title="Terminal 2 — your first route" flavor="output">{`
> curl -i http://127.0.0.1:8000/notes
< HTTP/1.1 200 OK
< content-length: 30

{"notes":["buy milk"]}
`}</Terminal>

**你剛剛寫了第一條路由。** 三行函式，加上一個裝飾器。這就是整個「後端」最小的形狀。

現在做一個小實驗，把第一條改名，再送一次：

<Terminal title="Terminal 2 — the path is part of the identity" flavor="output">{`
> curl -i http://127.0.0.1:8000/todos
< HTTP/1.1 404 Not Found
< content-length: 22

{"detail":"Not Found"}
`}</Terminal>

只改了 `@app.get("/notes")` 裡的字串，路由就不存在了。**path 不是給人看的裝飾，是路由表的鍵。**

<Callout type="important" title="為什麼要先寫再讀">
  如果你只是讀別人的表，「路由是一筆資料」會是一個你記住的句子。你自己加了一筆、又把它改錯一次之後，它才變成你能在送出 Request 之前拿來預測的工具。下一節的預測表之所以成立，是因為那張表裡現在有你自己的兩筆。
</Callout>

## 03. `{name}` 是樣板，不是比對字串

第二條路由更能看出重點：那條 path 樣板匹配的是**一個任意段落**。`/users/alice`、`/users/ghost`、`/users/delete` 都會命中它，`name` 各自帶進不同的值。

第二單元教過 `@app.get("/items/{item_id}")` 這個寫法。那裡講的是語法；這裡要看的是它的行為——它是樣板匹配，不是字串相等。

<Terminal title="bash — the pattern matched" flavor="output">{`
> curl -i http://127.0.0.1:8000/users/ghost
< HTTP/1.1 404 Not Found
< content-length: 27

{"detail":"User not found"}
`}</Terminal>

這是關鍵證據：`ghost` 命中了樣板、函式有執行、回 `404` 是**你的程式**決定的。

再看一條完全沒有對應路由的：

<Terminal title="bash — nothing matched at all" flavor="output">{`
> curl -i http://127.0.0.1:8000/nowhere
< HTTP/1.1 404 Not Found
< content-length: 22

{"detail":"Not Found"}
`}</Terminal>

兩個 `404`，但 Body 不同：

| 你送的路徑 | Status Code | Body | 是誰寫的 |
| --- | --- | --- | --- |
| `/users/ghost` | `404` | `{"detail":"User not found"}` | **你的 handler** 判斷資料不存在 |
| `/nowhere` | `404` | `{"detail":"Not Found"}` | **框架**，因為沒有任何路由命中 |

<Callout type="important" title="Status Code 會騙你，Body 不會">
  只看數字，你會以為這兩個 `404` 是同一件事。看 Body 就知道：`Not Found` 是框架在路由表裡找不到，`User not found` 是你的函式跑完之後自己拒絕。接下來寫自己的 API 時，讓 `detail` 寫清楚是誰的判斷，Client 才分得出來。
</Callout>

## 04. 四個出口

路由比對不會有第五種結果。把四個出口列全：

| 出口 | 條件 | Status Code | 誰寫的 Body |
| --- | --- | --- | --- |
| 1 執行 | method 與 path 都對上路由表 | `200`、`201`，或 handler 自己決定的 `404` | 你的 handler |
| 2 method 不對 | path 命中，但這個 method 沒登記 | `405` + `allow` | 框架 |
| 3 path 不對 | 沒有任何路由命中這個 path | `404` `Not Found` | 框架 |
| 4 Body 先壞 | 還沒比到路由，Body 就解析失敗 | `422` | 框架 |

出口 4 值得注意它的位置：**它發生在比對路由之前。** 你送 `POST /users` 附上一段壞掉的 JSON，路由表根本沒被查到。單元 07 會把這一條拆開講。

現在把出口 1 與出口 2 都跑一次。出口 1 讀得到資料：

<Terminal title="bash — outlet 1, the member exists" flavor="output">{`
> curl -i http://127.0.0.1:8000/users/alice
< HTTP/1.1 200 OK

{"name":"Alice","note":"First HTTP example"}
`}</Terminal>

出口 2 換一個 method：

<Terminal title="bash — outlet 2, method not registered" flavor="output">{`
> curl -i -X DELETE http://127.0.0.1:8000/users/alice
< HTTP/1.1 405 Method Not Allowed
< allow: GET
< content-length: 31

{"detail":"Method Not Allowed"}
`}</Terminal>

`allow: GET` 是 Server 照著路由表告訴你的：這條 path 登錄過的 method 只有 `GET`。`def get_user()` 沒有執行。

## 05. 同一個 405，兩種原因

`allow` 這個 Header 值得再往下看一層。把兩個 `405` 並排：

<Terminal title="bash — two 405, two different allow values" flavor="output">{`
> curl -i -X DELETE http://127.0.0.1:8000/users/alice
< HTTP/1.1 405 Method Not Allowed
< allow: GET

> curl -i http://127.0.0.1:8000/users
< HTTP/1.1 405 Method Not Allowed
< allow: POST
`}</Terminal>

第一個是**成員**路徑 `/users/alice`：它登錄過，只接受 `GET` 讀取。
第二個是**集合**路徑 `/users`：它登錄過，但只接受 `POST` 建立。

為什麼 `/users` 不接受 `GET`？因為這支練習 API 還沒有「列出全部 users」的路由。你想讀整組使用者時框架本來該給你一個清單，但那一條還沒被寫出來。

<Callout type="important" title="Client 遇到 405 的第一個動作是讀 allow">
  `405` 本身就是答案的一半。它附帶的 `allow` 才是另一半——直接告訴你這個目標能用哪些 method。與其猜 Client 端要換哪個 method，不如讀 Server 給的線索。
</Callout>

## 06. 送出之前先寫下答案

路由表是資料，意味著任何 `(method, path)` 組合的結果都是可預測的。先寫下你的預測，再送出來對答案：

| 你的預測 | 你送出的 Request | 預測 Status Code | 預測 Body 裡有什麼 |
| --- | --- | --- | --- |
| 1 | `GET /users/alice` | `200` | 使用者資料 |
| 2 | `GET /users/ghost` | `404` | `User not found`（handler 寫的） |
| 3 | `GET /nowhere` | `404` | `Not Found`（框架寫的） |
| 4 | `DELETE /users/alice` | `405` | `allow: GET` |
| 5 | `PUT /users/alice` | `405` | `allow: GET` |
| 6 | `GET /users` | `405` | `allow: POST` |
| 7 | `POST /users` 帶合法 JSON | `201` | 你送進去的內容 |

第 5 與第 6 特別值得先想：它們的 `405` 看起來一樣，但 `allow` 不同，代表 Server 認為該換 method 的方向不同。

這不是考試技巧。以後你寫 Client 端、要處理別人的 API 時，同樣的表格就是你的除錯工具——**先算，再送**，比送出之後猜回應快得多。

## 07. `/health`：你交付的第一份契約

預測表算得準，是因為路由表對你不再是黑盒子。但還有一件事沒解決：**你寫的東西到底被誰讀？**

這張路由表答得出 Status Code，答不出別的事：你寫的東西到底被誰讀？被瀏覽器讀的頁面，錯了有人立刻發現；被程式讀的端點，錯了不會有提示。`/health` 就是第二種。

這就是為什麼要有 `/health`。先看你剛才那兩條 `/notes` 路由：它們有誰在讀？答應過誰？答不出來。

<Terminal title="examples/http-api/compose.yaml — the healthcheck test" flavor="output">{`
healthcheck:
  test:
    - python
    - -c
    - "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"
  interval: 30s
  timeout: 3s
  retries: 3
  start_period: 10s
`}</Terminal>

這段程式不會畫任何東西。它只做一件事：送出 Request，拿到 `200` 就當作服務還活著，任何例外就當作不健康。你可以把它複製出來自己跑：

<Terminal title="bash — run the probe yourself">{`
python -c "import urllib.request; r=urllib.request.urlopen('http://127.0.0.1:8000/health'); print(r.status, r.read())"
`}</Terminal>

輸出是 `200 b'{"ok":true}'`。這就是探測程式看到的全部資訊。

現在做這一課最後一個實驗。把 `main.py` 的 `health()` 改成 `return {"ok": "yes"}`：

<Terminal title="Terminal 2 — a change that looks fine" flavor="output">{`
> curl -i http://127.0.0.1:8000/health
< HTTP/1.1 200 OK

{"ok":"yes"}
`}</Terminal>

狀態碼還是 `200`。人看到會覺得「服務好像還活著」。

但探測程式正在做這件事：

<Terminal title="bash — what the probe judges" flavor="output">{`
$ python -c "
import urllib.request, json
r = urllib.request.urlopen('http://127.0.0.1:8000/health')
body = json.load(r)
print('status ok:', r.status == 200)
print('body ok  :', body.get('ok') is True)
"
status ok: True
body ok  : False
`}</Terminal>

**`status ok: True`、`body ok: False`。** 你交付的東西在人類看來正常，在真正使用它的程式看來是壞的。**請立刻改回 `{"ok": True}`。**

<Callout type="warning" title="這個錯誤特別難抓的原因">
  它不會在你的畫面上跳出來。部署流程照跑、頁面照樣開、log 也不會紅。只有當探測程式在某一個夜裡判定「這個容器不健康」並把它重啟時，你才會知道。
</Callout>

探測程式判定完成之後，第二個問題才出現：健康檢查該檢查多少，答案盡量少，原因在下一段。

<Terminal title="what a too-broad health check causes" flavor="output">{`
探測程式 ──> GET /health
              │
              ├─ 檢查程式本身存活        ── 必須做
              ├─ 檢查資料庫連線          ── 不要放進來
              └─ 檢查外部 API            ── 更不要放進來

資料庫故障 → 回 500 → 探測程式判定整個服務不健康
            → 平台重啟容器 → 連線全斷，資料庫恢復也沒用
`}</Terminal>

原因很單純：**容器被重啟時，裡面正在處理的 Request 全部中斷。** 資料庫短暫故障不該讓你的服務被重啟，因為重啟不會讓資料庫恢復，只會讓你連資料庫的能力暫時歸零。

| 該放進 `/health` | 不該放進 `/health` |
| --- | --- |
| 程式本身還能接受 Request 並回應 | 資料庫、外部 API、第三方服務 |
| 回應夠快（這支 API 的十次量測都在 `0.08s` 內） | 任何需要等待的檢查 |
| 不改動任何狀態（單元 01 的 safe method） | 會寫入或觸發工作的檢查 |

第三個問題：method 也在契約裡。第四課說過 `405` 會附上 `allow`。`/health` 只登錄了 `GET`，所以：

<Terminal title="bash — the method is part of the contract" flavor="output">{`
> curl -I http://127.0.0.1:8000/health
< HTTP/1.1 405 Method Not Allowed
< allow: GET

{"detail":"Method Not Allowed"}
`}</Terminal>

`curl -I` 送的是 `HEAD`，回 `405`。很多工具習慣用 `HEAD` 輕量探測一個 URL，但這條路由沒有答應過 `HEAD`。要讓它也能用，得明確登錄：

<Terminal title="main.py — adding HEAD explicitly" flavor="output">{`
@app.get("/health")
@app.head("/health")
def health():
    return {"ok": True}
`}</Terminal>

這一行差別，就是「契約裡有這件事」與「契約裡沒這件事」的差別。

把這節合起來，`GET /health` 答應了四件事：

| 契約 | 規格 | 違約的後果 |
| --- | --- | --- |
| 路徑 | 固定是 `/health` | 探測程式拿到 `404`，判定不健康 |
| 方法 | 只接受 `GET` | 送 `HEAD` 拿到 `405`，判定不健康 |
| 狀態碼 | 正常時固定 `200` | 任何其他數字，判定不健康 |
| Body | 固定是 `{"ok":true}` | `ok` 不是布林 `true`，判定不健康 |

<Callout type="important" title="你開始被別人依賴了">
  你寫的那兩條 `/notes` 路由和這條 `/health`，差別只在有沒有人依賴。前三課你是 API 的使用者；從這一節起，寫在這張表裡的每一列，都是別人會依賴的地方。**改動任何一列，都是 breaking change。**
</Callout>

這也是為什麼這個 repo 對 `main.py` 有測試。跑一次看看它在檢查什麼：

<Terminal title="bash — the existing test for this route">{`
cd examples/http-api
python -m pytest tests/test_main.py -q -k health
`}</Terminal>

那條測試斷言兩件事：`status_code == 200`，以及 `response.json() == {"ok": True}`。第二個斷言就是上面那個實驗的機器版——它擋下來的正是 `{"ok":"yes"}` 那種看起來沒問題的改動。怎麼自己寫出這種測試，單元 13 會處理。

## 08. 終端實戰驗證：四個出口各跑一次

四個出口各跑一次。兩個 Terminal 都開著，每一條指令送出之後，都去 Terminal 1 看對應的 access log 有沒有出現。

### 第一步：出口 1，命中並執行

<Terminal title="bash — outlet 1">{`
curl -i http://127.0.0.1:8000/users/alice
`}</Terminal>

觀察 `200`，Body 是使用者資料。

### 第二步：出口 3，路由表裡沒有這條

<Terminal title="bash — outlet 3">{`
curl -i http://127.0.0.1:8000/nowhere
`}</Terminal>

觀察 `404`，Body 是框架寫的 `Not Found`。

### 第三步：出口 2，method 沒登記

<Terminal title="bash — outlet 2">{`
curl -i -X DELETE http://127.0.0.1:8000/users/alice
curl -i http://127.0.0.1:8000/users
`}</Terminal>

觀察兩個 `405`，`allow` 分別是 `GET` 與 `POST`。Terminal 1 只會印 access log，不會有 traceback—— 因為函式沒有執行。

### 第四步：出口 4，Body 在比對路由之前就壞掉

<Terminal title="bash — outlet 4" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8000/users \\
>   -H 'Content-Type: application/json' \\
>   -d '{"name": "bob"'
< HTTP/1.1 422 Unprocessable Entity

{"detail":[{"type":"json_invalid","loc":["body",14],
  "msg":"JSON decode error","input":{},
  "ctx":{"error":"Expecting ',' delimiter"}}]}
`}</Terminal>

這裡沒有 `allow`，也沒有路由比對的痕跡：`/users` 這條路由是存在而且接受 `POST` 的，但壞掉的 Body 在比對之前就被擋下來了。單元 07 會說明這一步是誰在做。
