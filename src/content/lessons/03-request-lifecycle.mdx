## 01. Server 是一個等待的迴圈

`fastapi dev examples/http-api/main.py` 啟動的東西，是一個會一直等在那裡的程式。`main.py` 只是被它呼叫其中一段。

那個迴圈每次收到連線，就跑一輪：讀取、拆解、找對應的程式、執行、把結果寫回去，然後等下一個連線。`curl` 的每一次 `-v` 都對應其中一輪。

現在回頭看 Terminal 1。你在 Terminal 2 每送一次 Request，Terminal 1 就會多印一行：

<Terminal title="Terminal 1 — access log" flavor="output">{`
INFO:     127.0.0.1 - "GET /health HTTP/1.1" 200 OK
`}</Terminal>

這一行裡的三樣東西——`GET` 這個動作動詞（method）、目標路徑，以及 Status Code—— 正是接下來兩課要追的三條線。它們能出現在這裡，是因為那個迴圈每一輪都把它們算好了才往下走。

<Callout type="note" title="Terminal 1 與 Terminal 2 都要開">
  接下來每一個指令都分成兩個視窗：`curl` 打在 Terminal 2，觀察結果打在 Terminal 1。這個習慣到單元 15 看 log 時會直接用到。
</Callout>

## 02. 讀到空行為止

第一單元確認過：連續兩組 CRLF 代表 Header 結束。這個規則在 Server 端有一個具體後果——**在讀到那個空行之前，Server 還不知道你的 Request 到哪裡結束。**

回到 Terminal 2 的 `curl -v` 輸出，注意 `> Accept: */*` 後面還有一個單獨的 `>`：

<Terminal title="Terminal 2 — the blank line" flavor="output">{`
> GET /health HTTP/1.1
> Host: 127.0.0.1:8000
> User-Agent: curl/8.7.1
> Accept: */*
>
* Request completely sent off
`}</Terminal>

那個孤立的 `>` 就是空行。curl 送出它之後才印出 `* Request completely sent off`，然後 Server 才知道「收完了」，可以往下走。

這個等待是真的會發生的事。如果你送出一個沒有空行的 Request，Server 會繼續等，不會回應。在你還沒送出結尾的時候，它沒辦法決定 Status Code。

## 03. 解析：把純文字變成程式能用的東西

讀完之後，Server 把純文字拆成三部分：

| 原文 | 拆成 | 變成 |
| --- | --- | --- |
| `GET /health HTTP/1.1` | method `GET`、target `/health`、version `HTTP/1.1` | 三個字串 |
| `Host: 127.0.0.1:8000` | 欄位名與值 | 一組可以查的資料 |

第二單元講過，`scheme` 與 `host` 會影響連線，`host` 會進 Header。現在換到 Server 那一端：**這些值不只是被收下來，它們可以被你的程式讀出來。**

<Terminal title="Terminal 2 — ask the server what it saw" flavor="output">{`
> curl -i http://127.0.0.1:8000/request-info
< HTTP/1.1 200 OK

{"client":"127.0.0.1","scheme":"http","host":"127.0.0.1:8000"}
`}</Terminal>

`host` 的值 `127.0.0.1:8000` 正是你網址裡那個 port。Server 從 Request 的 Header 讀到了它，並且用 `application/json` 的形式還給你。

第二單元教你在 `curl -v` 的 Request 裡標出這一段；這一課看到的是它變成程式裡的一個值。標示與取值，是同一件事的兩面。

---

## 04. 比對：拿 method 與 path 對路由表

解析之後，Server 拿 `method` 與 `target` 去對照它的路由表，找出該執行哪一段程式。

**對不上的時候，Response 在這裡就已經決定了**，你寫的那個函式一行都還沒跑。`405 Method Not Allowed` 與 `404 Not Found` 都是在這一步產生的。

這一課先看見它的位置。路由表到底是什麼、對不上的時候有哪幾種結果、該怎麼在送出之前就預測——是下一課整節的主題。

---

## 05. 執行與序列化：你的函式一個位元組都沒寫

對上了路由表，函式就會跑。回頭看課堂 API 的程式：

<Terminal title="examples/http-api/main.py — the whole handler" flavor="output">{`
@app.get("/health")
def health():
    return {"ok": True}
`}</Terminal>

這三行裡沒有 Status Line，沒有 Header，也沒有把字串接起來。它只回傳了一個 Python 的 `dict`。

再看 Response：

<Terminal title="Terminal 2 — what the framework added" flavor="output">{`
< HTTP/1.1 200 OK
< content-length: 11
< content-type: application/json

{"ok":true}
`}</Terminal>

`{"ok":true}` 剛好 11 個字元，`content-length` 就是 11。curl 自己也數了一次：

<Terminal title="Terminal 2 — curl counts the bytes" flavor="output">{`
{ [11 bytes data]
{"ok":true}
`}</Terminal>

`200` 從哪裡來？`content-type` 從哪裡來？`content-length` 從哪裡來？答案是：**框架算的，不是你寫的。**

<Callout type="important" title="content-length 是數出來的，而且它決定對方在哪裡停">
  第二單元說過 `Content-Length` 指明 Body 的確切位元組長度。現在你知道它是誰算的：框架序列化你的回傳值之後數出來的。Client 讀到這個數字為止的位元組就停止讀取 Body—— 數字錯一個位元組，Client 就會讀錯或卡住。這個數字不能靠感覺。
</Callout>

你可以自己驗一次，不用相信我數的：

<Terminal title="Terminal 2 — verify the byte count yourself">{`
curl -s http://127.0.0.1:8000/health | wc -c
`}</Terminal>

輸出 `11`。這是這一課最值得記住的一件事：**你在後端寫的是資料，框架寫的是封包。** 兩者的邊界，就是你對 Response 的控制權結束的地方。

後果會在後面幾個單元展開：檢查寫在哪一層，決定 Client 拿到 `422` 還是 `500`（單元 07）；log 裡出現的欄位也由這一層決定（單元 15）。這一課只需要記住那條邊界在哪。

---

## 06. 五個階段，五個可能決定 Status Code 的位置

把這張表放進去，後面幾課的位置就清楚了：

| 階段 | 發生什麼 | 可能決定 Status Code 的位置 |
| --- | --- | --- |
| 01 連線 | 建立 TCP 連線 | 連不上時沒有 HTTP 狀態碼，只有 TCP 層的失敗 |
| 02 讀取 | 讀到空行為止 | Request 不完整時，框架可能回 `400` |
| 03 解析 | 拆 method 與 path，Header 收成資料 | Body 格式不合法時，框架在這裡就決定（例如 `422`） |
| 04 比對 | 對照路由表 | `405`、`404`（下一課） |
| 05 執行 | 跑你的函式 | 你自己決定 `200`、`201`、`404`；函式拋例外則是 `500`（單元 07） |

第一單元講過：狀態碼的第一碼決定責任歸屬。這張表補上另一個問題——**責任是在哪一步被決定的**。

同一個「Request 失敗」，在第 03 步被擋下來，跟在第 05 步崩潰，對 Server 來說是完全不同的兩件事。差別不在數字，在它發生在哪裡。

接下來把這五個階段各跑一次，讓你看到每一步各自留下什麼證據。

## 07. 沒有 Request 的工作

第 06 節那張表從連線走到執行，五個階段，最後一個產出 Response。**整個生命週期到這裡就結束了**，而且它有個前提你還沒注意到：從頭到尾都有一個人在等。

<Terminal title="bash — doing the work during the request" flavor="output">{`
$ python queue_demo.py inline
1. Doing the work during the request
  request handled, client got its response
    jobs: 1 (done=1)   effects: 1
   The client knows the answer, because the client was still waiting.
   If charge() had raised, the client would have gotten a 500.
`}</Terminal>

<Callout type="important" title="Client 還在等，所以成功與失敗都有地方送">
  這是 Request 生命週期給你的東西：一條**已經接好的、雙向的**回報通道。

  成功就是 `200`。失敗就是 `500`。逾時就是 Client 自己的錯。**每一種結果都有一個位置可以送到。**

  背景工作沒有這條通道。這一節講的就是沒有通道之後該怎麼辦。
</Callout>

### 07.1 把工作丟到 Client 看不到的地方

最常見的做法是：把工作寫進一個佇列（先是一張表），立刻回 `202 Accepted`，然後交給另一個行程慢慢做。

<Terminal title="bash — the request ends, the work has not" flavor="output">{`
$ python queue_demo.py queued
2. The same work, after the response
  request handled, client got 202 Accepted
    jobs: 1 (pending=1)   effects: 0
    ^ these disagree. nothing raised. nothing was logged.
   The client no longer knows the answer, and that is the trade.

  worker finished
    jobs: 1 (done=1)   effects: 1
   Now the client knows nothing, the worker knows, and only the log ties them.
`}</Terminal>

<Callout type="important" title="`202` 的意思是「我收到了」，不是「我辦完了」">
  這兩個字在這裡差得很遠。`202` 只保證一件事：**這筆工作不會丟掉，它在某個地方排隊。**

  它不保證成功，也不保證什麼時候完成。**所以 Client 想知道結果，就必須自己再問一次**——輪詢一個狀態端點，或者接受 webhook。

  這是設計，不是缺陷。`202` 存在的唯一理由就是「我現在還不知道答案」；它在 RFC 9110 裡跟 `200`、`201` 同屬 **2xx**，**非同步不等於失敗**。
</Callout>

### 07.2 工作跑到一半，行程死了

這是第一個沒有 Client 幫你擋住的東西。

<Terminal title="bash — killed after the charge, before the bookkeeping" flavor="output">{`
$ python queue_demo.py crash
3. The worker dies between the charge and the bookkeeping
  worker killed after charging, before marking done
    jobs: 1 (running=1)   effects: 1
   status is stuck at 'running'. No exception, no 500, no Client to tell.
   The queue still holds a job that will never finish on its own.
`}</Terminal>

<Callout type="warning" title="注意 `effects: 1`——錢已經扣了">
  這個狀態最危險的地方在於**它看起來還在進行中**。`status` 是 `running`，不是 `failed`。

  - 沒有例外，因為行程不是因為錯誤死的。
  - 沒有 log，因為行程死掉的時候沒有東西會替你記下最後走到哪裡。
  - 沒有 Client 會來問，因為 Client 早就拿到 `202` 走人了。

  **前面六節教的三個發現問題的機制，在這裡同時失效。** 這是本節存在的理由。
</Callout>

<Callout type="note" title="單元 15 會處理怎麼讓它至少留下紀錄">
  單元 15 教的是用 request id 把兩段 log 接起來。但這裡要誠實地說：**就算 log 接得很好，這個工作還是卡住了。** log 讓你看見問題，不會解決問題。

  解決問題的是下面這個機制。
</Callout>

### 07.3 重試，然後收兩次錢

這個 `running` 不會自己好。要嘛有人剛好看見它卡住並重跑一次，要嘛之後有人回頭查這批資料時才發現——不管是哪種，重跑都是合理的反應。**而重跑安不安全，取決於那個 job 能不能重試。**

<Terminal title="bash — one retry" flavor="output">{`
$ python queue_demo.py retry
4. The operator retries the stuck job
  after one retry
    jobs: 1 (done=1)   effects: 2
    ^ these disagree. nothing raised. nothing was logged.

   1 job, 2 charges. The customer was billed twice.

   A queue cannot promise exactly-once. It promises at-least-once, which
   means 'at least', and the second time is your problem to make safe.
`}</Terminal>

<Callout type="important" title="「至少一次」的意思是「至少」，不是「只有一次」">
  幾乎所有訊息佇列（Redis、SQS、RabbitMQ）提供的都是 at-least-once 語意。原因很直覺：**寧可重複執行，也不要漏掉執行。**

  重複執行在純計算上是無害的——把一個數字加兩次，你重算一次就會覆蓋掉。但只要工作有**對外的作用**（扣款、寄信、寫進另一個系統），重複就是真的重複。

  **所以 exactly-once 不是佇列給你的，是你自己在那一行的程式碼裡做出來的。**
</Callout>

### 07.4 讓那一次「副作用」自己 idempotent

<Terminal title="bash — the same retry, with a guard" flavor="output">{`
$ python queue_demo.py idempotent
5. The same retry, when the charge is idempotent
   second attempt: already charged, skipping
  after the same retry
    jobs: 1 (done=1)   effects: 1

   1 job, 1 charge. The retry was safe.
`}</Terminal>

差別不在多問一句，而在**誰來擋重複**：`queue_demo.py` 加了一個 `UNIQUE` 約束，然後讓插入自己失敗，而不是先問再插。

<Callout type="warning" title="為什麼不能「先問再插」">
  常見的寫法是先問一次「這個 job 做過了嗎」，答案是沒有就插。但那是**兩條語句**，中間有一個空隙：

  ```sql
  SELECT COUNT(*) FROM effects WHERE job_id = 1;   -- 0
  -- 行程在這裡死掉
  INSERT INTO effects ...;                          -- 永遠不會執行到
  ```

  下一次重試會重新問一次，然後插進去 —— 這次沒問題。但如果死掉發生在**插入之後、更新狀態之前**，下一個人就分不清「從來沒做過」和「做完了但沒記錄」。

  這叫 **check-then-act 的競態**，跟單元 05 第 02 節那個 lost update 是同一個形狀，只是發生在別的地方。
</Callout>

<Callout type="important" title="正確的機制是讓資料庫擋，不是讓你先問">
  `queue_demo.py` 做的事是加一個約束，然後讓插入自己失敗：

  ```python
  try:
      connection.execute("INSERT INTO effects (job_id, note) VALUES (?, ?)", ...)
      connection.commit()
      return "charged"
  except sqlite3.IntegrityError:
      connection.rollback()
      return "already charged, skipping"
  ```

  **沒有 SELECT。** 提問和記錄是同一條語句，資料庫保證它只會成功一次，所以中間沒有空隙可以掉進去。

  順帶一提，上一節那個 `effects` 表**故意沒有這個約束** —— 沒有它，你根本看不到重複是怎麼發生的。看 schema 是這個練習的一部分。
</Callout>

<Callout type="important" title="所以背景工作的三個實際規則">
  1. **假設它會被執行不只一次**，因為它一定會。重試是復原手段，不是例外。
  2. **副作用必須 idempotent**，而且 idempotency 的證明要跟副作用寫在同一個 transaction。
  3. **沒有人在等，所以失敗要自己留下紀錄。** 沒有 `500` 會跳出來，沒有 Client 會重試，也沒有人會注意到。

  第三條是最容易被忽略的，而且它正好是單元 15 的主題。
</Callout>

### 07.5 什麼時候該丟出去，什麼時候不該

<Callout type="important" title="不要為了「看起來比較好」而丟到背景">
  背景工作是**用延遲換可靠性**，不是免費的。

  | 丟出去 | 留在 Request 裡 |
  | --- | --- |
  | 寄信、產生日報 | 密碼檢查、權限判斷 |
  | 影片轉檔、圖片縮圖 | 驗證碼、付款前的前置檢查 |
  | 呼叫第三方 API | 使用者正在螢幕上等結果的事 |

  判斷標準是後面那三列：**這件事的結果，使用者現在需不需要看到。** 需要就留下來，讓它慢一點但誠實；不需要就丟出去，因為他反正不會站在那裡等你。

  用背景工作包裝一個 20 毫秒就能完成的事，得到的只是一個更難查的錯誤。
</Callout>

<Callout type="note" title="這個課程還沒教的部分">
  真實系統的佇列還要處理：工作的優先順序、同一個使用者的事件順序（先後順序不能反）、死信佇列、逾時、重試次數上限。

  那些都是同一個問題的變體：**沒有人在等，所以每一件事都要你自己定規則。**
</Callout>

## 08. 有 Client 在等，就要有期限

第 07 節的背景工作沒有 Client 在等，所以沒有地方回報成功或失敗。那 Client **在等**的情況呢？

<Callout type="important" title="等待是有代價的，而且代價不在 Client 那邊">
  第 07 節講「沒有人在等」的麻煩。這一節講相反的麻煩：**有人一直在等，而 Server 讓他等。**

  等待期間，那個處理請求的 worker 是**被你佔住**的。它不是空的、不是在思考，它是在等一個已經遲到的答案。
</Callout>

### 08.1 沒有期限的請求

<Terminal title="bash — the request that never ends" flavor="output">{`
$ python timeout_demo.py all
1. No timeout anywhere
   elapsed: 3.0s   client saw: HTTP 200

   The client waited. Nothing was wrong with the client.
   The server spent that whole time sleeping on a dependency that
   was never going to answer in time.

   That is not a slow response. That is an occupied worker.
`}</Terminal>

<Callout type="warning" title="`HTTP 200` 讓這一段特別危險">
  Client 拿到的是**成功**。Server 忠實地完成了它被要求做的事。

  但在那 3 秒裡，能處理其他請求的資源少了一個。**這個成本不會出現在任何一行 log 或任何一個狀態碼裡**，它只表現在「同時能服務幾個人」。
</Callout>

### 08.2 期限要往下傳，不是事後檢查

<Terminal title="bash — the same call, with the client's deadline" flavor="output">{`
2. The same call, with a deadline the client sent
   elapsed: 2.0s   client saw: HTTP 504

   Same server, same slow dependency, same 3 second wait in the
   dependency. The only difference is that the client said how long
   it is willing to wait.
`}</Terminal>

<Callout type="important" title="`504` 不是重點，2.0 秒才是">
  重點是**同樣那個 3 秒的依賴，這次只佔了 2 秒**。

  差別在於期限是**交給依賴去執行**的，而不是等依賴回來之後才檢查：

  ```python
  # 錯的：做完才檢查
  result = call_dependency()
  if took_too_long:
      return 504

  # 對的：期限先交下去
  result = call_dependency(timeout=deadline)
  if timed_out:
      return 504
  ```

  **事後檢查不是 timeout，是一個加在已經浪費掉的工作上面的狀態碼。** worker 還是佔用了同樣的時間，只是不再假裝一切正常。
</Callout>

### 08.3 三個依賴，一份預算

這是實務上最常錯的地方，而且錯得很自然，因為每一層單獨看都沒問題。

<Terminal title="bash — the budget is spent once and spent three times" flavor="output">{`
3. Three dependencies, one client budget

   A request that calls A, then B, then C. Each takes 1 second.
   The client will wait 2 seconds in total.

   after 1 call(s): 1s spent, fits
   after 2 call(s): 2s spent, fits
   after 3 call(s): 3s spent, already too late

   Each individual call is well inside the budget. The chain is not,
   because the budget is spent three times and only available once.
`}</Terminal>

<Callout type="warning" title="把每一層的 timeout 都設成 Client 的 timeout，是最常見的錯法">
  因為那樣看起來很安全——每一層都不會比 Client 更早放棄。

  **但整條鏈會超過 Client 的期限**，而最外層是最後才知道自己已經太慢的那一層。Client 早就走了，Server 還在把第三個查詢跑完。

  **正確的算法是遞減的**：最外層拿到 Client 給的期限，**往下傳的時候要減掉自己已經花掉的時間，並且留下一點給後面的步驟。**

  三層的話，每一層實際上只能用到三分之一左右。**而且這個值要寫在程式碼裡當預設值，不要留給部署時臨時決定**——因為設定的人通常不知道呼叫鏈有幾層。
</Callout>

### 08.4 為什麼這會變成整站掛掉

前面三段講的都是「一個請求變慢」。這一段換成**全部**請求都出問題，因為這才是會讓你半夜醒來的那一種。

<Terminal title="bash — four workers, one slow dependency" flavor="output">{`
4. Why that becomes a site outage

   The server has 4 workers. Each one is busy while it sleeps.

   One slow dependency, six requests:
     request 1: worker 1 occupied
     request 2: worker 2 occupied
     request 3: worker 3 occupied
     request 4: worker 4 occupied
     request 5: worker 1 queued, nobody free
     request 6: worker 2 queued, nobody free

   After 4 requests every worker is asleep. Request 5 waits,
   and so does every request after it, including the ones that would
   have been instant against a healthy dependency.
`}</Terminal>

<Callout type="warning" title="這叫連鎖故障，重點在最後那句">
  注意「including the ones that would have been instant against a healthy dependency」。

  **一個慢的依賴不只是讓慢的東西變慢，它把快東西需要的容量也吃掉了。** `/health` 這種零查詢的端點，本來應該永遠回應，但它排在同一條隊伍裡。

  這是為什麼 timeout 不是「效能優化」，是**可用性設計**：

  - 沒有 timeout：worker 被無限期佔用，直到數量用完為止。
  - 有 timeout：worker 在期限內被釋放，下一個請求拿到真正的答案而不是一個隊伍位置。

  **把 worker 還回去，就是全部。**
</Callout>

<Callout type="note" title="504 和 503 差在哪，這裡剛好用得上">
  單元 12 教過 `503` 是「我現在壞掉了」。而 `504` 是「**我等不到我相依的東西**」——它是因為**下游**慢，不是自己壞。

  這個區別在負載平衡器面前很重要：看到大量 `504` 的時候，要處理的是那個變慢的依賴，不是把 Server 開大。
</Callout>

### 08.5 這門課還沒教、但你會遇到的

<Callout type="important" title="連線池是同一個題目的另一半">
  timeout 管的是「**這次呼叫最多花多久**」，連線池管的是「**同時最多開幾條連線**」。

  兩者互相衝突：一個 30 秒的 timeout 搭配一個只有 10 條連線的池，意味著只要 10 個慢請求就能讓所有人在排隊。**timeout 開越大，池就越需要放大。**

  真實的設定通常是：timeout 設短一點（2 到 5 秒），池設大一點。**反過來做會得到一個「偶爾卡住而且沒有人知道為什麼」的系統。**

  SQLite 沒有這個問題——第 05 節提過，`BEGIN EXCLUSIVE` 會拒絕而不是排隊。**這個簡單是本機練習的優點，一旦換成網路資料庫就沒有了。**
</Callout>

<Callout type="note" title="一句話把這節收掉">
  第 07 節：**沒有人在等**，所以成功與失敗要自己記錄。

  這一節：**有人在等**，所以要告訴他你要等多久，而且要真的在那一刻停下來。

  兩個方向都指向同一件事——**你的 Server 只有有限的資源，而每一個請求都在佔用其中一份。**
</Callout>

## 09. 終端實戰驗證：五個階段各留一次證據

背景工作與請求期限都談完了，現在回到最初那條路徑：五個階段，每一個都要親眼看一次。接著兩個 Terminal 都開著，逐條跑。

### 第一步：連線

<Terminal title="Terminal 2 — step 1" flavor="output">{`
*   Trying 127.0.0.1:8000...
* Connected to 127.0.0.1 (127.0.0.1) port 8000
`}</Terminal>

觀察 `*` 開頭這兩行，是第一課講過的三向交握完成後的樣子。沒有它，後面都不會發生。

### 第二步：讀取

<Terminal title="Terminal 2 — step 2" flavor="output">{`
> Accept: */*
>
* Request completely sent off
`}</Terminal>

觀察那個孤立的 `>`：它是空行。curl 送出它之後才會說「送完了」。

### 第三步：解析

<Terminal title="Terminal 2 — step 3" flavor="output">{`
> curl -i http://127.0.0.1:8000/request-info
< HTTP/1.1 200 OK

{"client":"127.0.0.1","scheme":"http","host":"127.0.0.1:8000"}
`}</Terminal>

觀察 `host` 從 Request 的 Header 被讀出來，並出現在 Response 裡。

### 第四步：比對

<Terminal title="Terminal 2 — step 4" flavor="output">{`
> curl -i -X DELETE http://127.0.0.1:8000/health
< HTTP/1.1 405 Method Not Allowed
< allow: GET

{"detail":"Method Not Allowed"}
`}</Terminal>

觀察這個 `405` 在比對階段就產生了，`def health()` 沒有執行。Terminal 1 不會出現這條路徑的 traceback。

### 第五步：執行

<Terminal title="Terminal 2 — step 5" flavor="output">{`
> curl -s http://127.0.0.1:8000/health | wc -c
11

> curl -i http://127.0.0.1:8000/health
< HTTP/1.1 200 OK
< content-length: 11

{"ok":true}
`}</Terminal>

觀察數出來的 11 個位元組，就是框架寫進 `content-length` 的那個 11，而它是這條生命週期的最後一個 Response。

### 第六步：沒有 Request 的工作

前五步每一個都有 Client 在等，Response 也因此有地方可送。第六步把 Client 拿掉，看還剩什麼。

<Terminal title="bash — step 6, inline then queued" flavor="output">{`
$ python queue_demo.py inline
  request handled, client got its response
    jobs: 1 (done=1)   effects: 1

$ python queue_demo.py queued
  request handled, client got 202 Accepted
    jobs: 1 (pending=1)   effects: 0
    ^ these disagree. nothing raised. nothing was logged.
`}</Terminal>

### 第七步：重試，然後收兩次錢

<Terminal title="bash — step 7, the retry" flavor="output">{`
$ python queue_demo.py retry
  after one retry
    jobs: 1 (done=1)   effects: 2

$ python queue_demo.py idempotent
   second attempt: 1 record(s) for job 1 already, skipping
  after the same retry
    jobs: 1 (done=1)   effects: 1
`}</Terminal>

**第一段是 `effects: 2`，第二段是 `effects: 1`。** 同一個重試，唯一差別是那個副作用有沒有記錄自己做過。

### 第八步：給等待設一個期限

第七步的工作沒有 Client 在等。第八步反過來，有人在等。

<Terminal title="bash — step 8, with and without a deadline" flavor="output">{`
$ python timeout_demo.py all
1. No timeout anywhere
   elapsed: 3.0s   client saw: HTTP 200
2. The same call, with a deadline the client sent
   elapsed: 2.0s   client saw: HTTP 504
`}</Terminal>

**第一次回 `200`，第二次回 `504`。** 看 `elapsed` 那一行：同樣那個 3 秒的依賴，第二次只佔了 2 秒，因為 Client 這次有說自己只等 2 秒，那個期限往下傳了。
