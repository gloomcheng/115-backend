## 01. 形狀：型別、必填、長度

先看 `/strict` 那條路由怎麼宣告它的形狀：

<Terminal title="exercises/10-validation/main.py — the model" flavor="output">{`
class UserStrict(BaseModel):
    name: str = Field(min_length=1, max_length=40)
    role: str | None = Field(default=None, max_length=20)
`}</Terminal>

`name: str` 是型別，`min_length=1` 與 `max_length=40` 是長度限制。這些宣告存在的期間，Server 就已經知道「什麼樣的 Body 可以進來」，而且**你的 handler 還沒開始跑**。

四種壞資料，四個 `422`：

<Terminal title="bash — four shapes of wrong" flavor="output">{`
# 少一個欄位
> curl -s -X POST http://127.0.0.1:8003/strict \\
>   -H 'Content-Type: application/json' -d '{"role":"student"}'
{"detail":[{"type":"missing","loc":["body","name"],
  "msg":"Field required","input":{"role":"student"}}]}

# 型別不對
> curl -s -X POST http://127.0.0.1:8003/strict \\
>   -H 'Content-Type: application/json' -d '{"name":123}'
{"detail":[{"type":"string_type","loc":["body","name"],
  "msg":"Input should be a valid string","input":123}]}

# 空字串
> curl -s -X POST http://127.0.0.1:8003/strict \\
>   -H 'Content-Type: application/json' -d '{"name":""}'
{"detail":[{"type":"string_too_short","loc":["body","name"],
  "msg":"String should have at least 1 character","input":"",
  "ctx":{"min_length":1}}]}

# 太長
> curl -s -X POST http://127.0.0.1:8003/strict \\
>   -H 'Content-Type: application/json' -d '{"name":"xxxx...45"}'
{"detail":[{"type":"string_too_long","loc":["body","name"],
  "msg":"String should have at most 40 characters","input":"xxxx...",
  "ctx":{"max_length":40}}]}
`}</Terminal>

四個 Body 的錯誤都不一樣，但 `type` 這個欄位讓它們可以被程式分類：

| `type` | 意義 | Client 該做什麼 |
| --- | --- | --- |
| `missing` | 欄位沒送 | 把該欄位標成必填 |
| `string_type` | 送錯型別 | 不要轉型，請使用者重輸入 |
| `string_too_short` | 太短 | 顯示最小長度 |
| `string_too_long` | 太長 | 顯示最大長度 |

<Callout type="important" title="loc 才是重點">
  `type` 讓程式分類，`loc` 讓畫面定位。`["body","name"]` 讀成「在 Body 的 `name` 欄位」。Client 拿它去對照表單欄位，就能把紅框畫在正確的那一格。第七課那個手寫的 `{"detail":"name is required"}` 只有一句話，做不到這件事。
</Callout>

## 02. loc 會一路指進陣列裡

如果 Body 有巢狀結構，loc 會把位置一節一節記下來。這條路由的模型是：

<Terminal title="exercises/10-validation/main.py — a nested model" flavor="output">{`
class Tags(BaseModel):
    label: str
    weight: int

class PostStrict(BaseModel):
    title: str
    tags: list[Tags]
`}</Terminal>

送兩個 tag，第二個的 `weight` 寫成字串：

<Terminal title="bash — the index is in the location" flavor="output">{`
> curl -s -X POST http://127.0.0.1:8003/post-strict \\
>   -H 'Content-Type: application/json' \\
>   -d '{"title":"week 8","tags":[{"label":"a","weight":1},{"label":"b","weight":"heavy"}]}'
{"detail":[{"type":"int_parsing",
  "loc":["body","tags",1,"weight"],
  "msg":"Input should be a valid integer, unable to parse string as an integer",
  "input":"heavy"}]}
`}</Terminal>

**`["body","tags",1,"weight"]`。** 從左邊讀：`Body` → `tags` 陣列 → **索引 1**（第二個）→ `weight` 欄位。

這就是 Client 表單能做到「把第二個 tag 的權重欄位標紅」的原因，也是沒有型別宣告時永遠做不到的事。

## 03. Body 本身壞掉時，loc 指向位置

前三種是「Body 進來了，但裡面某個值不對」。還有一種是 Body 連形狀都不對：

<Terminal title="bash — three broken bodies" flavor="output">{`
# Body 是一個陣列，不是物件
> curl -s -X POST http://127.0.0.1:8003/strict \\
>   -H 'Content-Type: application/json' -d '[1,2,3]'
{"detail":[{"type":"model_attributes_type","loc":["body"],
  "msg":"Input should be a valid dictionary or object to extract fields from",
  "input":[1,2,3]}]}

# JSON 語法錯
> curl -s -X POST http://127.0.0.1:8003/strict \\
>   -H 'Content-Type: application/json' -d '{"name":'
{"detail":[{"type":"json_invalid","loc":["body",8],
  "msg":"JSON decode error","input":{},"ctx":{"error":"Expecting value"}}]}

# 完全沒送 Body
> curl -s -X POST http://127.0.0.1:8003/strict -H 'Content-Type: application/json'
{"detail":[{"type":"missing","loc":["body"],"msg":"Field required","input":null}]}
`}</Terminal>

第二個的 `loc` 是 `["body", 8]`——**第 8 個字元**是壞掉的地方。數一下 `{"name":` 正好 8 個字元。

`loc` 的形狀會變：欄位錯時是 `["body", 欄位名]`，語法錯時是 `["body", 位置]`。Client 端要能分辨這兩種，判斷方式就是看第二個成員是字串還是數字。

<Callout type="note" title="四個錯誤都發生在 handler 之前">
  注意這四個回應裡，你的 `create_strict` 一行都沒執行。Server 在比對路由之後、進入你的程式之前就把 Request 擋下來了。這是單元 3 那五個階段裡的第 03 階段。
</Callout>

## 04. 為什麼 `/loose` 同一份資料會變 500

現在換那條沒有型別宣告的路由。它的形狀是 `body: dict`，所以框架沒有任何東西可以檢查。

<Terminal title="exercises/10-validation/main.py — the hand-written route" flavor="output">{`
@app.post("/loose")
def create_loose(body: dict):
    if "name" not in body or not body["name"]:
        raise HTTPException(status_code=422, detail="name is required")
    if len(body["name"]) > 40:
        raise HTTPException(status_code=422, detail="name must be 40 characters or fewer")
    ...
`}</Terminal>

送一份缺欄位的 Body，它會得到和之前一樣的 `422`：

<Terminal title="bash — the loose route still catches the obvious case" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8003/loose \\
>   -H 'Content-Type: application/json' -d '{"role":"student"}'
< HTTP/1.1 422 Unprocessable Entity

{"detail":"name is required"}
`}</Terminal>

但送一份**型別錯**的，就不一樣了：

<Terminal title="bash — the same body that strict handled with 422" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8003/loose \\
>   -H 'Content-Type: application/json' -d '{"name":123}'
< HTTP/1.1 500 Internal Server Error
< content-type: text/plain; charset=utf-8
< content-length: 21

Internal Server Error
`}</Terminal>

`not body["name"]` 對整數 `123` 是 `False`，所以第一道檢查放行了。接著 `len(body["name"])` 對整數呼叫 `len()`，在 handler 裡拋出例外：

<Terminal title="Terminal 1 — the traceback the client never sees" flavor="output">{`
File ".../main.py", line 50, in create_loose
  if len(body["name"]) > 40:
     ^^^^^^^^^^^^^^^^^
TypeError: object of type 'int' has no len()
`}</Terminal>

**同一個 Server、同一份 Body、兩個答案。** 差別只有一件事：型別是宣告在 handler 之前，還是只能靠 handler 裡的程式碼。

<Callout type="important" title="這就是第七課那句話的完整版">
  單元 7 說「422 不是自動產生的，它出現在錯誤還沒變成例外的位置」。這裡把兩個位置放在同一個行程裡比較：宣告型別的那個位置產生 `422` 與 `loc`，手寫檢查的那個位置產生 `500` 與一句沒有用處的純文字。
</Callout>

順帶回答一個常見問題：手寫檢查一定比較差嗎？不是。手寫的 `detail` 是你自己寫的字串，你可以放任何想放的訊息。差別在於**它只能在你想得到的情況下生效**——`/loose` 漏掉了「型別不是字串」這一支，因為那個情況需要 `isinstance` 而不是 `not`。

## 05. 規則：形狀對了，規則不過

到目前為止驗證的都是形狀：型別、必填、長度。這些都能從宣告得出來，不需要看資料庫。

**規則**是另一類問題。它需要知道資料庫裡有什麼：

<Terminal title="what only a rule can answer" flavor="output">{`
形狀：name 必須是字串、長度 1 到 40
      → 宣告得出來，不需要資料庫

規則：這個 email 還沒被別人用嗎？
      這個使用者還有沒有未結清的訂單？
      這個名稱在整組使用者裡唯一嗎？
      → 必須查資料庫才知道
`}</Terminal>

`POST /users` 收到 `{"name":"iris"}` 一次，`201`。收到第二次，`409`——那是第八課看過的主鍵衝突，而它是由 SQLite 從 `name TEXT PRIMARY KEY` 丟出來的，不是一條可以寫在宣告裡的規則。

<Callout type="warning" title="不要把規則塞進 422">
  一個常見的偷懶做法是：只要驗證不過就丟 `422`，不管原因是形狀還是規則。這會讓 Client 無法分辨「把欄位改一下就好」和「這個值在系統裡已經被占用了」。單元 7 已經說過，實務上 `409` 常常被 `422` 頂替——**你有機會不要成為其中一個。**

  判斷標準：把資料修好之後，重送一次會不會成功？會，就歸形狀或規則；不會（要換一個值、或要改系統狀態），就該是 `409`。
</Callout>

順序也不能顛倒。先擋形狀，再檢規則：

<Terminal title="why shape comes first" flavor="output">{`
先驗形狀 → 再查規則

反過來會怎樣？
  送 {"name": 123}
  → 你的規則檢查先執行，len(123) 拋例外 → 500
  → 而這個 Request 從頭到尾就不該進入規則檢查
`}</Terminal>

## 06. 一個沒被擋下來的問題

這一課最後要講一個**兩種驗證都擋不住**的問題。送一個多出來的欄位：

<Terminal title="bash — the field nobody complained about" flavor="output">{`
> curl -s -X POST http://127.0.0.1:8003/strict \\
>   -H 'Content-Type: application/json' -d '{"name":"iris","admin":true}'
{"name":"iris","role":null,"source":"strict"}
`}</Terminal>

`admin: true` 送進去了，沒有任何錯誤，回應裡也沒有 `admin`。**它被安靜地丟掉了。**

這件事在兩個層級都沒有被擋下：

- 形狀沒有擋，因為 `UserStrict` 沒有宣告 `admin`，而預設行為是忽略沒宣告的欄位
- 規則沒有擋，因為根本沒有人問到它

<Callout type="warning" title="這在授權上會出事">
  如果你寫了一個只有 `user_id` 的表單，而 API 接受任何 JSON，一個被改過的 Client 可以送出 `{"user_id": 7, "is_admin": true}`。Server 不會拒絕——它會忽略那個欄位。但只要你的路由有任何一處用 `**body` 展開全部內容，或有一個沒被擋住的權限欄位在讀 request body，風險就變成真的。

  要擋，宣告模型時要明確要求：例如禁止未宣告欄位。怎麼宣告、以及這件事在單元 12 的權限邊界裡怎麼延伸，都在那裡處理。
</Callout>

## 07. XSS：形狀對了，規則也過了，然後呢

第 06 節留了一個問題：有一種東西，**形狀驗證和規則驗證都不會擋**。它是一個完全合法的字串，而且只有 25 個字，離那個欄位的 40 字上限還很遠。

<Terminal title="bash — the payload unit 10 already accepts" flavor="output">{`
> curl -s -X POST http://127.0.0.1:8003/strict \\
  -H 'Content-Type: application/json' -d '{"name":"<script>alert(1)</script>"}'
{"name":"<script>alert(1)</script>","role":null,"source":"strict"}
`}</Terminal>

`200`。形狀是對的（字串），規則也過了（25 字，在 40 以內）。

<Callout type="important" title="驗證通過，從來不等於安全">
  `max_length=40` 擋掉的是**太長的字串**，不是**危險的字串**。

  <Terminal title="bash — the same payload, one character over" flavor="output">{`
  $ python -c "print(len('<script>alert(1)</script>'))"
  25

  # 25 個字：200
  # 42 個字（同一段 payload 加上 A）：422 string_too_long
  `}</Terminal>

  同一段文字，25 個字時被接受，42 個字時被拒絕——**理由是長度，不是內容。**

  驗證做的事是「這看起來像不像 `name` 欄位」。XSS 要的是「這段文字到了 HTML 解析器手裡會變成什麼」。**兩個問題沒有重疊。**
</Callout>

### 07.1 這支 API 結構上不會有 XSS

不過先別急。在單元 01 到 10 裡，這個字串是安全的——所有 API 都回傳 JSON，而 JSON 會被 `JSON.parse()` 讀成資料結構，**不會被當成程式碼執行**。

<Callout type="important" title="和單元 12 的 CSRF 一模一樣的結構">
  | 攻擊       | 需要什麼                              | 這個課程現在有嗎 |
  | ---------- | ------------------------------------- | ---------------- |
  | CSRF       | 憑證被瀏覽器自動附上（Cookie）         | 沒有，用 Bearer    |
  | **XSS**    | 使用者文字進到 **HTML 解析器**          | **沒有，回 JSON** |

  **兩者都是「攻擊者控制的文字」被送進「會執行它的東西」。**JSON 回應裡沒有 HTML 解析器，所以 `<script>` 就是一個長度 25 的普通字串。

  所以接下來要看的不是「怎麼在 JSON API 裡防 XSS」，而是**在哪一步它會變成真的**。
</Callout>

### 07.2 漏洞需要一個 HTML 頁面

要看到差異，需要一個會把 HTML 送進瀏覽器的頁面。`xss_server.py` 是一支很小的 FastAPI，唯一的差別就是它回傳 HTML。

<Terminal title="bash — print the HTML without a browser" flavor="output">{`
$ python xss_server.py --check
--- GET /raw  name='<script>alert(1)</script>'
<h1>profile</h1><p>name: <script>alert(1)</script></p>

--- GET /escaped  name='<script>alert(1)</script>'
<h1>profile</h1><p>name: &lt;script&gt;alert(1)&lt;/script&gt;</p>
`}</Terminal>

<Callout type="warning" title="`/raw` 那一行裡的 `<script>` 是真的標籤">
  瀏覽器收到這一行的時候，HTML 解析器會把它當成一個真的 `<script>` 元素，**然後執行裡面的 JavaScript**。

  這不是「看起來像腳本」，這是「就是腳本」。`curl` 只會把字串印出來，所以要親眼看效果必須用瀏覽器：

  ```bash
  python xss_server.py
  # 然後在瀏覽器打開：
  # http://127.0.0.1:8009/raw?name=<script>alert(1)</script>
  ```

  瀏覽器會跳出 alert。同一個網址換成 `/escaped`，畫面上會出現字面的 `<script>alert(1)</script>` 這幾個字。
</Callout>

攻擊者能拿到什麼？**他讓受害者的瀏覽器，用受害者自己的權限，執行他寫的程式。**包括讀取頁面上看得到的資料、代替使用者送出表單、竊取別的 cookie（`HttpOnly` 擋得住 session cookie，但擋不住頁面上的東西）。

這跟 CSRF 的結構一模一樣：一個是「攻擊者讓瀏覽器帶著憑證送請求」，一個是「攻擊者讓瀏覽器執行程式」。**後者更嚴重，因為程式是在受害者頁面的環境裡跑的。**

不過跳出 alert 不是重點。重點是跳脫這件事有四種版本，而其中一種最像是「已經做好了」——**它的輸出裡同樣沒有任何尖括號，瀏覽器一樣看起來沒事。**

### 07.3 同一個字串，四個地方要四種跳脫

跳脫本身只差一個參數就能做對。**最危險的是「我以為我已經跳脫過了」**——`/naive-attr` 就是那種錯誤的樣子。

<Terminal title="bash — a naive escape, and what it produced" flavor="output">{`
--- GET /naive-attr  name='" onfocus=alert(1) x="'
<h1>profile</h1><input value="" onfocus=alert(1) x="">
`}</Terminal>

<Callout type="warning" title="跳脫「有做」，注入「成功」">
  這段 code 確實把 `<` 和 `>` 換掉了，所以輸出裡一個尖括號都沒有。**看起來完全防護了。**

  但送出來的 HTML 是：`<input value="" onfocus=alert(1) x="">`

  **`value` 的內容在第一個引號就結束了，`onfocus=alert(1)` 變成了一個真的屬性。**游標移進輸入框就會觸發。

  這個函式沒有做錯任何它宣稱做的事，它是**不完整**：它假設值會落在頁面本文，而這次落在屬性裡。
</Callout>

<Terminal title="bash — escaping the quotes too" flavor="output">{`
--- GET /escaped-attr  name='" onfocus=alert(1) x="'
<h1>profile</h1><input value="&quot; onfocus=alert(1) x=&quot;">
`}</Terminal>

`html.escape(name, quote=True)` 多跳脫了 `"`，所以值留在 `value` 裡面，`onfocus` 只是文字。

<Callout type="important" title="所以規則是：依「它要去哪裡」跳脫，不是依「它看起來像什麼」跳脫">
  同一個使用者文字，放的地方不同，要用的函式不同：

  | 放的位置 | 危險的是 | 正確做法 |
  | --- | --- | --- |
  | HTML 本文 | `<` `>` `&` | `html.escape(v)` |
  | 屬性值裡 | 上面全部 **加上 `"` 和 `'`** | `html.escape(v, quote=True)` |
  | URL 的查詢字串 | `&` `=` `#` 會改變查詢結構 | `urllib.parse.quote(v, safe='')` |

  比較一下就知道為什麼 HTML 的跳脫在 URL 裡是錯的：

  <Terminal title="bash — two escapes, two different answers" flavor="output">{`
  $ python -c "import html, urllib.parse; v='a&b=1#x'; \\
    print('html.escape ->', html.escape(v)); \\
    print('quote       ->', urllib.parse.quote(v, safe=''))"
  html.escape -> a&amp;b=1#x
  quote       -> a%26b%3D1%23x
  `}</Terminal>

  `html.escape` 把 `&` 變成 `&amp;`，那是**給 HTML 閱讀器**看的。URL 需要的是給**URL 解析器**看的編碼，兩者不同。
</Callout>

### 07.4 實際上你不用自己寫這段

上面這些是為了讓你看清楚規則。實際上模板引擎預設就會跳脫，所以你平常寫的程式是安全的。

<Callout type="important" title="危險的只有一種情況：明確關掉跳脫">
  各家模板引擎都有「不跳脫」寫法，長得都像：Jinja 的 `{{ name | safe }}`、Twig 的 `| raw`、Handlebars 的 `{{{ name }}}`。

  **三重括號的意思是「這段已經是安全的 HTML，直接插進來」。**所以 `{{ triple_braces(user_input) }}` 就是一個漏洞，而 `{{ double_braces(user_input) }}` 不是。

  寫法上的差別只有三個字元，安全上差一整個類別的漏洞。
</Callout>

<Callout type="note" title="為什麼模板引擎預設跳脫，而這不是壞事">
  因為「跳脫」是安全的那個選擇。預設不跳脫的話，每一個模板都會是危險的，而且要靠每個寫模板的人記得加上跳脫。

  **預設值決定了犯錯的成本。**這一點和單元 08 課的 `extra="forbid"`、單元 12 課的白名單是同一個道理：把允許的列舉出來，比擋掉危險的容易維護。
</Callout>

### 07.5 回頭看第 06 節

第 06 節那個 `admin: true` 和這裡的 `<script>`，是同一個現象的兩種面貌：

| | 形狀驗證 | 規則驗證 | 結果 |
| --- | --- | --- | --- |
| `{"admin": true}` | 通過（欄位被忽略） | 通過（沒人問） | 安靜地沒被拒絕 |
| `{"name": "<script>…"}` | 通過（是字串） | 通過（長度夠短） | 安靜地沒被拒絕 |

**上表兩列都通過了全部檢查，而且都不會讓你的程式回報任何錯誤。**

接下來兩節把證據補齊，然後回到第 06 節那個 `admin` 一起看。

<Callout type="warning" title="這一課真正要記的是順序，不是 XSS">
  驗證是**進來的門**，跳脫是**出去的門**。兩者都要，而且不能互相取代。

  - 只做驗證不做跳脫：把 `<script>` 存進資料庫，之後任何一個把它放進 HTML 的頁面就中標。
  - 只做跳脫不做驗證：使用者存了一百萬個字元的名字，資料庫和畫面都被拖慢。

  這一課的 `422` 擋的是第二種。**第一種要靠下一段那件事擋，而它跟驗證完全無關。**
</Callout>

## 08. 終端實戰驗證：同一份 Body 兩次

回頭把第 06 節與第 07 節的證據一起看清楚。Terminal 1 跑著 `fastapi dev main.py --port 8003`，下面四步每一個都留下一張截圖。

### 第一步：形狀錯，兩種答案

<Terminal title="bash — step 1">{`
curl -i -X POST http://127.0.0.1:8003/strict \\
  -H 'Content-Type: application/json' -d '{"name":123}'
curl -i -X POST http://127.0.0.1:8003/loose \\
  -H 'Content-Type: application/json' -d '{"name":123}'
`}</Terminal>

一個 `422` 一個 `500`，而 Body 完全相同。這是第一個對照。

### 第二步：看 loose 的 traceback

<Terminal title="Terminal 1 — step 2" flavor="output">{`
TypeError: object of type 'int' has no len()
`}</Terminal>

這行 Client 永遠看不到，只在你的 Terminal。

### 第三步：loc 指向陣列索引

<Terminal title="bash — step 3">{`
curl -s -X POST http://127.0.0.1:8003/post-strict \\
  -H 'Content-Type: application/json' \\
  -d '{"title":"week 8","tags":[{"label":"a","weight":1},{"label":"b","weight":"heavy"}]}'
`}</Terminal>

traceback 看完了，回到 Client 看得見的東西：比對第 02 節那個形狀，`loc` 應該逐字等於 `["body","tags",1,"weight"]`，差一個字都要找出來。

### 第四步：多出來的欄位

<Terminal title="bash — step 4">{`
curl -s -X POST http://127.0.0.1:8003/strict \\
  -H 'Content-Type: application/json' -d '{"name":"iris","admin":true}'
`}</Terminal>

比對第 06 節那個被丟掉的 `admin`：回應裡沒有它，也沒有 `422` 或 `409` 跳出來。沒有人反對過，所以它安靜地通過。

### 第五步：一個通過所有檢查的危險字串

第四步是「該擋的沒擋」。第五步是相反的方向：**每一條規則都通過了，東西還是危險。**

<Terminal title="bash — step 5, the payload passes">{`
curl -s -X POST http://127.0.0.1:8003/strict \
  -H 'Content-Type: application/json' -d '{"name":"<script>alert(1)</script>"}'
`}</Terminal>

<Terminal title="bash — step 5, and the rule that rejected it" flavor="output">{`
$ python -c "print(len('<script>alert(1)</script>'))"
25
`}</Terminal>

`200`。25 個字，遠低於 40 的上限。**沒有任何一條規則拒絕它**——因為每一條規則都在回答別的問題：長度多少、型別對不對、有沒有宣告。

### 第六步：把同一段文字放進 HTML

<Terminal title="bash — step 6, print the HTML first">{`
python xss_server.py --check
`}</Terminal>

`/raw` 的輸出裡有一個真的 `<script>` 標籤，`/escaped` 只有 `&lt;script&gt;`。**同一個字串，兩種結果。**

要親眼確認 `<script>` 標籤真的會執行，curl 做不到，因為它只會把字串印出來。**用瀏覽器：**先跑 `python xss_server.py`，再開 `http://127.0.0.1:8009/raw?name=<script>alert(1)</script>`，截圖必須包含跳出的 alert 視窗。接著打 `http://127.0.0.1:8009/escaped?name=<script>alert(1)</script>`，截圖必須顯示畫面上出現的是字面的 `<script>alert(1)</script>` 幾個字、沒有 alert。**兩張截圖並排放，這是本課的證據。**
