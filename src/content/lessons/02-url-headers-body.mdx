## 01. URI 是總稱，URL 是其中一種定位方式

你在瀏覽器網址列輸入的字串，通常叫 URL。它告訴 Client 要使用哪種協定、找哪個主機、請求哪個資源。

URI 是較大的總稱：只要一個字串能識別某個資源，就可以稱為 URI。URL 是帶有定位方式的 URI。例如 `https://example.com/users/alice` 同時是 URI 與 URL；而 `urn:isbn:9780131103627` 可以識別一本書的國際標準書號，但不告訴瀏覽器要連哪台主機，因此不是用來直接建立連線的 URL。

這條 RFC 3986 規範定義了通用的 URI 語法結構，最常見的標準形狀如下：

<Terminal title="URI — common URL shape" flavor="output">{`
scheme://[userinfo@]host[:port]/path?query#fragment
`}</Terminal>

從標準結構來看，`userinfo@`（例如 `user:password@`）雖然在語法上被允許放在主機名稱前面，但現代網路規格早已強烈棄用這種寫法；永遠不要把密碼、Token 或 API Key 暴露在網址列中。

這裡不靠空白字元對齊。每個標籤都直接指向 URL 中的實際字串；真正的語法要看分隔符號。每一段負責的事不同：

| 部分 | 例子 | Client 用它做什麼 |
| --- | --- | --- |
| `scheme` | `https` | 決定使用哪種 URI 存取方式；HTTP 網頁常見 `http` 與 `https` |
| `userinfo` | `user` | 語法上可以放在 authority 前面；不要把密碼、Token 或 API key 放進 URL |
| `host` | `api.example.com` | 找到要連線的主機名稱或 IP 位址 |
| `port` | `8443` | 指定主機上的網路入口；省略時由 scheme 的預設規則決定 |
| `path` | `/users/alice` | 指出要操作的資源路徑；最後怎麼解讀由 Server 的路由決定 |
| `query` | `active=true` | 把篩選、排序或其他參數交給 Server；它不是另一條 path |
| `fragment` | `profile` | 指向 Response 內容中的位置，由 Client 處理，不送給 Server |

`host` 是完整的主機名稱。`api.example.com` 裡的 `api` 常被叫作 subdomain，`example.com` 常被叫作 domain；這是命名與 DNS 的分工，不要把它們和 HTTP path 混在一起。

`http` 預設使用 port `80`，`https` 預設使用 port `443`。其他 scheme 也有自己的常見入口，例如本機開發常見 port `8000` 或 `3000`；這些是協定或作業系統通訊埠的約定。URL 沒寫出來，不代表連線沒有 port；Client 仍然會依照 scheme 自動選用預設入口。

如果 URL 沒寫 path，Client 會預設請求 `/`。Server 要不要把 `/` 對應到首頁或 `index.html`，是後端程式或伺服器的路由設定，不是 URL 規格自動決定的事。

### 百分比編碼（Percent-Encoding）的必要性

在網路線路傳輸時，URL 只能包含 ASCII 字元集中的未保留字元（英文字母、數字與少數符號）。

如果網址中包含中文字、特殊符號或空白鍵，Client 必須先將字元轉換為 UTF-8 位元組，再以百分比編碼（Percent-Encoding）表示。例如中文字「台」會被編碼為 `%E5%8F%B0`，空白鍵會被編碼為 `%20`。如果未經編碼直接送出，許多終端工具或舊版伺服器將直接拒絕處理並回傳 400 錯誤。

## 03. URL 怎麼變成 Request Target

接著瀏覽器或 `curl` 解析 URL 後，會把其中需要送給 Server 的部分組成 Request。`scheme` 與 `host` 會影響連線；在 HTTP/1.1 的一般 Request 中，Request Target 主要看到 path 與 query，Host 則放在 Header。

<Terminal title="HTTP — URL becomes a request" flavor="output">{`
URL:
https://httpbin.org/get?course=115&topic=uri#fragment

Request:
> GET /get?course=115&topic=uri HTTP/1.1
> Host: httpbin.org
> User-Agent: curl/8.x
>
`}</Terminal>

這裡有三個可驗證的界線：

- `https` 決定 Client 使用 TLS 保護連線。
- `httpbin.org` 出現在 `Host` Header，讓 Server 知道這個 Request 要交給哪個 host。在同一台主機掛載多個網站的虛擬主機環境中，`Host` 欄位是後端判斷目標站點的唯一依據。
- `#fragment` 沒有被送出。它是 Client 讀完 Response Body 後，用來在瀏覽器畫面上滾動定位內容的提示錨點。

<Callout type="important" title="Fragment 不是秘密通道">
  Fragment 不送到 Server，不代表整個 URL 都不會留下紀錄。`path` 與 `query` 可能出現在 Browser history、Server log、proxy log 與分析工具中。密碼、Token、API key 不要放在 URL；改用 HTTPS 也不會讓它們從 log 消失。
</Callout>

回到資料傳輸的本質，URL 與 Header 負責定位與控制，而實體資料則需要另外的承載空間。

## 04. Header 與 Body 放的不是同一種資料

Header 是 Request 或 Response 的附加欄位資訊。它描述這個訊息的格式、來源、快取條件或認證資訊。Body 則是訊息內容本身；不是每一個 Request 都有 Body。

一個讀取 Request 通常只有 Request Line 與 Header：

<Terminal title="HTTP — GET has no request body" flavor="output">{`
> GET /users/alice HTTP/1.1
> Host: api.example.com
> Accept: application/json
>
`}</Terminal>

一個建立資料的 Request 則會把資料放在 Body：

<Terminal title="HTTP — POST body" flavor="output">{`
> POST /users HTTP/1.1
> Host: api.example.com
> Content-Type: application/json
> Content-Length: 16
>
> {"name":"alice"}
`}</Terminal>

空白行把 Header 與 Body 分開。根據 HTTP 規格，連續兩組 CRLF 標記著 Header 的終點。

在常見的 Header 欄位中，`Content-Type` 告訴接收端如何解析 Body（例如 `application/json` 代表 JSON 物件，`application/x-www-form-urlencoded` 代表傳統表單），而 `Content-Length` 則指明 Body 的確切位元組長度。

<Callout type="note" title="單元 11 的狀態保持">
  當使用者完成登入時，伺服器通常會在 Response Header 中回傳 <code>Set-Cookie</code>，或是要求前端在未來的 Request Header 帶上 <code>Authorization</code> Token。
</Callout>

除了登入狀態之外，後端程式在日常開發中最頻繁處理的，就是如何精確解析網址中的路徑與查詢參數。

## 05. Path parameter、query parameter 與 FastAPI 路由

先看它們在**程式裡**長什麼樣。下面這段你先不要試著執行——`FastAPI()` 與 `@app.get(...)` 會在單元 04 才有完整說明，`BaseModel` 在單元 10。**這一節要你記住的只有一件事：path 與 query 的差異，在函式簽名裡是看得見的。**

<Terminal title="Python — FastAPI parameter types" flavor="output">{`
from fastapi import FastAPI

app = FastAPI()

# Path parameter: identifies a specific item resource
@app.get("/items/{item_id}")
def get_item(item_id: int):
    return {"item_id": item_id, "type": "path_parameter"}

# Query parameter: filters or sorts resources
@app.get("/items")
def search_items(category: str, limit: int = 10):
    return {"category": category, "limit": limit, "type": "query_parameter"}
`}</Terminal>

當 Client 送出 `GET /items/42` 時，FastAPI 會自動把路徑中的 `42` 提取並轉換為整數 `item_id`，這就是 Path Parameter（路徑參數），專門用於定位單一具體資源。

當 Client 送出 `GET /items?category=books&limit=5` 時，跟在 `?` 後面的鍵值對會被解析為函數參數 `category` 與 `limit`，這就是 Query Parameter（查詢參數），專門用於篩選、排序或分頁。

如果需要由 Client 提供一整筆新的資料物件，則會改用 POST 搭配 Request Body：

<Terminal title="Python — FastAPI request body" flavor="output">{`
from pydantic import BaseModel

class ItemCreate(BaseModel):
    name: str
    price: float

@app.post("/items")
def create_item(payload: ItemCreate):
    return {"created_name": payload.name, "created_price": payload.price}
`}</Terminal>

這三種資料傳遞方式的分工非常清晰：**Path Parameter 定義「是誰」、Query Parameter 定義「怎麼篩選」、Request Body 承載「完整資料」。**

注意上面兩個函式的差別只有一個字：`item_id: int` 是 `int`（宣告型別，單元 07 會說明宣告型別如何決定 Client 拿到 `422` 還是 `500`），`category: str` 也是。而 `limit: int = 10` 多了一個 `= 10`，那是**有預設值**，省略時 Server 直接用它。

## 06. 檔案上傳：Body 的第四種形狀

第 04 節把 Header 和 Body 分開看了，那一節的 Body 裡面放的是 JSON，而 Client 送來的就是那一段。**但 Body 不只那一種形狀。**

檔案上傳用的 Body 叫 `multipart/form-data`，它的結構跟 JSON 完全無關。先看它在線上到底是什麼：

<Terminal title="bash — every byte the server received" flavor="output">{`
$ curl -s -F "note=hello" -F "file=@a.txt" http://127.0.0.1:8011/raw
{"bytes":317,"boundary":"------------------------qsdGfN3QkHUZiOkfobrXUX","parts":2}

--- raw body as received ---
--------------------------HI1hbqi37krL3waUapIorr
Content-Disposition: form-data; name="note"

hello
--------------------------HI1hbqi37krL3waUapIorr
Content-Disposition: form-data; name="file"; filename="a.txt"
Content-Type: text/plain

line one
line two

--------------------------HI1hbqi37krL3waUapIorr--

--- end ---
`}</Terminal>

<Callout type="important" title="四個地方跟 JSON 不一樣">
  1. **Header 裡多了一個 `boundary=`。**它出現在 `Content-Type` 的最後，是一個分隔字串。
  2. **每一段都有自己的 Header**，然後空一行，再來才是資料。JSON 沒有「每一段各自的 Header」這回事。
  3. **分隔字串在兩種長度。**中間用 `------abc` 分開，最後一段用 `------abc--`，**多兩個破折號**，那是「結束了」的標記。
  4. **資料可以是二進位。**換行、引號、大括號、看起來像 Header 的行，全都不能拿來當分隔。

  然後 `Content-Disposition` 裡的 `name="note"` 和 `name="file"`，就是 JSON 裡的 key。**只不過在這裡，key 是用文字標出來的，不是用文法推導的。**
</Callout>

### 06.1 為什麼需要 boundary：JSON 不需要

這是這一段唯一需要想清楚的地方：**JSON 不需要分隔字串，檔案需要，差別只在一件事。**

<Terminal title="bash — why the delimiter exists" flavor="output">{`
$ python multipart_demo.py boundary
2. Why a boundary exists at all

   JSON needs no delimiter. This is well defined:
     {"note": "hello", "count": 3}
        ^     ^        ^
   The parser knows a string starts at a quote and ends at the next
   quote, so it can tell where one value ends and the next begins.

   A file has no such rule. It can be any bytes at all, including:
     newlines, quotes, braces, a line that looks like a header,
     and 200 MB of a JPEG with no particular structure.

   So the sender invents a string that does not occur in the data, and
   writes it between the parts. That is the entire job of a boundary.
`}</Terminal>

<Callout type="important" title="JSON 的文法自帶邊界，檔案不會">
  JSON 的文法是**自定界的**：字串從引號開始、到下一個引號結束，所以解析器永遠知道現在在第幾個值。

  **檔案沒有文法。**它就是一堆位元組，可能剛好包含換行、包含看起來像 `boundary=------` 的那一行。

  所以發送端自己挑一個**不會出現在資料裡**的字串，把它寫在中間當分隔。**boundary 的全部工作就是這一句。**

  而且實務上是隨機產生的，因為猜得到等於可以偽造：

  <Terminal title="bash — two requests, two boundaries" flavor="output">{`
  $ curl -s -o /dev/null -v -F "note=x" -F "file=@a.txt" http://127.0.0.1:8011/upload
  > Content-Type: multipart/form-data; boundary=------------------------xcC7iQbGk8RzHtSTfIFioX

  $ curl -s -o /dev/null -v -F "note=x" -F "file=@a.txt" http://127.0.0.1:8011/upload
  > Content-Type: multipart/form-data; boundary=------------------------r1rLqWLpb5ttcI8dYHQ6MW
  `}</Terminal>
</Callout>

### 06.2 自己解析一次，就不用框架了

<Terminal title="bash — splitting the body by hand" flavor="output">{`
$ python multipart_demo.py parse
3. Reading it back, without any framework

   body is 209 bytes
   delimiter is b'------abc123'
   split gives 4 pieces, and the first and last are empty:
     [0] b''
     [-1] b'--\r\n'

   part:
     Content-Disposition: form-data; name="note"
     data: b'hello'

   part:
     Content-Disposition: form-data; name="file"; filename="a.txt"
     Content-Type: text/plain
     data: b'line one\r\nline two'
`}</Terminal>

<Callout type="important" title="`data: b'line one\r\nline two'` 那一行才是重點">
  資料**裡面有換行**，而且沒有被切開。

  因為規則是：**分隔字串必須自己站在一行開頭。**中間那些換行不會讓解析器困惑，因為它認的是「整行等於 boundary」而不是「某處出現 boundary 這幾個字」。

  如果資料裡剛好有一行的開頭就是 boundary，那格式就毀了。**這就是為什麼那個字串要隨機產生。**
</Callout>

### 06.3 一個你會先撞到的框架行為

分隔字串講完了，接下來是一個很實務的問題：**你想自己印出原始 bytes**。你會先寫成這樣：

```python
@app.post("/upload")
async def upload(request: Request, note: str = Form(...), file: UploadFile = File(...)):
    raw = await request.body()      # RuntimeError: Stream consumed
```

<Terminal title="Terminal — what actually happens" flavor="output">{`
RuntimeError: Stream consumed
`}</Terminal>

<Callout type="warning" title="宣告了 Form，就等於宣告「body 給我，不要了」">
  你一旦宣告 `note: str = Form(...)`，框架就會**自己把 body 讀走並解析**，之後 `request.body()` 拿不到東西了——它不是回傳空值，是直接拋錯。

  Request 的 body 是一道**一次性的流**，不是可以重讀好幾次的屬性。

  所以要看原始 bytes，必須走一條**什麼都不宣告**的路徑：

  <Terminal title="multipart_demo.py — two routes on purpose" flavor="output">{`
  @api.post("/raw")
  async def raw_body(request: Request):
      body = await request.body()          # nothing declared, so nothing consumed
      ...

  @api.post("/upload")
  async def upload(note: str = Form(...), file: UploadFile = File(...)):
      ...
  `}</Terminal>

  **這是本節最實用的一段。**之後你要除錯任何 multipart 的問題，都需要這條「不解析、看原始」的路徑。
</Callout>

### 06.4 唯一絕對不能相信的欄位

<Terminal title="bash — the field the client chose" flavor="output">{`
$ python multipart_demo.py filename
4. The one field you must never trust
   filename="a.txt"          <- fine
   filename="../../../etc/passwd"   <- the header said so

   Content-Disposition comes from the Client. It is text the Client
   chose, not a fact about a file on your disk.

   So this is wrong:
     path = UPLOAD_DIR / upload.filename      # traversal, straight up

   And this is right:
     path = UPLOAD_DIR / (uuid4().hex + suffix)
`}</Terminal>

<Callout type="important" title="`filename` 是 Client 寫的一段文字">
  它跟 `{"name": "iris"}` 裡的 `name` 性質**完全一樣**：都是外面進來的資料。

  差別只在於 `name` 放在 Body 的 JSON 裡你還會想一想，`filename` 放在一個看起來「像檔案資訊」的 Header 裡，就容易當成事實。**它不是事實，它是對方給你的一個字串。**

  這正好接上單元 08 第 07 節那個 `role = 'admin', name`：值可以安全地被綁進 SQL，欄位名不行，因為欄位名沒有地方可以綁。**檔名也是同一類問題——它決定檔案落在哪裡，所以它是指令，不是資料。**
</Callout>

<Callout type="note" title="還沒講、但你會遇到的">
  - **大小限制。**沒有設上限的話，一個 10 GB 的檔案會把磁碟塞滿。`Content-Length` 可以被說謊，所以要在讀的時候累加計數。
  - **檔案型別。**副檔名和 `Content-Type` 都是 Client 給的。真的要看內容，就讀開頭幾個位元組判斷 magic number。
  - **不要放在可被執行的目錄。**上傳目錄不該跟程式碼同一層。
</Callout>

## 07. 終端實戰驗證：用 curl 觀察傳輸界線

現在打開終端機，執行以下四組具代表性的指令，逐一驗證網址與封包在傳輸線路上的真實面貌：

### 第一步：驗證 Fragment 永遠不進網路線

執行帶有 `#fragment` 的網址：

<Terminal title="bash — verify fragment">{`
curl -v 'https://httpbin.org/get?course=115&topic=uri#fragment'
`}</Terminal>

觀察輸出中的 `> GET` 這一行：你會發現 Request Target 只有 `/get?course=115&topic=uri`，後方的 `#fragment` 被 curl 在本地直接忽略。

### 第二步：驗證 Path 與 Query 的伺服器回顯

向 httpbin 的萬用回顯路徑發出請求：

<Terminal title="bash — path vs query echo">{`
curl -v 'https://httpbin.org/anything/users/alice?active=true'
`}</Terminal>

觀察伺服器回傳的 JSON 結構：在 `url` 欄位中可以看到完整路徑與參數，而在 `args` 物件中可以看到伺服器把 `active: "true"` 正確解析為獨立參數。

### 第三步：發送帶有 JSON Body 的 POST 請求

用 curl 發送一個帶有 Header 與 Body 的完整 Request：

<Terminal title="bash — post with json body">{`
curl -i -X POST 'https://httpbin.org/anything/users' \\
  -H 'Content-Type: application/json' \\
  -d '{"name":"alice","role":"student"}'
`}</Terminal>

觀察輸出內容：在 Request Header 中帶上了 `Content-Type: application/json`，中間間隔了一個空白行，下方則是長度精確對應的 JSON Body 字串。

### 第四步：觀察百分比編碼的傳輸效果

發送包含中文編碼的查詢參數：

<Terminal title="bash — test percent encoding">{`
curl -v 'https://httpbin.org/get?query=%E5%8F%B0%E7%81%A3'
`}</Terminal>

這時伺服器回傳的 JSON 會顯示接收到的 `args` 為 `query: "台灣"`，證明了線路上雖然只傳遞 ASCII 百分比碼，伺服器接收後能精準還原為原始中文。

### 第五步：看一個不是 JSON 的 Body

前四步的 Body 都是 JSON。第五步換成檔案，而且要看原始 bytes，所以先把 Server 起來。

先開一個 Terminal 起 Server：

```bash
cd exercises/02-url
printf 'line one\nline two\n' > /tmp/a.txt
python multipart_demo.py serve
```

Terminal 2 送兩次**內容相同**的表單，但打的是**不同兩條路由**：

<Terminal title="bash — step 5, two routes, same form">{`
$ curl -s -F "note=hello" -F "file=@/tmp/a.txt" http://127.0.0.1:8011/raw
{"bytes":317,"boundary":"------------------------qsdGfN3QkHUZiOkfobrXUX","parts":2}

$ curl -s -F "note=hello" -F "file=@/tmp/a.txt" http://127.0.0.1:8011/upload
{"note":"hello","filename":"a.txt","content_type":"text/plain","file_bytes":18}
`}</Terminal>

兩點要親眼看到：

- **`/raw` 的回應裡有 `boundary`，而且每次都不一樣。**再送一次 `/raw`，比對 `boundary` 兩個字串。
- **Terminal 1 印出了原始 body。**截圖必須包含 `------` 開頭的分隔行和最後那個多兩個破折號的 `------`。
