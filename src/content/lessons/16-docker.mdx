單元 17 要把一支 API 送上 VPS。在那之前，必須先回答一個問題：**送上機器的到底是什麼？**

送上機器的是一個 image，一個已經裝好所有東西、可以被完整複製與刪除的檔案系統快照。不是一個 `python main.py` 的指令。

這個 repo 已經有一個寫好的 `Dockerfile`，先看它的前五層再說「送上機器的是什麼」：

<Terminal title="examples/http-api/Dockerfile">{`
FROM python:3.14-slim AS base

ENV PYTHONDONTWRITEBYTECODE=1 \\
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
`}</Terminal>

先建起來：

<Terminal title="Terminal 1 — bash — build the base image">{`
cd examples/http-api
docker build --target base -t lesson16-base .
`}</Terminal>

## 01. 一個 image 是什麼

`docker build` 跑完之後，你得到一個可以搬走的檔案系統。先確認它真的存在：

<Terminal title="Terminal 2 — bash — what did we just build" flavor="output">{`
> docker images lesson16-base
REPOSITORY      TAG       IMAGE ID       CREATED         SIZE
lesson16-base   latest    225a001f4ec7   14 seconds ago   306MB
`}</Terminal>

**306MB。**這不是錯的——裡面有完整的 Python 3.14、FastAPI 和它的相依套件。

這就是 image 的本質：**一個自帶所有東西的檔案系統。**它不需要在目標機器上裝 Python、不需要記得版本、不需要連網下載相依套件。

<Callout type="important" title="「帶著所有東西」是關鍵">
  沒有容器的話，你把程式碼交給別人，他要在自己的機器上裝對的 Python 版本、對的套件版本、對的系統套件，然後祈禱你的 `python main.py` 會動。

  有容器的話，他拿到的是那 306MB 的東西本身。**「在我電腦上可以跑」這個問題從此不存在**，因為「我的電腦」已經被包含在交付物裡了。
</Callout>

## 02. 容器不是小電腦，它有自己的 127.0.0.1

現在做這一課最重要的一個實驗。先把**你要送上機器的那一個** image 建成出來：

<Terminal title="Terminal 1 — bash — build the stage that actually runs" flavor="output">{`
docker build --target runtime -t lesson16-runtime .
`}</Terminal>

<Terminal title="why runtime and not base" flavor="output">{`
> docker inspect lesson16-base --format 'base    Cmd={{json .Config.Cmd}}'
base    Cmd=["python3"]

> docker inspect lesson16-runtime --format 'runtime Cmd={{json .Config.Cmd}}'
runtime Cmd=["fastapi","run","main.py","--host","0.0.0.0","--port","8000",...]
`}</Terminal>

`base` 階段沒有 `CMD`，它繼承到的是 `python3.14-slim` 的預設值。**用 `docker run` 跑它，容器會立刻結束**，因為沒有東西告訴它要啟動伺服器。

`runtime` 階段才有 `CMD`，也有 `USER appuser`。這就是第 05 節要講的差別：base 是共用的底，runtime 才是你真的部署的東西。

現在把容器跑起來：

<Terminal title="Terminal 2 — bash — run it and publish one port" flavor="output">{`
> docker rm -f l16
> docker run -d --name l16 -p 127.0.0.1:8016:8000 lesson16-runtime
> docker port l16
8000/tcp -> 127.0.0.1:8016
`}</Terminal>

`-p 127.0.0.1:8016:8000` 讀法是：**把容器的 8000，發布成主機的 8016。**

現在從主機打它：

<Terminal title="bash — from the host, it works" flavor="output">{`
> curl -s -i http://127.0.0.1:8016/health
< HTTP/1.1 200 OK

{"ok":true}
`}</Terminal>

接著，**進到容器裡面，用同一個位址打**：

<Terminal title="bash — from inside the container, the same address fails" flavor="output">{`
> docker exec l16 python -c "
import urllib.request
try:
    urllib.request.urlopen('http://127.0.0.1:8016/health', timeout=3)
except Exception as e:
    print('port 8016 ->', type(e).__name__)
print('port 8000 ->', urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=3).status)
"
port 8016 -> URLError
port 8000 -> 200
`}</Terminal>

**同一個字串 `127.0.0.1`，在主機和在容器裡指的是不同的機器。**

容器的 `127.0.0.1` 是容器自己。而容器的檔案系統裡，沒有主機那個 8016 埠——那個埠存在於主機的網路堆疊，而容器有自己的網路命名空間。

<Callout type="warning" title="這個差別會咬人，而且症狀很像「程式壞了」">
  常見的錯誤是：健康檢查寫成主機上的位址，於是容器一直回報不健康，但應用程式其實好好地在跑。

  或者反過來：應用程式裡寫 `http://127.0.0.1:5432` 連資料庫，在容器裡會連到**容器自己**的 5432，不是資料庫。PostgreSQL 在另一個容器時，要用服務名稱連，不是 `127.0.0.1`。

  **判斷規則：`127.0.0.1` 永遠只指「我現在所在的這台機器」。**容器有自己的 `127.0.0.1`，和主機無關。
</Callout>

## 03. log 裡的 IP 是誰

單元 15 講過 access log 會記來源 IP。在容器裡，那個 IP 是誰？

<Terminal title="Terminal 1 — bash — watch the access log" flavor="output">{`
> docker logs l16
INFO:     Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
INFO:     192.168.215.1:49432 - "GET /health HTTP/1.1" 200 OK
`}</Terminal>

`192.168.215.1` 不是你的筆電 IP，也不是 `127.0.0.1`。它是 docker 網路裡的閘道位址。

**這是單元 15 那個警告的實例。**你若靠 access log 的 IP 做稽核，在容器環境裡會記到一個完全沒有意義的位址。

那怎麼拿到真實的來源？改用 proxy 傳來的 Header，而單元 15 提過的那個 `X-Forwarded-For` 就是它的來源，這支 API 的 Dockerfile 已經開了：

<Terminal title="Terminal 2 — bash — the proxy headers actually work" flavor="output">{`
> curl -s http://127.0.0.1:8016/request-info
{"client":"192.168.215.1","scheme":"http","host":"127.0.0.1:8016"}

> curl -s -H 'X-Forwarded-For: 203.0.113.9' -H 'X-Forwarded-Proto: https' \\
>   http://127.0.0.1:8016/request-info
{"client":"203.0.113.9","scheme":"https","host":"127.0.0.1:8016"}
`}</Terminal>

<Callout type="note" title="`--proxy-headers` 不是開關，是信任宣告">
  `fastapi run --proxy-headers --forwarded-allow-ips=*` 的意思是「**我假設所有連到我的人都可信賴，他們帶的 `X-Forwarded-For` 就是真的**」。

  上面那個 `203.0.113.9` 是我隨便 `curl` 出來的，應用程式照單全收。**只有在後面確實有一台可信 proxy 會覆寫這個 Header 時，才可以這樣開。**如果 port 8000 直接暴露在 internet 上又開了這個參數，任何人都能偽造自己的 IP。

  這個 repo 的做法是安全的：`compose.yaml` 把埠綁在 `127.0.0.1:8000`，所以外部連不到，只能從同機的 nginx 進來。單元 17 會驗收這個邊界。
</Callout>

## 04. 兩個 ENV 決定 log 能不能看

Dockerfile 第二行有兩個環境變數，它們不是裝飾，而且第一個直接決定你看不看得到 log：

<Terminal title="bash — confirm they are set in the image" flavor="output">{`
> docker exec l16 python -c "
import os
print('PYTHONUNBUFFERED      =', os.environ.get('PYTHONUNBUFFERED'))
print('PYTHONDONTWRITEBYTECODE =', os.environ.get('PYTHONDONTWRITEBYTECODE'))
"
PYTHONUNBUFFERED      = 1
PYTHONDONTWRITEBYTECODE = 1
`}</Terminal>

第一個就是 log 能不能看的關鍵。`PYTHONUNBUFFERED=1` 讓 Python 的輸出**不緩衝**。沒有它，`print()` 會被累積到一個區塊大小才送出，於是 `docker logs` 會出現「什麼都沒有，然後突然一大段」的情況。你會以為 log 壞了。

`PYTHONDONTWRITEBYTECODE=1` 讓 Python 不寫 `__pycache__`。容器裡沒有「重跑一次會變快」的需求，而那些檔案只會讓 image 變大。

<Callout type="important" title="log 是容器的標準輸出，不是檔案">
  `docker logs` 讀的是容器的 stdout/stderr。這代表兩件事：

  應用程式的 `print()` 和 `logging` 輸出會自動被收集，**你不需要寫任何檔案，也不需要設定 log 輪替**——那會交給容器執行環境處理。
  但也代表**把 log 寫進檔案再 `tail` 是多餘的**，而且會讓 log 脫離 `docker logs` 的視野。單元 17 的 `docker compose logs --tail=100 api` 就是讀這條標準輸出。
</Callout>

## 05. 為什麼要分兩個 stage

Dockerfile 有三個 stage：`base`、`test`、`runtime`。`base` 只有一個 runtime image 大小是 306MB，而且**沒有 pytest**：

<Terminal title="bash — the runtime image has no test tooling" flavor="output">{`
> docker run --rm lesson16-runtime python -c "import pytest"
ModuleNotFoundError: No module named 'pytest'
`}</Terminal>

這是刻意的。`test` stage 裝了測試工具，`runtime` stage 從 `base` 重新分支，只裝執行時真正需要的東西。

<Callout type="note" title="stage 不是三個 image，是三份 build 說明">
  `runtime` 沒有繼承 `test`，它繼承的是 `base`。Docker 只會建 `runtime` 實際用到的部分，而且把相同的那層共用一份。

  分開的好處是**攻擊面**：執行時不需要的工具，就不會在執行時的環境裡。`docker history lesson16-runtime` 可以看到實際組成的層，那 81.8MB 是 `pip install`，53.2MB 是 `useradd`。
</Callout>

順便看那個 `useradd`。這是另一個刻意的決定：

<Terminal title="bash — base runs as root, runtime does not" flavor="output">{`
> docker run --rm lesson16-base whoami
root

> docker run --rm lesson16-runtime whoami
appuser
`}</Terminal>

**如果程式被塞住，攻擊者拿到的預設身分不是 root。**這是單元 11 講的「權限邊界」在部署層的版本——同樣的道理，只是對象從使用者變成行程。

## 06. 容器裡有幾個檔案

<Terminal title="bash — the filesystem is only what was COPYed" flavor="output">{`
> docker exec l16 ls /app
main.py
requirements.txt

> docker exec l16 ls /app/tests
ls: cannot access '/app/tests': No such file or directory
`}</Terminal>

那個非 root 的身分還擋掉了一整類問題：`/app` 只有兩個檔案。**Dockerfile 沒有 `COPY` 進去的東西，容器裡就沒有。**沒有 `.git`、沒有 `README`、沒有 `__pycache__`、沒有你的 `.env`。

這是 `.dockerignore` 的工作：

<Terminal title="examples/http-api/.dockerignore">{`
__pycache__/
*.py[cod]
.env
.git
.venv/
venv/
`}</Terminal>

<Callout type="important" title="`.env` 在這份清單裡，而且這不是可選的">
  單元 12 講過簽發金鑰必須從環境變數來，因為寫在檔案裡就會進 Git。

  **`.dockerignore` 保護的是另一條路徑。**沒有它，`docker build` 會把整個目錄送進 build context，而 `.env` 會變成 image 的一層——然後 `docker push` 就把它送上了 registry。Git 裡刪掉也沒用，因為 image 裡已經有了。

  同一個原則的兩個出口：**Git 和 image 都會把檔案帶走，所以兩個都要擋。**
</Callout>

## 07. 健康檢查寫在哪裡

最後一件實務上的事，是這份 image 怎麼宣告自己活著。`compose.yaml` 裡有一個 health check：

<Terminal title="examples/http-api/compose.yaml — the healthcheck" flavor="output">{`
    healthcheck:
      test:
        - CMD
        - python
        - -c
        - "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')"
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 10s
`}</Terminal>

注意那個位址是 **`127.0.0.1:8000`**，也就是容器自己的埠。這正是第 02 節的結論：這個檢查是**在容器內部執行**的，所以 `127.0.0.1` 對它來說就是正確答案。

順帶一件我原本以為會在 image 裡、其實不會的事：

<Terminal title="bash — HEALTHCHECK lives in compose, not in the image" flavor="output">{`
> docker inspect lesson16-runtime --format '{{json .Config.Healthcheck}}'
null
`}</Terminal>

**`Dockerfile` 沒有 `HEALTHCHECK` 指令，這份健康檢查是 compose 提供的。**兩者都能定義，差別在於 compose 的定義會隨著 `docker compose up` 一起生效，不需要 `docker run` 時手動加參數。

<Callout type="note" title="這個檢查有效嗎？確認一下它抓得到壞掉的狀態">
  健康檢查最常見的失效方式是「永遠通過」——它檢查的東西根本不會壞，所以它只是一個裝飾。

  這個檢查是真的會失敗的：

  ```
  > docker exec l16 python -c "
  import urllib.request
  try:
      urllib.request.urlopen('http://127.0.0.1:9999/health', timeout=2)
  except Exception as e:
      print('dead port ->', type(e).__name__)
  "
  dead port -> URLError
  ```

  它打的是真的 HTTP、真的 port。程式沒起來，它就失敗。**判斷標準是：把 port 改錯，它會不會紅？**不會的話，那不是健康檢查。
</Callout>

`interval`、`timeout`、`retries`、`start_period` 各自回答一個問題：

| 設定 | 回答的問題 |
| --- | --- |
| `interval: 30s` | 多久檢查一次 |
| `timeout: 3s` | 多久算它沒回來 |
| `retries: 3` | 連續失敗幾次才判定不健康 |
| `start_period: 10s` | 剛啟動的前 10 秒內不要判失敗 |

最後一個最容易忘記。**沒有它，一個正常的慢啟動會先被判成不健康，然後被 restart，然後永遠起不來。**

## 08. 終端實戰驗證

那個 `start_period` 防止的「一直起不來」，值得自己驗一次。Terminal 1 跑著 `docker build`，Terminal 2 跑下面六組。

1. `docker images lesson16-base` 的截圖，必須包含大小。回答：一個 image 裡包含了什麼，讓它不需要在別的機器上安裝任何東西？
2. `docker run -d --name l16 -p 127.0.0.1:8016:8000 lesson16-runtime` 然後 `docker port l16`，截圖必須包含 `8000/tcp -> 127.0.0.1:8016`。
3. `curl -s http://127.0.0.1:8016/health`（必須 `200`）與 `docker exec l16 python -c "...urlopen('http://127.0.0.1:8016/health')"`（必須 `URLError`）**兩張截圖並排**。回答：同一個字串，為什麼在兩邊意思不同？
4. `docker logs l16 | tail -3` 的截圖，必須包含一個 `192.168.x.x` 的 IP。回答：那是誰的位址？單元 15 的警告在這裡具體長什麼樣？
5. `docker exec l16 ls /app` 與 `docker exec l16 ls /app/tests`（必須失敗）的截圖。回答：`.dockerignore` 裡的 `.env` 這一行，擋掉的是哪一條路徑？
6. `docker exec l16 python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health').status)"` 的截圖，必須 `200`。回答：為什麼健康檢查要寫 `8000` 而不是 `8016`？

## 單元實作作業

在本地環境完成以下八項操作，每一項的截圖與簡答都記錄下來。

1. `docker build --target base` 的完整輸出截圖（必須包含 `DONE`）+ `docker images` 的大小。回答：如果目標機器沒有 Python，image 裡的 306MB 扮演的是什麼角色？
2. `docker run` 與 `docker port` 的截圖（必須含 `8000/tcp -> 127.0.0.1:8016`）。回答：`8016` 這個數字是誰決定的？改成 `9000:8000` 會影響到容器裡的程式嗎？
3. 從主機 `curl 127.0.0.1:8016/health` 得 `200`，從容器內 `curl 127.0.0.1:8016/health` 得 `URLError`，**兩張截圖並排**。回答：容器的網路和主機的網路是同一個嗎？用「網路命名空間」這個詞回答。
4. `docker logs` 裡的 `192.168.x.x` 截圖 + 用 `curl -H 'X-Forwarded-For: 203.0.113.9'` 證明 `request-info` 會回那個 IP。回答：這個 Header 可以被誰偽造？Dockerfile 為什麼敢開 `--proxy-headers`？
5. `docker exec l16 whoami` 對 `lesson16-base`（`root`）與 `lesson16-runtime`（`appuser`）兩張截圖。回答：如果程式被塞住，這個差異保護了什麼？
6. `docker exec l16 ls /app` 與 `ls /app/tests` 失敗的截圖。回答：`.env` 被 `docker build` 送進 image 和被 `git add` 進 repo，是同一個問題的兩個出口嗎？各自該在哪裡擋？
7. 把 `compose.yaml` 的 healthcheck 埠從 `8000` 改成 `8016`，`docker compose up` 之後 `docker compose ps` 的 STATUS 會變成什麼？截圖必須包含那個狀態。改回去之後說明：`start_period` 存在的原因是什麼？
8. 回答：以下四個檔案該不該進 `.dockerignore`？各用一句話說明。`.git/`、`__pycache__/`、`.env`、你的作業截圖資料夾。其中一個的答案取決於它是什麼，你會怎麼分辨？

把作業截圖與簡答筆記存入 `exercises/16-docker/`，並以 Git 提交至個人儲存庫。提交前執行 `git status`，確認只包含作業檔案。

`examples/http-api/Dockerfile`、`compose.yaml` 與 `.dockerignore` 是這門課的教材，第 7 題改完必須改回去。**不要**把任何真實憑證或 `.env` 檔案加進版本控制。
