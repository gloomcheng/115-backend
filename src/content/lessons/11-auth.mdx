## 01. 無狀態留下來的洞

第一課講過「每一次 Request 都是獨立的」，那個協定層的規則現在有具體後果了。

登入之後拿到一枚 token，然後把它拿掉：

<Terminal title="bash — the same route, with and without the token" flavor="output">{`
> curl -i http://127.0.0.1:8004/private
< HTTP/1.1 401 Unauthorized
< www-authenticate: Bearer realm="lesson-11"

{"detail":"Missing credentials"}

> curl -i http://127.0.0.1:8004/private \\
>   -H "Authorization: Bearer $TOKEN"
< HTTP/1.1 200 OK

{"secret":"only a signed-in user sees this","sub":"iris"}
`}</Terminal>

同一條路徑、同一個 Server、兩次不同的結果。**差別只在 Request 裡有沒有那個 Header。**

這就是無狀態的實際樣貌：Server 沒有「登入狀態」這種東西可以保存。`POST /login` 那一次並沒有讓 Server 記住 iris —— 它只是**交給 Client 一份可以重複出示的證明**，之後每個 Request 都由 Client 自己帶上。

<Callout type="important" title="這一課的主詞是 Client，不是 Server">
  很多人以為「登入」是 Server 記住了你。實際上是 Client 記住了那枚 token，而且願意每次都帶著它。「登入狀態」存在 Client 端與網路上的那串字裡，不存在 Server 裡。
</Callout>

## 02. JWT 是什麼：base64 加 HMAC，沒有別的

這支 API 沒有安裝任何 JWT 套件。簽發與驗證都在 `exercises/11-auth/main.py` 裡，用的是 Python 標準庫：

<Terminal title="exercises/11-auth/main.py — issuing a token" flavor="output">{`
def sign(header: dict, payload: dict) -> str:
    header_part = b64encode(json.dumps(header, separators=(",", ":")).encode())
    payload_part = b64encode(json.dumps(payload, separators=(",", ":")).encode())
    signature = b64encode(
        hmac.new(SECRET, f"{header_part}.{payload_part}".encode(), hashlib.sha256).digest()
    )
    return f"{header_part}.{payload_part}.{signature}"
`}</Terminal>

三段，用點號隔開：

<Terminal title="JWT — the shape" flavor="output">{`
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJpcmlzIiwi... . Z-Se3QP8ajcLOd5j...
└───────────── header ─────────────┘   └────── payload ──────┘   └─── signature ───┘
               base64url                        base64url              HMAC-SHA256
`}</Terminal>

<Callout type="note" title="為什麼不用套件">
  這不是要你重新發明 JWT 庫，是要你看見它沒有魔術。整份「加密的登入憑證」實際上就是兩段 JSON 做 base64 編碼，加上一段用密鑰算出來的簽名。知道這三段怎麼組出來的，你才知道哪一段可以信任、哪一段不能。
</Callout>

**沒有金鑰。沒有 Server。沒有任何權限。** 任何拿到這串 token 的人，都看得到 `role` 是 `student`、它是什麼時候發的、什麼時候到期。

`iat` 和 `exp` 那兩個數字是你這台機器的時鐘，跑出來會不一樣。**它們仍然擋在 payload 裡、仍然不用金鑰就能讀**，而那才是這一節要證明的事。

base64 不是加密。它是一種編碼——把位元組換成可以塞進 URL 的字元，**不需要金鑰就能還原**。單元 2 講過 `path` 裡的百分比編碼，那是同一類的東西。

<Callout type="warning" title="所以永遠不要把秘密放進 JWT 的 payload">
  密碼、身分證號碼、信用卡、內部使用者 ID 以外的機密——都不能放。JWT 的 payload 是公開的，任何中介（反向代理、CDN、log 收集器）只要看一眼 Header 就會記下來。

  JWT 簽名的作用是**防篡改**，不是**防偷看**。要同時做到兩件事，需要 JWE 那類的加密格式，而那已經超出這門課的範圍。
</Callout>

## 04. 簽名擋的是篡改

既然 payload 不用密鑰就能還原，第二個問題就跟著來了：那可不可以**改**？

可以，而且「可以改」正是第三段存在的理由：改完 payload 之後，第三段就對不上了。用 Python 把 `role` 從 `student` 改成 `admin`，然後把改過的 token 送回去：

<Terminal title="bash — hand-edit the role" flavor="output">{`
$ python - > /tmp/tampered.txt <<'PY'
import base64, json, os

head, payload, sig = os.environ["TOKEN"].split(".")
data = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
data["role"] = "admin"
tampered_payload = (
    base64.urlsafe_b64encode(json.dumps(data, separators=(",", ":")).encode())
    .rstrip(b"=")
    .decode()
)
print(f"{head}.{tampered_payload}.{sig}")
PY

$ curl -i http://127.0.0.1:8004/admin \\
>   -H "Authorization: Bearer $(cat /tmp/tampered.txt)"
< HTTP/1.1 401 Unauthorized
< www-authenticate: Bearer realm="lesson-11"

{"detail":"Bad signature"}
`}</Terminal>

Server 收到的 `role` 已經是 `admin`，但它回的是 `401` 加 `Bad signature` —— 連「你是不是管理員」都還沒輪到判斷。

所以 Server 做的只有一件事：用同一把密鑰對 `header.payload` 重新算一次簽名，然後比對。

<Terminal title="exercises/11-auth/main.py — verifying a token" flavor="output">{`
def read_token(token: str) -> dict:
    header_part, payload_part, signature = token.split(".")
    expected = b64encode(
        hmac.new(SECRET, f"{header_part}.{payload_part}".encode(), hashlib.sha256).digest()
    )
    # Compare in constant time so the check does not leak the expected value.
    if not hmac.compare_digest(signature, expected):
        raise HTTPException(status_code=401, detail="Bad signature", headers=CHALLENGE)
    ...
`}</Terminal>

你改了 payload，`header.payload` 就變了，算出來的簽名跟第三段不再相同。**Server 手上沒有任何東西可以還原你的 payload —— 但它有密鑰可以證明這段 payload 沒被動過。**

<Callout type="important" title="簽名能證明沒被動過，不能證明是誰給你的">
  簽名沒有「只有我能發出這枚 token」以外的意義。任何拿到密鑰的人都能簽發任何內容，而拿到 token 的人可以重複使用它到過期為止。這兩件事的差別，是單元 12 要處理的。
</Callout>

## 05. 401 與 403：兩個問題，兩組證據

現在回到這堂課的標題。先用學生 token 打一個只有管理員能用的路徑：

<Terminal title="bash — authenticated but not allowed" flavor="output">{`
> curl -i http://127.0.0.1:8004/admin \\
>   -H 'Authorization: Bearer <學生的 token>'
< HTTP/1.1 403 Forbidden
< content-type: application/json

{"detail":"Admins only"}
`}</Terminal>

`403`。**注意 Header：`www-authenticate` 不見了。**

換成管理員的 token：

<Terminal title="bash — authenticated and allowed" flavor="output">{`
> curl -i http://127.0.0.1:8004/admin \\
>   -H 'Authorization: Bearer <管理員的 token>'
< HTTP/1.1 200 OK

{"admin_panel":true,"sub":"root"}
`}</Terminal>

把四種情況並排：

| 情況 | Status Code | `WWW-Authenticate` | 誰該修 |
| --- | --- | --- | --- |
| 沒帶 token | `401` | 有 | Client 要重新登入 |
| 密碼錯 | `401` | 有 | 使用者要重打密碼 |
| 簽名被改過 | `401` | 有 | 有人嘗試偽造，該記錄 |
| 過期 | `401` | 有 | Client 換一枚新的 |
| 有效但權限不足 | `403` | **沒有** | 使用者要換權限，或聯絡管理員 |

<Callout type="important" title="Header 的差別不是裝飾，是規格要求">
  RFC 9110 §15.5.2 規定：Server 回 `401` 時 **MUST** 送出 `WWW-Authenticate`，說明要用哪種認證方式。`403` 沒有這項**要求**——§15.5.4 完全沒有提到這個 Header。

  規格也沒有禁止它在 `403` 上出現。§11.6.1 寫的是「A server **MAY** generate a WWW-Authenticate header field in other response messages」，也就是說別的回應可以帶它。**所以正確的說法是「`401` 必須帶、`403` 不要求帶」，而不是「`403` 不該帶」。** 我們的 API 選擇不带，而 Client 不該把這個選擇當成保證。

  Client 端可以用這個 Header 決定行為：看到 `401` 就跳登入頁，看到 `403` 就顯示「你沒有這個權限」。**不要用兩個都跳登入頁的寫法**，那會讓權限不足的使用者被無限次踢回登入頁，而且永遠不知道自己為什麼不行。
</Callout>

單元 1 提過 `401 Unauthorized` 這個 reason phrase 容易讓人誤會成「沒有權限」。現在你有實據了：**`401` 處理的是「你是誰」，`403` 才是「能不能做」。**

## 06. 過期：一枚簽名正確但沒用的 token

簽名正確不代表還能用。這支 API 提供一個 `exp` 已經在過去的 token：

{"detail":"Token expired"}

還是 `401`。把這枚 token 解開看：

exp = expiration  到期時間
`}</Terminal>

**這枚 payload 只有一個時間欄位，而且 Server 只認它。** 對照第 03 節那枚正常的 token —— 那裡有 `iat` 和 `exp` 兩個，這裡只有 `exp`，因為 `main.py` 的 `login-expired` 沒有簽發時間可填。

差別在於兩件事：`iat` 只是**資訊**（「這是什麼時候發的」），`exp` 是**契約**（「超過這個時刻就不算數」）。Server 必須自己檢查 `exp`，因為簽名有效只證明「這段 payload 沒被改過」，不證明「這段 payload 現在還成立」。這兩件事都是 Server 的責任，而 Client 完全查不出來 —— Client 只是把字串轉交出去。

<Callout type="note" title="這是無狀態的代價">
  因為 Server 不保存狀態，它無法「把你的登入清掉」。Token 到期或被竊取，唯一能做的就是讓它在時間上失效，或把密鑰換掉讓所有 token 一起失效。單元 12 會處理「怎麼讓已發出的 token 提前失效」這個問題。
</Callout>

## 07. OAuth 在哪裡：發憑證的流程，和憑證本身

<Callout type="note" title="這堂課為什麼看不到 OAuth">
  因為這門課把四個角色塞進同一台 Server：`POST /login` 同時做了使用者授權、簽發憑證、驗證憑證三件事。發憑證的人和收憑證的人是同一個，授權流程就沒有戲可演；OAuth 登場的條件，是這幾件事分屬不同服務。

</Callout>

## 09. 把它接回 harness：誰可以寫事件，誰可以讀狀態

前一節講到 `401` 和 `403` 的差別：前者是「我不知道你是誰」，後者是「我知道你是誰，而你的角色不能做這件事」。harness 裡這兩件事都真的發生了，而且同一組 token 兩邊都要用。

先把 harness 的 token 簽出來。`harness/authz.py` 沒有套任何 JWT 函式庫，整個簽章流程就是第 04 節講的那三段：

<Terminal title="bash — mint the first token from the command line">{`
cd exercises/agent-harness
export HARNESS_SECRET='test-secret-not-for-production'
export TOKEN=$(python -m harness.authz root admin)
echo "$TOKEN"
`}</Terminal>

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkhBUk5FU1MifQ.eyJleHAiOjE3OTI4Mzk1OTAsInJvbGUiOiJhZG1pbiIsInN1YiI6InJvb3QifQ.<signature>
```

第三段是簽章，這裡用 `<signature>` 代替。把真的簽章貼進文件，等於教人把憑證貼進文件。

中間那段 base64url 解開就是 `{"exp":...,"role":"admin","sub":"root"}`。簽章涵蓋前兩段，所以呼叫端不能把 `role` 換掉而保留簽名——這正是第 04 節「簽名擋的是篡改」的用途。

接著，harness 有三個角色，分級的意思是 `writer` 讀得到、`reader` 寫不了：

| 角色 | 可以做什麼 |
|---|---|
| `reader` | 讀重播出來的狀態。不能寫事件。 |
| `writer` | 寫事件、讀狀態。 |
| `admin` | writer 做得到的都做得到，外加簽發新 token。 |

現在把那兩種拒絕都跑一次：

<Terminal title="bash — 401 and 403, two different problems" flavor="output">{`
$ curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8010/events
401

$ curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8010/events/tool-result \\
    -H "Authorization: Bearer $READER_TOKEN" -H 'Content-Type: application/json' \\
    -d '{"tool_call_id":"call_1","tool_name":"todowrite"}'
403
`}</Terminal>

`401` 的修法是重新登入，`403` 的修法是換角色。把它們分成兩個狀態碼，Client 才知道該做哪一件。

<Callout type="note" title="這個單元的規則">
  每個請求帶著一個角色，寫與讀都要先對角色。harness 對「能寫事件」和「能讀狀態」是兩個獨立的檢查，因為這兩件事的風險不同：寫進去的事件會變成之後每一次重播的基礎。
</Callout>

## 10. Refresh Token：一枚 token 不夠用的時候

第 03 節講過 JWT 的 `exp`：token 過期後 Server 回 `401 Token expired`。這帶來一個兩難：

- **token 壽命短**：被偷走也只偷到短時間，但使用者頻繁被踢回登入頁，體驗差。
- **token 壽命長**：使用者不用頻繁登入，但外洩後攻擊者長時間可用。

解法是**把「證明身分」和「換發新憑證」拆成兩枚 token**：

- **AT（Access Token）**：短命（幾分鐘到幾小時）。每次呼叫受保護 API 時帶在 `Authorization` header，Server 驗簽名 + 檢查 `exp`。被偷走也只偷到短時間。
- **RT（Refresh Token）**：長命（幾天到幾週）。**只在 AT 過期時用一次**，去換一張新的 AT，不用重新登入、不用重新輸入密碼。
- **ET（Expiration Time）**：Server 告訴 client「AT 什麼時候過期」，client 可以在過期前主動用 RT 去換新 AT，避免請求失敗。

流程：

```
1. 登入 → Server 發 AT（短）+ RT（長）+ ET
2. client 用 AT 呼叫 API（正常請求）
3. AT 過期 → client 用 RT 去換新 AT（不用重新登入）
4. RT 也過期或被撤銷 → 回到登入頁
```

**為什麼要分開**：AT 外洩，攻擊者最多用幾分鐘；RT 外洩，攻擊者可以換出新的 AT，但 RT 只在「換發」時用一次，被用到的頻率低。RT 通常還綁定裝置／IP，進一步降低風險。

<Callout type="note" title="本課的 JWT 就是 Access Token">
  第 02 節發的那枚 JWT，本質上就是 Access Token。本課沒有實作 refresh token，因為那是進階主題；但你讀別人的 API 文件時，看到 `access_token` / `refresh_token` / `expires_in` 這三個欄位，就知道它們在做同一件事。
</Callout>
