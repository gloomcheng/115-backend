第六課你看到 `GET /users` 回 `405 allow: POST`，因為那條集合路徑還沒有「列出全部」的路由。第七課講了 `422` 怎麼來的。第五課你已經讓資料活過了行程結束。

這一課把三件事接起來：**`path` 指向資料庫裡的一筆東西，`method` 決定你對它做什麼。**

CRUD 這四個字母是 Create、Read、Update、Delete。整個 Web 後端的寫入操作基本上都是這四種，加上單元 6 講過的「讀取全部」。它們每一種都要對到一條 SQL，所以程式放在 `exercises/08-crud/main.py`，儲存的資料庫就是第五課那個 `sqlite3` 檔案。

## 01. 集合路徑終於派上用場

第六課那個 `405 allow: POST` 是這樣來的：集合路徑 `/users` 登錄了，但只有 `POST`。現在補上讀取：

<Terminal title="Terminal 2 — bash — the collection, empty" flavor="output">{`
> curl -i http://127.0.0.1:8002/users
< HTTP/1.1 200 OK
< content-length: 2

[]
`}</Terminal>

`200`，Body 是空陣列。**這兩件事合起來才是重點**：路由存在（所以不是 `405`），資料真的沒有（所以不是 `404`），而且 Body 是一個合法的空集合，不是 `null` 也不是 `""`。

<Callout type="warning" title="空集合和查不到，是兩個不同的答案">
  一個空的資源集合回 `200` 加 `[]`；一個不存在的資源回 `404`。寫 Client 的時候，這兩件事的處理方式完全不同：前者要畫出「還沒有任何東西」，後者要畫出「這個東西不存在」。把它們混成同一個回應，Client 就沒辦法分辨。
</Callout>

## 02. 建立一筆，並且告訴 Client 它住在哪裡

<Terminal title="bash — create" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8002/users \\
>   -H 'Content-Type: application/json' -d '{"name":"iris","role":"student"}'
< HTTP/1.1 201 Created
< content-length: 32

{"name":"iris","role":"student"}
`}</Terminal>

第六課留了一個問題：那支練習 API 的 `201` 沒有 `Location`，而 RFC 9110 說 Server 應該回報新資源的 URL。你可以在自己的 API 裡補上：

<Terminal title="main.py — returning the created resource's URL" flavor="output">{`
@app.post("/users", status_code=201)
def create_user(payload: UserIn):
    ...
    return JSONResponse(
        status_code=201,
        content={"name": payload.name, "role": payload.role},
        headers={"Location": f"/users/{payload.name}"},
    )
`}</Terminal>

有了 `Location`，Client 就不必猜：它讀 `Location`，接著 `GET` 那個網址就知道剛建立的東西現在是什麼狀態。沒有的話，Client 只能從 Body 的欄位反推，而 Body 裡要是沒有識別欄位，就連推都推不出來。

現在重複建立同一個名字：

<Terminal title="bash — the same name twice" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8002/users \\
>   -H 'Content-Type: application/json' -d '{"name":"iris"}'
< HTTP/1.1 409 Conflict

{"detail":"User already exists"}
`}</Terminal>

**`409`。** 這個狀態碼在第七課出現過一次——當時我們說 RFC 9110 把「與資源目前狀態衝突」的位置指派給它，而實務上常常被 `422` 頂替。現在它是對的位置，因為這裡就是主鍵衝突。

而且它是 SQLite 擋下來的，不是 Python 檢查的：

<Terminal title="bash — the rule lives in the schema" flavor="output">{`
$ sqlite3 users.db ".schema users"
CREATE TABLE users ( name TEXT PRIMARY KEY NOT NULL, role TEXT);
`}</Terminal>

`name TEXT PRIMARY KEY` 這行是第五課說的「規則與資料同住」。`sqlite3.IntegrityError` 是引擎丟出來的，你的 route 只是把它翻譯成 `409`。

<Callout type="important" title="為什麼這裡是 409 而不是 422">
  Request 本身完全合法：`{"name":"iris"}` 語法對、型別對、欄位齊全。問題是**目標資源已經在那裡**。這正是 409 的定義範圍，把它說成「內容無法處理」會讓 Client 誤以為改資料就能解決。
</Callout>

## 03. 讀回來：兩條不同的路

<Terminal title="bash — member then collection" flavor="output">{`
> curl -s http://127.0.0.1:8002/users/iris
{"name":"iris","role":"student"}

> curl -s http://127.0.0.1:8002/users
[{"name":"iris","role":"student"}]
`}</Terminal>

兩條都是 `200`，但回來的東西不同：`/users/{name}` 回一個物件，`/users` 回一個陣列。**差別在 path 有沒有帶 `{name}`**——成員路徑識別一筆，集合路徑識別一整組。

這一課把它們記成一張表：

| 目標 | 識別什麼 | Body 是什麼 |
| --- | --- | --- |
| `/users` | 一整組 users | 陣列，可能是空的 |
| `/users/{name}` | 集合裡的其中一筆 | 一個物件，或 `404` |

## 04. 修改：PUT 換掉整筆，PATCH 換掉部分

這兩個 method 的差別很容易記錯，而且它直接對應到 SQL 的一個差別。

<Terminal title="bash — PUT sends every field" flavor="output">{`
> curl -i -X PUT http://127.0.0.1:8002/users/iris \\
>   -H 'Content-Type: application/json' -d '{"name":"iris","role":"ta"}'
< HTTP/1.1 200 OK

{"name":"iris","role":"ta"}
`}</Terminal>

`PUT` 送的是 `role:"ta"`，它把整筆狀態換掉。現在只用 `PATCH` 改一個欄位：

<Terminal title="bash — PATCH sends only what changes" flavor="output">{`
> curl -i -X PATCH http://127.0.0.1:8002/users/iris \\
>   -H 'Content-Type: application/json' -d '{"role":"student"}'
< HTTP/1.1 200 OK

{"name":"iris","role":"student"}
`}</Terminal>

對照兩次的 SQL 就清楚了：

| method | 送什麼 | SQL |
| --- | --- | --- |
| `PUT` | 整筆狀態 | `UPDATE users SET name = ?, role = ? WHERE name = ?` |
| `PATCH` | 只有要改的欄位 | `UPDATE users SET role = ? WHERE name = ?` |

<Callout type="important" title="PUT 送空值會清掉欄位">
  `PUT` 的語意是「這份 Body 就是這筆資源現在的全部狀態」。所以 `PUT -d '{"name":"iris"}'`（沒有 `role`）會把 `role` 設成 `null`，而不是保留原本的值。`PATCH` 才是不動沒提到的欄位。這是為什麼 Client 端「編輯表單只改一個欄位」要用 `PATCH`，用 `PUT` 會把沒送出來的欄位清掉。
</Callout>

送一個不存在的欄位試試：

<Terminal title="bash — PATCH ignores nothing it was told it does not know" flavor="output">{`
> curl -s -o /dev/null -w '%{http_code}\n' \\
>   -X PATCH http://127.0.0.1:8002/users/iris \\
>   -H 'Content-Type: application/json' -d '{"nickname":"x"}'
422
`}</Terminal>

`422`，因為這支 route 只認 `name` 與 `role`，而且沒有任何欄位可以改。這是第七課講過的：驗證發生在 handler 之前還是之後，決定了 Client 拿到 `422` 還是 `500`。這裡是前者。

## 05. 刪除兩次，都回 204

<Terminal title="bash — delete, then delete again" flavor="output">{`
> curl -i -X DELETE http://127.0.0.1:8002/users/iris
< HTTP/1.1 204 No Content

> curl -i -X DELETE http://127.0.0.1:8002/users/iris
< HTTP/1.1 204 No Content
`}</Terminal>

驗證段落講完了，接下來是刪除。同一筆刪兩次，**兩次都是 `204`。** 這個選擇需要一個理由，而理由不在這支 route 裡。

刪除不存在的東西該回 `204` 還是 `404`？這題連教科書都直接承認沒有共識。Full Stack Open 的原文：

<Terminal title="Full Stack Open — no consensus on this one" flavor="output">{`
"There's no consensus on what status code should be returned to a DELETE
request if the resource does not exist. The only two options are 204 and
404. For the sake of simplicity, our application will respond with 204 in
both cases."
`}</Terminal>

<Callout type="note" title="這支 API 選 204 的理由">
  單元 1 講過 `DELETE` 是 idempotent：刪兩次的**最終狀態**相同，那筆資料都不在了。「最終狀態」是重點——不是「有沒有東西被刪掉」。回 `204` 表示「你要的狀態已經達成」，回 `404` 表示「你要的東西不存在」，那是另一個問題。

  真實系統兩種都有。你串接別人的 API 時，先讀它的文件；這正是第十四課的主題。
</Callout>

但**讀取**就不一樣了。刪掉之後再讀：

<Terminal title="bash — reading after delete" flavor="output">{`
> curl -i http://127.0.0.1:8002/users/iris
< HTTP/1.1 404 Not Found

{"detail":"User not found"}
`}</Terminal>

`404`。刪除的「目標狀態」和讀取的「目標狀態」在這裡被明確區分開了：刪除要的是「它不在」，讀取要的是「它在那裡」。

最後回到資料庫確認：

<Terminal title="bash — the rows are actually gone">{`
$ sqlite3 users.db "SELECT COUNT(*) FROM users;"
0
$ curl -s http://127.0.0.1:8002/users
[]
`}</Terminal>

`204` 是「我沒有 Body 給你」，不是「我沒做事」。資料庫裡確實少了那一筆。

## 06. 把五個 method 對起來

這一課沒有新規則，只有一張對照表。寫 Client 或寫 route 的時候，照著它對：

| method | 目標 | 對資料庫 | 正常回 | 目標不存在時 |
| --- | --- | --- | --- | --- |
| `GET` | `/users` | `SELECT` 全部 | `200` + 陣列 | 不適用，集合永遠存在 |
| `GET` | `/users/{name}` | `SELECT` 一筆 | `200` + 物件 | `404` |
| `POST` | `/users` | `INSERT` | `201` + 新資源 | `409`（主鍵重複） |
| `PUT` | `/users/{name}` | `UPDATE` 全部欄位 | `200` | `404` |
| `PATCH` | `/users/{name}` | `UPDATE` 部分欄位 | `200` | `404` |
| `DELETE` | `/users/{name}` | `DELETE` | `204` | `204`（本課的選擇） |

第二欄和第五欄是這一課真正要記的兩件事：**path 決定你識別哪一個目標，method 決定你對它做什麼。** Status Code 是那條 SQL 執行完的結果，不是你挑的。

順帶確認一下這條集合路徑現在接受什麼：

<Terminal title="bash — the allow header has grown" flavor="output">{`
> curl -s -o /dev/null -w 'GET  /users -> %{http_code}\n' http://127.0.0.1:8002/users
GET  /users -> 200

> curl -i -X PUT http://127.0.0.1:8002/users -H 'Content-Type: application/json' -d '{"name":"x"}'
< HTTP/1.1 405 Method Not Allowed
< allow: GET, POST
`}</Terminal>

第六課時這裡是 `allow: POST`。現在多了讀取，`allow` 變成 `GET, POST`——**路由表改了，`allow` 跟著變**，而那個 Header 是單元 4 說的「Server 照著自己的表列出可用的 method」。

<Callout type="note" title="為什麼 PUT 沒有集合版本">
  `/users` 加上一個 `PUT`，語意上等於「把整組 users 換掉」。這在實務上幾乎沒人做，而且危險——它會清掉所有沒列在 Body 裡的成員。這一課的 route 沒有登錄它，所以 Server 誠實地回 `405` 加上 `allow` 告訴你它接受什麼。
</Callout>

## 07. SQL injection：值可以綁，欄位名不行

五個 method 都通了，資料也存得下來。但在討論「Client 送什麼進來」之前，有一件事必須先確認：**這些字是怎麼進到資料庫的？** 答案在每一個 `execute()` 裡。

先看最常見的那一行：

```python
row = connection.execute("SELECT name, role FROM users WHERE name = ?", (name,)).fetchone()
```

那個 `?` 就是全部的防線。Client 送的 `name` 不管長什麼樣，都被當成**值**綁進去，不會變成句子的結構。

<Callout type="important" title="先把這個區分講清楚，後面的注入才有意義">
  SQL 句子有兩種東西：**結構**（`SELECT`、`WHERE`、逗號、欄位名）與**值**（`iris`、`student`）。

  `?` 只能替換**值**。你可以綁十個值，但你沒有辦法把 `?` 放在 `ORDER BY` 後面讓它變成一個欄位名。

  注入的定義因此是：**Client 的文字改變了句子的結構**。
</Callout>

### 07.1 值被接進去：整張表被讀出來

`injection.py` 把同一個查詢寫兩種版本。差別只有一個地方：

<Terminal title="bash — the bug, then the fix" flavor="output">{`
$ python injection.py value
1. The value is pasted into the statement
   searching for the user named iris:
    SQL: SELECT name, role FROM users WHERE name = 'iris'
    -> ('iris', 'student')
   searching for ' OR '1'='1:
    SQL: SELECT name, role FROM users WHERE name = '' OR '1'='1'
    -> ('iris', 'student')
    -> ('root', 'admin')
   the same search with a bound parameter:
    SQL: SELECT name, role FROM users WHERE name = ?
    -> 0 rows
`}</Terminal>

看中間那行 SQL 是怎麼來的。Client 送 `' OR '1'='1`，程式碼把它放進單引號裡，於是資料庫讀到的句子是：

```sql
SELECT name, role FROM users WHERE name = '' OR '1'='1'
                                          ↑ ↑
                                          └ └ 兩個引號中間什麼都沒有，
                                            所以 `name` 被比對成空字串，
                                            `OR '1'='1'` 變成了句子的新條件
```

從 `WHERE` 開始，條件變成了 `name 等於空字串，**或者** 1 等於 1`。後面那半句恆為真，所以每一列都通過。

這個條件一個字都沒被擋下。**Client 送的是一個名字，Server 執行的是「回傳所有人」**，而且沒有任何錯誤——這是一個成功的 `200`。

<Terminal title="bash — the same mistake in a DELETE" flavor="output">{`
$ python injection.py delete
2. The same mistake in a DELETE
   deleting the user named iris:
    SQL: DELETE FROM users WHERE name = 'iris'
    -> deleted 1, 1 left
   deleting 'x' OR '1'='1 :
    SQL: DELETE FROM users WHERE name = 'x' OR '1'='1'
    -> deleted 2, 0 left
   the same request with a bound parameter:
    SQL: DELETE FROM users WHERE name = ?
    -> deleted 0, 2 left
`}</Terminal>

<Callout type="warning" title="`deleted 2, 0 left`：一個請求，兩筆資料，沒了">
  讀出來的資料至少還會出現在回應裡，攻擊者看得到就知道成功了。

  `DELETE` 不會回傳任何東西。Server 會回 `204 No Content`，乾淨俐落，跟正常刪除一模一樣。**被刪掉的人不會收到通知，因為根本沒有人通知過他們。**
</Callout>

### 07.2 同一堂課的 `main.py` 也有一次「字串被接進去」

回到 `main.py` 的 `update_user`：

```python
assignments = ", ".join(f"{column} = ?" for column in updates)
cursor = connection.execute(
    f"UPDATE users SET {assignments} WHERE name = ?",
    (*updates.values(), name),
)
```

這裡有 f-string，但**它不是漏洞**——因為 `updates` 已經被過濾了：

```python
updates = {key: value for key, value in payload.items() if key in {"name", "role"}}
```

<Callout type="important" title="這個白名單就是防線本體">
  值（`?` 綁的）本來就安全，不需要白名單。**欄位名沒有 `?` 可以用**，唯一的做法就是自己檢查。

  所以這裡的白名單不是「多寫一層防禦」，是**唯一**的防禦。拿掉它，這段程式碼立刻變成注入點。
</Callout>

這個白名單有多重要，用實驗量得出來。先送一個從來不存在的欄位名，看它擋不擋得住：

<Terminal title="bash — a key name that was never a column" flavor="output">{`
$ curl -i -X PATCH http://127.0.0.1:8002/users/iris \\
    -H 'Content-Type: application/json' \\
    -d '{"role = '"'"'admin'"'"', name":"x"}'
< HTTP/1.1 422 Unprocessable Entity
{"detail":"No supported field to update"}

$ sqlite3 users.db "SELECT name, role FROM users;"
iris|student
root|admin
`}</Terminal>

白名單擋住了，`422`，資料沒動。

現在把 `if key in {"name", "role"}` 改成 `if isinstance(key, str)`，重啟 Server，再送一次：

<Terminal title="bash — the same request after removing the allow-list" flavor="output">{`
$ curl -i -X PATCH http://127.0.0.1:8002/users/iris \\
    -H 'Content-Type: application/json' \\
    -d '{"role = '"'"'admin'"'"', name":"x"}'
< HTTP/1.1 500 Internal Server Error

$ sqlite3 users.db "SELECT name, role FROM users;"
x|admin
root|admin
`}</Terminal>

<Callout type="warning" title="回應是 500，但資料庫已經被改了">
  `role = 'admin', name` 這個字串被接進去之後，湊出來的句子是：

  ```sql
  UPDATE users SET role = 'admin', name = ? WHERE name = ?
  ```

  逗號讓 SET 多了一個欄位，攻擊者用一個**欄位名**指定了 `role` 的值。`iris` 從 `student` 變成 `admin`。

  然後為什麼是 `500`？因為程式接著用舊的 `name`（`iris`）去查回這一筆，`iris` 已經不存在了，取到 `None`，然後 `None["name"]` 就炸了。

  **所以這一次回應騙了你。** 攻擊者看到 `500`，會以為失敗然後收手——但權限已經被改掉了。這比乾乾淨淨的成功更難察覺。

把 `main.py` 改回去。白名單和 `?` 兩道防線都在的時候，你根本不需要想注入這件事。
</Callout>

### 07.3 你可以防 Injection，沒有辦法靠「把字串濾乾淨」

Server 端最常見的直覺做法是：擋掉那些看起來很壞的字元。`injection.py identifier` 示範了為什麼這行不通。

<Terminal title="bash — the column name cannot be bound" flavor="output">{`
$ python injection.py identifier
3. The column name cannot be a placeholder
   ORDER BY name, checked against an allow-list:
    SQL: SELECT name, role FROM users ORDER BY name
    -> ('iris', 'student')
    -> ('root', 'admin')
   ORDER BY role, checked against an allow-list:
    SQL: SELECT name, role FROM users ORDER BY role
    -> ('root', 'admin')
    -> ('iris', 'student')
   ORDER BY name; DROP TABLE users -- , with the allow-list:
    -> 0 rows
   the same input, with the allow-list removed:
    SQL: SELECT name, role FROM users ORDER BY name; DROP TABLE users --
    -> ('ERROR', 'You can only execute one statement at a time.')
   and a column the author never imagined, still unchecked:
    SQL: SELECT name, role FROM users ORDER BY 1
    -> ('iris', 'student')
    -> ('root', 'admin')
`}</Terminal>

看最後那兩段示範的輸出，兩段的差別是整個安全觀念的關鍵。

先看第二段的輸出：它送 `name; DROP TABLE users --`，**資料庫驅動程式擋了下來**，回 `You can only execute one statement at a time.`。表還在。你看到這裡可能會覺得「那沒差，驅動程式擋住了」。

第三段就是為什麼這個想法不成立：

<Terminal title="bash — no DROP needed to cause damage" flavor="output">{`
    SQL: SELECT name, role FROM users ORDER BY 1
    -> ('iris', 'student')
    -> ('root', 'admin')
`}</Terminal>

`ORDER BY 1` 沒有任何危險字元，驅動程式也沒有理由擋它。它只是安靜地改了排序——**攻擊者不需要拿到 admin，也不需要刪表，改掉查詢結果的順序就已經改掉了資料。**

<Callout type="important" title="為什麼字串過濾一定會漏">
  你要擋的是「壞的輸入」，但你沒辦法列出所有輸入。你能擋掉 `DROP TABLE`，擋不掉 `ORDER BY 1`；你擋掉引號，會擋掉 `O'Brien` 這個合法的名字。

  **白名單不一樣。**它不問「這個輸入看起來安不安全」，它問「這個輸入是不是我預期的那一個」。`{"name", "role"}` 這個集合是有限的、你自己寫的、可以讀完的。

  這是整個後端安全最重要的一條：**能列舉允許的值，就不要過濾拒絕的值。**
</Callout>

### 07.4 判斷注入風險，只看一件事

<Callout type="important" title="一個問題">
  這一行裡，Client 的文字是綁進去的，還是被接進去的？

  - **綁進去**（`?` + 參數）→ 安全。
  - **接進去**（f-string、`%`、`+` 組字串）→ 看有沒有白名單擋著。沒有就是漏洞。
</Callout>

拿本課的 `main.py` 對照，那十幾個 `execute` 呼叫裡：

- 值全部用 `?` 綁（`name`、`payload.name`、`payload.role`）——安全。
- 只有一處用 f-string（`f"UPDATE users SET {assignments} ..."`）——靠白名單活著。

<Callout type="note" title="為什麼 ORM 之後這件事還是會出現">
  用 ORM（SQLAlchemy、Django ORM）的時候，你幾乎不會自己寫 SQL，所以注入少很多。但 ORM 仍然提供「原生 SQL」的入口讓你繞過去，那個入口一樣要自己綁參數。

  **ORM 減少的是打錯字的機會，不是你的責任。**判斷標準還是一樣：Client 的文字有沒有被接進去。
</Callout>

## 08. 終端實戰驗證：五個 method 各跑一次

Terminal 1 跑著 `fastapi dev main.py --port 8002`。先清空資料：

<Terminal title="bash — clean start">{`
rm -f users.db
`}</Terminal>

**接著要重啟 Terminal 1 的 Server。** 這一步不能跳：正在執行的 Server 在啟動時就建好了資料表，你把檔案刪掉之後，它手上的那個連線仍然指向一個已經不存在的檔案。`GET /users` 會回 `500` 而不是 `[]`。重啟之後 Server 才會重新建立空表。

### 第一步：空集合

<Terminal title="bash — step 1" flavor="output">{`
> curl -i http://127.0.0.1:8002/users
< HTTP/1.1 200 OK
< content-length: 2

[]
`}</Terminal>

### 第二步：建立兩次

<Terminal title="bash — step 2" flavor="output">{`
> curl -i -X POST http://127.0.0.1:8002/users \\
>   -H 'Content-Type: application/json' -d '{"name":"iris","role":"student"}'
< HTTP/1.1 201 Created

> curl -i -X POST http://127.0.0.1:8002/users \\
>   -H 'Content-Type: application/json' -d '{"name":"iris"}'
< HTTP/1.1 409 Conflict

{"detail":"User already exists"}
`}</Terminal>

### 第三步：讀成員，再讀集合

<Terminal title="bash — step 3">{`
curl -s http://127.0.0.1:8002/users/iris
curl -s http://127.0.0.1:8002/users
`}</Terminal>

一個物件、一個陣列。

### 第四步：PUT 與 PATCH

<Terminal title="bash — step 4" flavor="output">{`
> curl -s -X PUT http://127.0.0.1:8002/users/iris \\
>   -H 'Content-Type: application/json' -d '{"name":"iris","role":"ta"}'
{"name":"iris","role":"ta"}

> curl -s -X PATCH http://127.0.0.1:8002/users/iris \\
>   -H 'Content-Type: application/json' -d '{"role":"student"}'
{"name":"iris","role":"student"}
`}</Terminal>

### 第五步：刪兩次，然後讀

<Terminal title="bash — step 5" flavor="output">{`
> curl -i -X DELETE http://127.0.0.1:8002/users/iris
< HTTP/1.1 204 No Content

> curl -i -X DELETE http://127.0.0.1:8002/users/iris
< HTTP/1.1 204 No Content

> curl -i http://127.0.0.1:8002/users/iris
< HTTP/1.1 404 Not Found

{"detail":"User not found"}
`}</Terminal>

### 第六步：用 sqlite3 確認

<Terminal title="bash — step 6">{`
sqlite3 users.db "SELECT COUNT(*) FROM users;"
curl -s http://127.0.0.1:8002/users
`}</Terminal>

`0` 與 `[]`。

### 第七步：把白名單拿掉

前六步都在用白名單擋欄位名。停掉 Server，把 `main.py` 裡的 `if key in {"name", "role"}` 改成 `if isinstance(key, str)`，重啟 Server，塞兩筆資料進去，然後送那個從來不存在的欄位名：

<Terminal title="bash — step 7, allow-list removed" flavor="output">{`
> curl -s -X POST http://127.0.0.1:8002/users -H 'Content-Type: application/json' -d '{"name":"iris","role":"student"}'
{"name":"iris","role":"student"}

> curl -i -X PATCH http://127.0.0.1:8002/users/iris \\
    -H 'Content-Type: application/json' \\
    -d '{"role = '"'"'admin'"'"', name":"x"}'
< HTTP/1.1 500 Internal Server Error

$ sqlite3 users.db "SELECT name, role FROM users;"
x|admin
`}</Terminal>

資料庫裡的 `iris` 已經變成 `admin`，但回應是 `500`。這是第 07 節那個教訓的完整現場。

第七步結束後，**把 `main.py` 改回去**，後面的單元都建立在那個白名單上。
